# F4 - Query Rewriting and Expansion Techniques for RAG

**Research Angle**: Query optimization techniques — HyDE, Multi-Query, Step-Back Prompting, Query Decomposition, Rewrite-Retrieve-Read, Self-RAG, Adaptive RAG
**Date**: 2026-06-18
**Sources**: arXiv papers, LangChain blog, RAG survey literature (2022–2025)

---

## Finding 1 - HyDE (Hypothetical Document Embeddings): Zero-Shot Dense Retrieval via LLM-Generated Hypothetical Answers

**Claim**: HyDE instructs an LLM to generate a hypothetical document that *would* answer the query, then encodes that document (not the raw query) for retrieval. This bridges the semantic gap between short queries and long document passages. HyDE significantly outperforms unsupervised dense retrievers (Contriever) and shows performance comparable to fine-tuned retrievers across web search, QA, and fact verification tasks — without any relevance labels.

**When it helps**:
- Zero-shot or low-label retrieval settings where no fine-tuned retriever is available
- Queries that are short, ambiguous, or phrased very differently from the target documents
- Domain-specific tasks where the LLM can generate plausible domain-relevant documents

**When it hurts**:
- If the LLM generates factually incorrect hypothetical documents, the retrieved results may be biased toward incorrect content (the "hallucination amplification" problem)
- High-frequency or well-structured queries where the raw query embedding already matches well — HyDE adds latency for no gain
- Domains where the LLM has weak prior knowledge (niche technical domains)

**Latency cost**: +1 LLM generation call (~200–500ms for a single hypothetical doc) + embedding computation. Total overhead: ~0.3–1.0s per query depending on LLM and hardware. Can be parallelized with async retrieval.

**Benchmarks**: Original paper (Gao et al., 2022) showed HyDE outperforms Contriever by 5–10% recall@100 on BEIR benchmark. On TriviaQA and Natural Questions, it approaches supervised DPR performance.

**Source**: Gao et al., "Precise Zero-Shot Dense Retrieval without Relevance Labels" (arXiv:2212.10496, Dec 2022)
**Confidence**: High — well-cited foundational paper (4000+ citations), widely adopted in LangChain/LlamaIndex

## Finding 2 - Multi-Query Retrieval: Generating Query Variants to Maximize Recall

**Claim**: Multi-Query generates N semantically equivalent but lexically diverse query variants from the original question using an LLM, retrieves documents for each variant independently, then deduplicates and ranks the union. This addresses the fundamental limitation that a single embedding can miss relevant documents due to vocabulary mismatch.

**When it helps**:
- Ambiguous or multi-faceted questions that can be interpreted multiple ways
- When high recall is critical (e.g., legal discovery, medical literature search)
- Cross-lingual retrieval where different phrasings may hit different document clusters

**When it hurts**:
- Simple, well-defined factual questions where a single retrieval is sufficient — adds unnecessary latency and noise
- When the retriever is already high-quality and tuned for the domain, marginal gain is small
- Increases the risk of retrieving irrelevant documents (precision may drop), requiring strong re-ranking

**Latency cost**: N× retrieval cost + 1 LLM call for query generation. For N=3–5 variants, this is ~2–5× the latency of single-query retrieval. With parallel retrieval and a fast LLM (e.g., GPT-3.5-turbo), practical overhead is 1–3 seconds.

**Benchmarks**: RAG-Fusion (Raudaschl, 2023) using reciprocal rank fusion over 4 sub-queries showed 10–15% improvement in answer relevance over single-query RAG on open-domain QA. LangChain's MultiQueryRetriever reports consistent improvements on conversational QA where user queries are vague.

**Source**: LangChain MultiQueryRetriever documentation; Raudaschl "RAG-Fusion" (2023 blog/cookbook); Gao et al. RAG Survey (arXiv:2312.10997)
**Confidence**: Medium-High — widely implemented in production frameworks, but systematic benchmarks are sparse compared to academic baselines

## Finding 3 - Step-Back Prompting: Abstracting Queries for Deeper Reasoning Before Retrieval

**Claim**: Step-Back Prompting (Google DeepMind) instructs the LLM to first generate a higher-level, more abstract version of the question before answering. This retrieves documents at the level of principles/concepts rather than specific details, improving reasoning on knowledge-intensive and multi-hop tasks. Applied to RAG, the step-back query serves as a better retrieval target for grounding the final answer.

**When it helps**:
- Multi-hop reasoning questions (e.g., "What is the population growth rate of the capital of the country where the 2008 Olympics were held?")
- STEM questions requiring retrieval of underlying principles/formulas
- Temporal reasoning and knowledge QA where specific facts chain to broader concepts

**When it hurts**:
- Simple factual lookups where the original query is already optimal for retrieval
- When the abstraction is too broad, retrieving overly generic documents that lack the specific answer
- Real-time applications where the extra LLM call for abstraction is too costly

**Latency cost**: +1 LLM call for abstraction generation (~200–400ms). Total overhead: ~0.3–0.8s. Modest compared to multi-query since only one additional query is generated.

**Benchmarks**: Original paper reports PaLM-2L improvements: MMLU Physics +7%, Chemistry +11%, TimeQA +27%, MuSiQue multi-hop +7%. GPT-4 shows similar gains on STEM tasks. These are *reasoning* benchmarks; the retrieval-specific improvements when combined with RAG are less formally benchmarked but report consistent quality gains in LangChain/LlamaIndex cookbooks.

**Source**: Zheng et al., "Take a Step Back: Evoking Reasoning via Abstraction in LLMs" (arXiv:2310.06117, Oct 2023, ICLR 2024)
**Confidence**: High — Google DeepMind, ICLR publication, strong benchmark results. Retrieval-specific gains less formally measured.

## Finding 4 - Query Decomposition: Breaking Complex Questions into Retrieval-Friendly Sub-Queries

**Claim**: Query Decomposition splits a complex, multi-part question into simpler, atomic sub-queries that each map to a single retrieval operation. Sub-answers are then synthesized into a final answer. This is essential for multi-hop QA where no single document contains the full answer.

**When it helps**:
- Compositional questions requiring information from multiple documents/sources
- Comparative questions ("Which is better, X or Y?") where each entity needs separate retrieval
- Questions with temporal constraints, conditional clauses, or nested dependencies

**When it hurts**:
- Questions that are already atomic — decomposition produces trivially similar sub-queries, wasting retrieval budget
- When the decomposition itself is incorrect (LLM misinterprets the question structure), downstream retrieval cascades the error
- Latency-sensitive applications where N sub-queries multiply retrieval time

**Latency cost**: 1 LLM call for decomposition + N retrieval operations + 1 LLM call for synthesis. For typical 2–4 sub-queries: ~1–4 seconds total overhead. Can be parallelized (sub-queries are independent).

**Benchmarks**: On HotpotQA and MuSiQue multi-hop benchmarks, decomposition-based approaches (including least-to-most prompting) improve accuracy by 10–20% over single-query RAG. IRCoT (Trivedi et al., 2022) showed F1 improvements of ~15% on multi-hop QA datasets.

**Source**: Referenced in Gao et al. RAG Survey (arXiv:2312.10997); LangChain blog "Deconstructing RAG" (Nov 2023); IRCoT (Trivedi et al., 2022)
**Confidence**: Medium-High — well-established concept; specific benchmark numbers vary by decomposition strategy quality

## Finding 5 - Rewrite-Retrieve-Read Pipeline: Adapting the Query to Bridge Retriever-Reader Gap

**Claim**: The Rewrite-Retrieve-Read framework (Ma et al., EMNLP 2023) recognizes that user queries are often poorly formatted for retrieval (too colloquial, ambiguous, or lacking key terms). It uses an LLM to rewrite the query before retrieval, then a trainable small rewriter (fine-tuned via RL with LLM reader feedback) aligns the rewritten query to both the retriever and the frozen LLM reader. This consistently improves downstream QA performance.

**When it helps**:
- Conversational or chat-based RAG where queries are informal, anaphoric ("What about that?"), or context-dependent
- When the retriever and reader have different "languages" (e.g., BM25 keyword retriever + semantic LLM reader)
- Cross-domain deployment where user terminology differs from corpus terminology

**When it hurts**:
- When the rewriter introduces artifacts or over-specifies the query, reducing recall
- Simple, well-formed queries where rewriting adds noise
- Requires training data for the RL-based rewriter — zero-shot LLM rewriting is simpler but less optimized

**Latency cost**: +1 LLM call for rewriting (~100–300ms) or small model inference (~10–50ms for a fine-tuned small LM). Minimal overhead if the rewriter is a small model. Total pipeline: +0.1–0.5s.

**Benchmarks**: Original paper shows consistent improvements on open-domain QA (Natural Questions, HotpotQA) and multiple-choice QA. The RL-trained rewriter outperforms zero-shot LLM rewriting by 2–5%. REPLUG (Shi et al., 2023) with tuned retriever improves GPT-3 (175B) language modeling by 6.3% and Codex MMLU by 5.1%.

**Source**: Ma et al., "Query Rewriting for Retrieval-Augmented Large Language Models" (arXiv:2305.14283, EMNLP 2023); Shi et al., "REPLUG" (arXiv:2301.12652, 2023)
**Confidence**: High — EMNLP publication, RL-trained rewriter shows consistent gains

## Finding 6 - Self-RAG: Learning to Decide WHEN to Retrieve via Self-Reflection Tokens

**Claim**: Self-RAG (Asai et al., 2023) trains a single LM to adaptively decide whether to retrieve at each generation step, using special "reflection tokens" (Retrieve, IsRel, IsSup, IsUse). The model can choose to skip retrieval entirely when its parametric knowledge is sufficient, or trigger retrieval when it encounters uncertainty. It then critiques the relevance of retrieved passages and its own generated text. A 7B Self-RAG model outperforms ChatGPT and retrieval-augmented Llama2-chat on open-domain QA, reasoning, and fact verification.

**When it helps**:
- Mixed workloads where some queries need retrieval and others don't (e.g., creative writing vs. factual QA)
- Long-form generation where factuality must be verified at each step
- Reducing unnecessary retrieval overhead for queries the model can already answer

**When it hurts**:
- Requires fine-tuning the LM with reflection token training data — cannot be applied to frozen/black-box models
- The "retrieve or not" decision is imperfect; the model may hallucinate confidence and skip retrieval incorrectly
- More complex inference pipeline — each generation step may involve a retrieval decision + critique, slowing generation

**Latency cost**: Retrieval is conditional. When retrieval is triggered: +retrieval time + critique token generation (~50–200ms per step). When retrieval is skipped: effectively no overhead vs. standard generation. On average, Self-RAG retrieves for ~30–60% of generation steps on open-domain QA, resulting in moderate average latency increase.

**Benchmarks**: Self-RAG 7B outperforms ChatGPT on PopQA (78.4% vs 73.0%), ALCE fact verification, and long-form generation tasks (ALCE score 4.0 vs 3.5 for retrieval-augmented Llama2-13B). Self-RAG 13B further improves. Citation accuracy significantly higher than all baselines.

**Source**: Asai et al., "Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection" (arXiv:2310.11511, Oct 2023, ICLR 2024)
**Confidence**: High — strong benchmark results, ICLR publication, open-source implementation

## Finding 7 - Adaptive-RAG: Routing Queries by Complexity to Optimal Retrieval Strategy

**Claim**: Adaptive-RAG (Jeong et al., NAACL 2024) goes beyond Self-RAG's binary retrieve/not decision by classifying queries into three complexity levels and routing each to the appropriate strategy: (1) no retrieval for simple queries, (2) single-step retrieve-and-read for medium complexity, (3) iterative/multi-step retrieval for complex queries. A small classifier (trained on auto-labeled complexity data) makes the routing decision, optimizing for both accuracy and efficiency.

**When it helps**:
- Production systems handling diverse query types (simple factual to complex multi-hop)
- Cost-sensitive deployments where minimizing unnecessary LLM + retrieval calls is important
- When the distribution of query complexity is mixed (e.g., customer support with both simple FAQs and complex troubleshooting)

**When it hurts**:
- The complexity classifier can misroute queries, leading to under-retrieval on complex questions or over-retrieval on simple ones
- Auto-labeling for classifier training requires running all strategies on a sample, which is expensive
- Not beneficial if the query distribution is uniform (all simple or all complex)

**Latency cost**: +1 classifier inference (~5–20ms, negligible). The main benefit is *reducing* average latency by skipping retrieval for simple queries (~30–50% of queries) and using targeted retrieval for the rest. Net effect: 20–40% latency reduction compared to always using multi-step retrieval.

**Benchmarks**: On open-domain QA benchmarks spanning multiple complexity levels, Adaptive-RAG improves overall accuracy by 2–5% while reducing total retrieval+generation cost by 20–40% compared to always using iterative retrieval. Outperforms both always-retrieve and never-retrieve baselines.

**Source**: Jeong et al., "Adaptive-RAG: Learning to Adapt Retrieval-Augmented Large Language Models through Question Complexity" (arXiv:2403.14403, NAACL 2024)
**Confidence**: Medium-High — NAACL 2024, but limited to open-domain QA; production deployment results are sparse

## Finding 8 - FLARE (Forward-Looking Active REtrieval): Iterative Retrieval During Generation

**Claim**: FLARE (Jiang et al., EMNLP 2023) implements active retrieval during generation: it iteratively generates a sentence, checks for low-confidence tokens, and if found, uses the upcoming sentence as a retrieval query to regenerate that sentence with fresh context. This enables retrieval at precisely the moments when the model's parametric knowledge is insufficient, rather than only at the start.

**When it helps**:
- Long-form generation tasks (report writing, multi-paragraph answers) where information needs shift throughout
- Knowledge-intensive generation where different parts of the answer require different document retrieval
- Tasks where upfront retrieval cannot capture all needed information in one pass

**When it hurts**:
- Short-form answers (single sentence or fact) where iterative retrieval adds unnecessary overhead
- When confidence calibration is poor — the model may trigger unnecessary re-retrievals or miss needed ones
- High computational cost due to multiple retrieval calls per generation

**Latency cost**: Highly variable — depends on how many low-confidence triggers fire. Typically 2–5× the latency of single-pass RAG for long-form generation. Each trigger adds one retrieval round-trip (~200–500ms).

**Benchmarks**: On long-form QA (ASQA, ELI5) and multi-hop reasoning, FLARE outperforms single-retrieval RAG by 3–8% in correctness metrics. Performance on summarization tasks is competitive or superior.

**Source**: Jiang et al., "Active Retrieval Augmented Generation" (arXiv:2305.06983, EMNLP 2023)
**Confidence**: Medium-High — EMNLP publication, strong for long-form generation, less applicable to short-form QA

## Finding 9 - CRAG (Corrective Retrieval Augmented Generation): Assessing and Correcting Retrieval Quality

**Claim**: CRAG (Yan et al., 2024) adds a lightweight retrieval evaluator that assesses the quality of retrieved documents and triggers different actions: if documents are confident, use them directly (with decompose-recompose filtering); if ambiguous, combine with web search results; if incorrect, discard retrieval entirely and rely on web search + LLM parametric knowledge. This makes RAG robust to retrieval failures.

**When it helps**:
- Domains with sparse or incomplete knowledge bases where retrieval often fails
- Production systems where retrieval quality varies (noisy corpora, stale indexes)
- When web search can supplement a limited private corpus

**When it hurts**:
- Web search introduces latency and external dependencies (API costs, rate limits, non-determinism)
- The evaluator itself can be wrong, discarding relevant documents or accepting irrelevant ones
- Adds complexity to the pipeline with evaluator + web search fallback

**Latency cost**: +evaluator inference (~10–50ms) + conditional web search (~0.5–2s if triggered). Average overhead depends on retrieval quality — in good-quality corpora, web search is rarely triggered (~100ms avg overhead); in poor corpora, frequent web search can add 1–2s average.

**Benchmarks**: On 4 datasets (PopQA, Biography, short-form QA, long-form QA), CRAG consistently improves over standard RAG by 3–10%. Most significant gains on datasets where retrieval quality is variable.

**Source**: Yan et al., "Corrective Retrieval Augmented Generation" (arXiv:2401.15884, Jan 2024, updated Oct 2024)
**Confidence**: Medium — recent paper with strong concept but limited independent reproduction

## Finding 10 - Modular RAG: The Convergence Framework for Query Optimization Techniques

**Claim**: The Modular RAG framework (Gao et al., 2024) decomposes RAG into independent modules and operators, enabling any combination of query transformation, routing, scheduling, and fusion techniques. This is the emerging paradigm that unifies all the above techniques: HyDE, Multi-Query, Step-Back, Decomposition, Self-RAG, and CRAG become composable operators within a flexible pipeline. Common patterns include linear (simple RAG), conditional (Adaptive-RAG), branching (Multi-Query), and looping (FLARE/Self-RAG).

**When it helps**:
- Complex production systems that need to combine multiple query optimization techniques
- When different queries benefit from different strategies (the meta-routing problem)
- Systematic evaluation and ablation of RAG components

**When it hurts**:
- Over-engineering for simple use cases — a well-tuned simple RAG pipeline often outperforms a complex modular one
- Debugging and observability become harder with more modules
- Each module adds latency; without careful optimization, modular systems can be very slow

**Latency cost**: Depends entirely on the chosen modules and routing. The framework itself adds no overhead, but composing multiple operators (e.g., decomposition + multi-query + re-ranking) can multiply latency 5–10× over naive RAG.

**Benchmarks**: The Modular RAG survey (2024) does not provide unified benchmarks but synthesizes results from individual techniques. The key insight is that the right combination is task-dependent — no single configuration dominates.

**Source**: Gao et al., "Modular RAG: Transforming RAG Systems into LEGO-like Reconfigurable Frameworks" (arXiv:2407.21059, Jul 2024); Gao et al., "RAG Survey" (arXiv:2312.10997, Dec 2023, updated Mar 2024)
**Confidence**: Medium-High — emerging consensus in the field, but practical deployment guidance is still developing

## Key Takeaways for Production RAG Systems

1. **Start simple**: A well-tuned basic RAG (good chunking, embedding model, top-k) is the baseline. Only add query optimization when there's measurable degradation.

2. **Query rewriting (Rewrite-Retrieve-Read) has the best cost/benefit ratio**: One small LLM call with minimal latency overhead and consistent improvements, especially for conversational interfaces.

3. **HyDE is the best zero-shot option**: When you don't have training data for the retriever, HyDE provides near-supervised performance at modest latency cost.

4. **Multi-Query and Decomposition are high-recall but expensive**: Use them selectively when recall is critical and latency budget allows. Always combine with re-ranking.

5. **Self-RAG and Adaptive-RAG represent the future**: Adaptive retrieval (deciding WHEN and HOW to retrieve) is more efficient than always-on retrieval. Self-RAG's reflection tokens are the most principled approach but require fine-tuning.

6. **Combine techniques judiciously**: Modular RAG enables composition, but latency compounds. A practical stack might be: Rewrite → Single Retrieval → Re-rank for most queries, with decomposition triggered only for complex queries.
