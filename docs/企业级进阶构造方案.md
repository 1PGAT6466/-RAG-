# 企业级进阶构造方案（伏羲 RAG 知识库）

> 定位：在现有 Advanced-RAG 能力上，补齐企业级生产系统的最后几块拼图。
> 适用：本仓库（E:\更新RAG框架），2026-09 基线。

---

## 0. 结论先行

**现状判定：你的系统不是玩具，检索链路已经达到 Advanced RAG 水准**（混合检索 + 动态 RRF + rerank 降级链 + 精确置顶 + 引用校验 + 流式入库 + OCR 乱码检测），工程上也已有 trace_id 日志、慢查询、健康检查、孤儿向量对账、离线检索基准（20 条）。

**真正拉开与企业生产系统差距的，不是算法，是三件套 + 两个上限：**

1. **质量评测闭环**（最大差距）—— 现在没有"可复现、可对比、可回归"的质量度量，改一个参数不知道是变好还是变坏，只能靠感觉。
2. **任务与数据生命周期**—— 任务队列驻留内存、瞬时错误不重试、重启即丢（标记 failed 需重传）；无备份、无版本、无回收。
3. **可观测性到告警的断层**—— 已有日志/指标雏形，但没有连续指标、没有阈值告警、没有历史可回溯。
4. **检索上限**：parent-child 上下文、multi-query、rerank 缓存等未做。
5. **权限/审计粗粒度**：只有 admin/user 两级，无文件级权限、无操作审计。

**一句话路线：先补"看得见质量"（评测），再补"扛得住故障"（任务队列 + 备份 + 告警），最后"提上限"（检索演进 + 审计）。**

## 1. 现状盘点（与代码一一对应）

| 权限 | JWT + RBAC（`auth/`） | 缺：文件级权限映射（对接 SeedDMS）、操作审计 |

## 2. 六大差距（按优先级）

### D1 质量评测断层（P0，第一优先）
**问题**：`retrieval_benchmark.py` 只有 20 条、判 top1 文件名是否含关键词，且要起服务跑；没有 Recall@K/MRR/nDCG、没有答案质量评测、没有历史基线对比。结果：改 chunk_size、改权重、换 embedding 模型，只能靠人工抽几问感受，**无法判断是否回归**。
**目标**：任何检索/生成相关改动，都能在 30 分钟内用数字回答"变好还是变坏，差多少"。

### D2 任务队列脆弱（P0）
**问题**：`_tasks` 内存态 + 每任务一个 daemon 线程；瞬时错误（LLM 超时、远程 embed 网络抖动）直接 failed 不重试；进程重启后 `mark_stale_tasks_failed` 把 running/pending 全标 failed，**用户必须重新上传**——这就是"功能点偶尔不可用、任务莫名失败"的主要来源。
**目标**：瞬时错误自动重试、重启后可续跑、失败可查因。

### D3 数据生命周期不完整（P0/P1）
**问题**：无备份（`data/rag.db + Chroma + uploads` 是全部家当，`reset_data/wipe_data` 反而有）；同名上传行为未定义；无归档/回收；SeedDMS 同步靠手动机器。
**目标**：一键备份/恢复演练；上传替换级联安全；增量同步自动。

### D4 可观测性到告警断层（P0 部分/P1）
**问题**：有 `/api/health`（DB/Chroma/LLM 配置/磁盘/降级率快照）、有 stage profile，但都是"点了才看"。没有连续指标，没有"降级率 >20% 自动通知"，日志只落本地 JSON 文件。
**目标**：关键指标连续采集 + 阈值触发通知 + 历史可回溯。

### D5 检索/生成上限（P1）
**问题**：检索命中子块后，上下文直接拼 top_k 子块（每块截 800 字、总 6000 字）；表格/规格类文档的"父段上下文"没用上；语义查询没有 multi-query；rerank 每次远程调用无缓存；embedding 无去重缓存。
**目标**：表格/长文档问题质量可量化提升；rerank/embed 成本下降。

### D6 权限与审计（P2）
**问题**：admin/user 两级，无文件级可见性控制（SeedDMS 有文档权限但未映射）；无操作审计（谁删的、谁改的元数据）。
**目标**：审计可追溯；权限按文件收敛。

## 4. 分层改造方案

### L1 质量评测闭环（P0，第一优先）

#### 4.1 检索评测升级
- **Golden set 结构化**：新建 `data/eval/golden_retrieval.json`，每条：`{query, expected: [file_id 或 文件名关键词], category, note}`。期望先按现有知识库用 SQL 核对（沿用 `retrieval_benchmark.py` 的校准方法），避免拍脑袋。
- **指标**：在现有 `search()` 返回里取 top-k，计算 **Recall@K、MRR、nDCG@K**（K=5/10），并按分类（工业精确 / OA 语义 / 通用）拆分，输出表格。
- **可离线/可脚本化**：`scripts/eval_retrieval.py` 支持两种模式：`--offline`（直接 import `src.retrieval.search.search`，不起 HTTP 服务，pytest/CI 可用）和 `--base`（走 API，兼容现状）。
- **历史基线**：每次跑分结果存 `data/eval/results/`（JSON，含 git 描述/时间/config 快照），跑分时可 `--compare 上次` 输出 diff。
- **回归门禁**：`pytest` 加一个 `tests/test_eval_gate.py`，读取 golden set 跑离线评测，**允许阈值（如 Recall@5 ≥ 0.85）不达标则测试失败**——任何配置/代码改动过不了门禁不合并。

#### 4.2 答案质量评测（LLM-as-judge）
- 新建 `scripts/eval_answer.py` + `data/eval/golden_answer.json`（30~50 条：从 golden_retrieval 里精选 + 线上真实提问）。
- 每个问题：检索 → 生成 → 用 Flash 模型做裁判，三问打分（1~5）：
  1. **忠实度**：答案是否仅基于引用内容，有无编造；
  2. **完整性**：是否覆盖问题要点；
  3. **引用正确性**：引用编号对应的 chunk 是否真的支撑该句。
- 输出 JSON 分数 + 低分坏例（答案+引用内容）人工归因，写入 `docs/eval/`。

#### 4.3 坏例回流闭环
- 线上点踩（`src/storage/feedback.py` 已有）→ 每周导出"被点踩 query + 当时的答案/引用" → 人工标注（期望文档/坏因）→ 进 golden set。
- **这是让系统"越用越准"的机制，不是一次性建设。**

#### 4.4 触发时机
- **任何以下改动必须跑评测**：chunk_size/overlap、BM25/向量权重、RRF 参数、rerank 开关或模型、embedding 模型、分词器、改写策略、切块策略、prompt 结构。

**验收**：golden set ≥30 条；跑分可复现、有历史对比；答案评测能产出 1-5 分和坏例清单；`pytest test_eval_gate.py` 成为质量门禁。

### L2 任务与数据生命周期（P0）

#### 4.5 持久化任务队列（替代内存 `_tasks` + 裸线程）
- **存储**：SQLite 新表 `task_queue`：`task_id, file_id, filename, stage(checkpoint), status(pending/running/retrying/done/failed/dead), attempts, max_attempts, last_error, next_retry_at, created_at, updated_at`。
- **执行**：保留 Stage 编排（`engine.py` 的结构很好），但：
  - **checkpoint 幂等**：每个 sync stage 完成后记录 stage 名，重启后从最后完成的 stage 续跑（如已 embed 的 chunk 不重 embed——按 file_id+chunk_index 去重）。
  - **重试**：瞬时错误（LLM 超时/网络/远程 embed 5xx）`attempts+1`，指数退避（1min/5min/30min），超 `max_attempts` 进 `dead`（死信），管理端可见可手动重试。
  - **业务错误**（解析失败/无内容/格式不支持）直接 `failed` 不重试。
- **Worker**：常驻一个 worker 线程从 `pending/retrying` 取任务（沿用 `RAG_INGEST_MAX_CONCURRENT` 信号量），不再每任务开线程。
- **启动恢复**：`recover_tasks` 改为 `running → retrying`（可续跑），`pending → 继续执行`，不再一刀切 failed。
- **兼容**：`get_status/list_tasks` API 不动，前端无感。

#### 4.6 文档版本化与同名策略
- 明确上传策略：**同名文件默认"新版本"**（旧文件标记 `superseded_by`，可选保留历史），或管理端可选"替换"（走 `delete_file` 级联 → 重入库）。
- `files` 表加 `version`, `superseded_by`, `deleted_at` 软删除字段；检索默认过滤 `superseded/deleted`。

#### 4.7 内容去重
- 入库前 `sha256(file_content)`，命中已有记录且内容未变 → 跳过重入库（或提示已存在）。防重复上传白耗 embedding 费用。

#### 4.8 SeedDMS 增量同步
- `watch_folder.py` 已有轮询模式；扩展为按 `mtime+size` 或 `hash` 检测变更：新增→入库，变更→替换重入库，删除→级联删除。定时（如每小时）跑一次。

#### 4.9 归档/回收站
- 删除改为软删除进回收站（30 天保留），到期物理删除（走 `delete_file` 级联 + Chroma）。

**验收**：kill 服务进程 → 重启 → 任务自动续跑不丢；模拟 LLM 超时 → 自动重试成功；同名上传产生版本而非冲突；SeedDMS 增删改能自动同步。

### L3 可观测性与告警（P0 部分 / P1）

#### 4.10 连续指标（Prometheus 格式，`/api/metrics`）
- 用 `prometheus-client`（或零依赖自写文本格式）暴露：
  - HTTP：QPS、延迟直方图（p50/p95）；
  - 检索：四路召回耗时、rerank 耗时、总耗时（现有 `_last_profile` 是单次快照，改为**聚合计数**：每阶段耗时入直方图）；
  - LLM：调用量、token 数、失败率、降级率（`llm_audit` 已有数据，接进来）；
  - 任务：成功率、平均耗时、retrying/dead 数；
  - 缓存：语义缓存命中率、rewrite 缓存命中率；
  - 数据规模：files/chunks/entities 数、Chroma 孤儿数、磁盘剩余。
- 若内网不想引入 Prometheus+Grafana：先做**轻量版**——`health_check.py` 升级为"巡检器"（每 5 分钟调 `/api/health` + 指标端点，阈值超限调 webhook 通知），历史写 `logs/metrics_history.jsonl` 供趋势查询。

#### 4.11 告警规则（首批）
| 指标 | 阈值 | 动作 |
|---|---|---|
| LLM 降级率 | >20%（近 1 小时） | 通知 + 检查 API key/额度 |
| 检索 p95 | >3s（近 10 分钟） | 通知 + 查 profile |
| 任务失败率 | >10%（近 1 小时） | 通知 + 查 dead 队列 |
| 磁盘剩余 | <10GB | 通知 + 清理/扩容 |
| Chroma 孤儿向量 | >0 | 通知 + 跑 cleanup 脚本 |
| 缓存命中率 | 骤降 >30% | 通知 + 查语义缓存版本/失效 |

#### 4.12 日志
- `logs/` JSON 按日轮转已有；补：压缩归档 + 保留 30 天；明确 trace_id 贯穿链路（已有，保持）。

**验收**：能回答"上周系统稳定性/检索质量如何"；任一阈值触发 5 分钟内收到通知；故障定位可用 trace_id 全链路。

### L4 检索与生成再演进（P1）

#### 4.13 Parent-child（父段上下文）——表格/长文档收益最大
- 切块时记录 `section_id`（当前 heading 对应的完整段落文本），`chunks` 表加 `section_id`（或 `parent_id`）。
- 检索命中子块 → 组装上下文时，**优先把命中块所属的完整 section 喂给 LLM**（不超过 token 预算时），子块仅用于检索命中。表格类（标准件新表、规格书）问题质量提升明显。
- 需要配套评测验证（回到 L1），确认后再推广到所有文档类型。

#### 4.14 Multi-query 扩展
- 仅对 `route == "semantic"` 的查询：LLM 生成 2~3 个变体（同义改写/不同角度），分别检索 → 合并去重 → 再走 RRF/rerank。
- 成本控制：变体数 2~3、Flash 模型、失败静默回退单查询；加 feature flag `RAG_MULTI_QUERY`（默认关，评测通过再开）。

#### 4.15 元数据过滤
- 检索 API 增加可选过滤参数：`category`、`authority≥n`、`date_range`、`doc_kind`；前端检索页加筛选器（复用现有分类字典 `classification.py`）。
- 实现：在召回层按 `file_id` 预过滤（SQL 条件进 `fts_search` / 向量检索前过滤），避免"检索后过滤"浪费候选。

#### 4.16 Rerank 缓存 + 本地模型选项
- 缓存键 `(query_hash, chunk_id)`，缓存 rerank 分数/排序结果；热门查询命中率可 >50%，省 API 费降延迟。
- 可选：本地 `BAAI/bge-reranker-v2-m3` 作为第一优先（离线、无延迟波动），SiliconFlow 降为第二级。

#### 4.17 Embedding 去重缓存
- 进程内 LRU：`text → vec`（复用 `semantic_cache` 思路）；重入库/近似文本免重算。注意与向量库一致性（删除文档时清缓存条目）。

#### 4.18 Token 预算模型化
- `_build_reference_context` 的 `max_chunk_chars=800 / max_total_chars=6000` 硬编码 → 改为按模型上下文窗口动态计算（如 DeepSeek 64k 上下文，预留输出 1k，检索用 token 预算 = 模型限制 × 0.6），按 token 数计（中英混合用近似换算），支持单文档"整段读入"模式。

#### 4.19 生成护栏（grounding 检查）
- 生成后校验：答案中**关键断言**（含具体数值/结论的句子）是否能在其引用的 chunk 里找到支撑；找不到 → 标记或提示"该结论缺乏文档支撑"。
- 用 Flash 模型做轻量 entailment 判断（可选开关），或先用规则（数值/型号出现在引用文本中）。

**验收**：表格类评测用例通过率提升（以 L1 数据为准）；rerank 缓存命中率 >50%；语义查询在 multi-query 开启后 Recall@5 提升且延迟增幅 <30%。

### L5 性能与部署（P1/P2）

#### 4.20 备份与恢复（先做，最便宜）
- `scripts/backup.py`：备份 `data/rag.db`（SQLite `VACUUM INTO` 一致性快照）+ Chroma 目录 + `uploads/` + `images/` + `.env`（脱敏），压缩为 `backups/rag-YYYYMMDD-HHMMSS.zip`，保留最近 N 份（默认 7），可选同步到第二盘/网盘。
- `scripts/restore.py`：从备份恢复（停服 → 覆盖 → 起服 → 启动对账）。**必须做一次恢复演练**，否则备份等于没有。

#### 4.21 容量监控与扩展路径
- 指标里含 files/chunks 数；当 chunks >50 万或检索 p95 劣化时，评估路径：
  a. SQLite+Chroma 单机（现状，够用）→ b. 向量独立服务（Chroma Server/ES）→ c. Postgres+pgvector + 独立检索服务。
- 归档策略：超 N 年/已 superseded 文档移入只读归档库（`rag_archive.db`），在线库瘦身。

#### 4.22 部署收敛
- 新增 `Dockerfile` + `docker-compose.yml`（uvicorn + 数据卷挂载 `data/ logs/ backups/`），内网部署可选项。
- Windows 运维统一入口：`start_service.cmd` 已有，补"状态/重启/备份/日志尾部"子命令（一个 `ragctl.cmd`）。
- 前端构建产物服务方式保持（`server.py` SPA fallback）。

#### 4.23 前端性能（低成本）
- Element Plus 按需引入（当前全量注册 → 938KB chunk，`frontend/src/main.ts` 改 `unplugin-vue-components`），gzip 后预计省 60%+。
- 网络异常/后端 5xx 的前端提示（现有错误处理基础上升级为全局 toaster + 重试按钮）。

**验收**：备份恢复演练成功一次；`ragctl status` 可用；前端包体积显著下降；压测（50~100 并发）检索 p95 <2s。

## 6. 关键取舍（避免过度工程）

1. **评测先于优化**：一切检索/生成改动以 L1 数字为准，不为打磨而打磨（项目历史里"否决 FTS 双表重构、否决 RRF 盲目调参"的做法是对的，延续这个纪律）。
2. **任务队列用 SQLite 而非 Redis/Celery**：单机内网、零新依赖、重启续跑即可满足；只有未来多实例/多机时才迁 Redis。
3. **GraphRAG 不做全量社区摘要**：当前实体抽取 + 图谱召回已覆盖连接器/材料/标准等关系场景；除非评测显示"跨文档多跳关系"类问题占比高，否则不投入（成本高、难维护）。
4. **多租户不做**：内网单团队场景，文件级权限 + 审计先行即可；复杂租户隔离留到真正需要时。
5. **轻量告警优先**：内网可先不引 Prometheus+Grafana，巡检器 + webhook 通知 + 历史 JSONL 足够；规模上来再上全套。
6. **parent-child 先试点后推广**：先对表格/规格类文档开启，用评测验证，避免全量索引重做风险。
