# 阶段收获蒸馏（框架开始 → 2026-08-17）

> 本文是「伏羲」RAG 工业知识库从 0 到当前阶段的方法论沉淀，不是任务流水账。
> 目标是让未来的自己（及任何接手的人）一眼看清：我们建了什么、踩了什么坑、沉淀了什么判断。

---

## 一、我们到底建了什么

**一句话**：一个「数据库式内核 + 认知层图谱 + 插件运行时」的 RAG 工业知识库。

```
L0 插件运行时（子进程隔离 + manifest 契约 + 状态机）
L1 基础检索层（jieba BM25 + ChromaDB 向量 + 图谱召回，RRF 融合 + Rerank 精排）
L2 管理交互层（文件筛选 + 型号/材料标签 + 多维表格/卡片视图）
L3 认知图谱层（实体抽取 + 双图谱：文档引用图 / 实体关系图）
```

### 核心链路（已闭环）
1. **入库**：IngestEngine 统一驱动（parse→chunk→embed→store→classify→extract + 异步 summarize/tag/preindex），三触发器（HTTP 上传 / 文件夹监控 / cron）都只做「发现→enqueue」
2. **检索**：三召回源（BM25+向量+图谱）→ weighted_rrf_fusion 动态融合 → post_rank → rerank 三级降级链
3. **问答**：引用标注（代码生成 [编号]，LLM 强制引用，杜绝假引用）+ 精确锚点（ref/file_id/chunk_id/chunk_index）
4. **实体**：规则抽取（保底）+ LLM 抽取（按需异步增强），双通道降级；实体为本，文件为壳

### 数据模型核心（区别于旧框架的关键）
- 新增 4 表：`entities` / `entity_chunks` / `entity_files` / `entity_relations`
- 哲学转变：**旧框架「文件为本」→ 新框架「实体为本，文件为壳」**
- 语义边三类：`compatible_process`（材料→工艺，知识表驱动）、`uses_standard`（材料→标准，严格同句共现）、`spec`（连接器→参数，邻接窗口）

## 二、最重要的架构判断（这些决定能长期成立）

1. **插件必须子进程隔离**。旧框架用 importlib 直接 import 进主进程，是「不稳定根源」。新框架：子进程 + JSON-RPC + 超时 kill + 崩溃重启。这是对过往失败的正面回答。

2. **workflow 节点可回退 Agent，但不硬编码**。主链路（解析/分块/向量化/检索）固化成 Stage 是提可靠性的关键；但 LLM 调度仍走 Agent。稳定子任务固化 + 灵活任务留在 Agent。

3. **Feature Flag 优先于删代码**。几乎每个组件都有 `RAG_*` 开关（RERANK/DYNAMIC_RANKING/JIEBA/CHROMA/GRAPH_RECALL/ENTITY_LLM...），可随时回退。这保证了「激进演进但可回滚」。

4. **图谱从「可视化」升级为「检索导航」**。第三召回源 graph_recall 让图谱真正参与检索，而非只是漂亮的展示。这是认知层从「看」到「用」的质变。

5. **引用标注由代码生成，不由 LLM 编**。这是「诚实性」的工程解法——LLM 天生爱编引用，把编号生成权收归代码，LLM 只负责「用编号」。杜绝假引用。

## 三、踩过的坑（按价值排序）

### 坑 1：Windows 上的 HNSW 持久化 bug（最隐蔽）
Chroma 0.6.3 在数据量 >1000 触发 `_persist()` 时，Windows 下写出的 index.bin 损坏，但 pickle 已写入 → 重启报 `Cannot open header file`。
**解法**：metadata 设 `hnsw:sync_threshold=1000000000` 永不 persist，靠 sqlite 重建内存 HNSW。
**教训**：跨平台库在 Windows 上的持久化路径往往有暗雷，要用「绕过持久化」而非「修复持久化」的思维。

### 坑 2：文本字段命名不一致
新框架 chunk 字段是 `content`，旧框架是 `text`。移植组件时所有硬编码字段都会错位。
**教训**：数据模型变更时，字段名是最大迁移成本，应在早期统一并文档化。

### 坑 3：LLM 推理型模型的 reasoning_content 抢占 max_tokens
MiMo/DeepSeek 都是推理型，先花大量 token 在思考上，导致 content 为空/截断。
**解法**：max_tokens ≥4096，system prompt 明示「不要思考过程」，结构化输出优先用非推理的 DeepSeek。
**教训**：调 LLM 前先搞清模型是「推理型」还是「指令型」，参数策略完全不同。

### 坑 4：中文 \b 边界不成立 + 泛化型号正则误伤
`\b[A-Z]{2,5}[- ]?\d{2,4}\b` 在中文表格上疯狂误伤（标准件表抽出 481 个噪声 connector）。
**解法**：型号识别改成「白名单词典 + 明确系列前缀正则」，放弃泛化正则。
**教训**：工业领域实体抽取，词典/白名单 > 正则 > LLM，可靠性优先级反直觉但正确。

### 坑 5：chunk 级共现建边会严重误导
不锈钢被连上 47 个标准（密度表/紧固件表挤同 chunk）。
**解法**：语义边改「领域知识表 + 严格同句共现」双管齐下。
**教训**：知识图谱的边不能靠盲目共现，稀疏且正确的边 > 密集且错误的边。

### 坑 6：Windows 多进程对 RapidOCR 是负收益
ONNX 推理即使设线程数也吃满全核，多进程争用反而更慢（8进程 17s/页 vs 单进程 1.7s/页）。
**解法**：OCR 用单进程；但 GPU（DirectML）场景 4 进程挤满显存反而最快（1.49 页/秒）。
**教训**：CPU 绑定型任务多进程负收益，GPU 会话并行的任务多进程正收益，取决于瓶颈在哪。

### 坑 7：本地模型路径 bug 导致一直降级远程（本轮才发现）
标准 HF 路径只有 config 缺权重，`_get_local_path` 缺权重时直接 return 空，从没搜到旧路径里真实的 1.2GB 权重。
**教训**：路径搜索的「提前 return」是隐性 bug 高发区，缺资源应「继续找下一个」而非「直接放弃」。

### 坑 8：磁盘满导致一切写操作失败
C 盘被 EasyClaw Temp 下历史 deploy-verify 副本（工控软件部署验证）塞满到 0 字节。
**解法**：`cmd /c rmdir /s /q` 清理数十 GB。
**教训**：磁盘余量是「隐形前置条件」，满了会让 SQLite/Chroma 静默失败，排查半天才发现是磁盘问题。

## 四、可复用的工程模式

- **降级链**：rerank（SiliconFlow→DeepSeek→本地 TF-IDF）、embedder（远程→本地）、实体（规则→LLM）。每层都有 `_has_*` 校验 + 失败回退。
- **幂等迁移**：db 加列用 `_migrate_add_column`，`CREATE TABLE IF NOT EXISTS` 不会加列。
- **断点续跑**：OCR 重建每页落地 jsonl checkpoint，重跑自动续。
- **混合向量化**：大 batch（>300 chunk）走远程 API，小 batch 走本地模型，按数据量自动分流。
- **非阻塞后处理**：summarize/tag/preindex 全丢后台线程池，失败仅告警不阻断主链路。
- **声明式 UI**：插件 manifest 声明 → SchemaForm 通用渲染，不为每个插件手写页面。

## 六、给未来自己的一页纸

1. **先看 MEMORY.md 的「关键环境事实」和「重要坑」**，别重复踩。
2. **磁盘、端口、进程**是这台机器的三大环境暗雷（C 盘紧张 / 8099 易被占 / 历史 python 进程残留），排查问题先查这三样。
3. **跨平台库在 Windows 上永远多留个心眼**（HNSW、多进程、路径、编码）。
4. **工业领域：词典 > 正则 > LLM，稀疏正确 > 密集错误**——这是本项目最反直觉但最重要的判断。
5. **服务启动用 `python server.py`**（别用 `uvicorn server:app`，会有模块路径问题加载旧代码）。
