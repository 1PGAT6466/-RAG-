# 伏羲 RAG 系统级专业优化蓝图（扩展版）

> 版本 v2.0（2026-08-26）
> 定位：在用户三点战略（RAG核心优先 / LLM决策+工作流执行 / 完善健壮）基础上，
>       以 RAG 系统架构师视角做专业扩展，突破原始框架的局限。
> 依据：真实代码全链路体检（config/llm/engine/orchestrator/search/rerank/ingest_stages/storage）

---

## 一、战略目标的专业化重构

用户三点战略，映射到业界公认的 RAG 架构范式：

| 用户诉求 | 业界范式 | 专业内涵 |
|---------|---------|---------|
| RAG 核心为主 | Retrieve-then-Read 双塔 | 检索质量是上限，生成是放大器，其余皆服务于此 |
| LLM 决策 + 工作流执行 | **Intent-aware Routing + 规则优先降级** | LLM 只做「语义判断」，确定性环节走规则/缓存/预计算 |
| 完善健壮 | **可观测性 + 幂等 + 降级 + 自愈** | 三级降级链、全链路追踪、数据一致性守护 |

**核心洞察**：这套系统的架构骨架已经是对的（Stage 工作流、Feature Flag、三级降级链、规则优先抽取）。真正的优化空间不在"加什么"，而在**把 LLM 从"每个环节都亲自下场"收敛到"只在语义判断时出手"**，以及**补齐可观测性让系统可被度量、可被验证**。

## 二、LLM 权重再平衡 —— 专业版的「决策/执行分离」

### 范式：LLM 调用点分级

| 级别 | 环节 | LLM 角色 | 当前状态 | 优化方向 |
|------|------|---------|---------|---------|
| L0 规则层 | 分词/实体抽取(规则)/标准分类(规则)/FTS/BM25 | 不参与 | ✅ 已规则化 | 保持 |
| L1 缓存层 | 改写缓存/rerank缓存/语义缓存 | 不参与（命中即走） | ✅ 已有 | 补版本失效 |
| L2 轻LLM | 查询改写/意图分类/复杂度 | Flash，可规则兜底 | 🟡 改写纯LLM | **加规则兜底** |
| L3 重LLM | 生成/摘要/标签/预索引 | Pro/主模型，不可替代 | ✅ 正确 | 合并调用 |
| L4 语义重排 | rerank | SiliconFlow 专用模型 | ✅ 正确 | 保持 |

### 专业扩展点（超出用户原始框架）

1. **查询改写的「规则优先 + LLM 兜底」双层架构**（L2）
   - 先走「同义词表 + 领域词典 + 去停用词 + 关键词抽取」的纯规则改写
   - 规则改写结果满足阈值（如与原 query 重叠度 + 关键词覆盖）就直接用，**不碰 LLM**
   - 只有规则无法改善（口语化、指代、省略）时才调 Flash LLM
   - 收益：约 70% 口语 query 零 LLM 改写，延迟↓、成本↓、稳定性↑

2. **入库后处理的「批量化 + 一次调用多产出」**（L3）
   - summarize + tag 合并成**一次 LLM 调用，输出单个 JSON {summary, tags}**
   - preindex（4 次调用）改为**按文档类型条件触发**：工业手册/标准文档才预生成问答；OA 操作手册、报表等**跳过**
   - 收益：入库 LLM 调用量 -40%+，大文件入库显著提速

3. **意图分类的「规则主 + LLM 微调」闭环**（L2）
   - 当前 classify_intent 是纯规则（9/9 准确），保持
   - 但可以加**低频 LLM 复核**：当规则置信度低（多模式关键词命中冲突）时，才调 Flash 复核
   - 收益：极少数模糊 query 的意图判断更准，其余零成本

## 三、RAG 核心链路的专业强化

### 1. 检索可观测性（P0，所有优化的地基）
当前只有请求级耗时，缺**阶段级 profile**。业界标准是每个检索阶段打点：
- `embed_query` / `fts_search` / `vector_search` / `graph_recall` / `fusion` / `rerank` / `recover_exact`
- 产出结构化 profile：`{query, stages: {embed: 12ms, fts: 8ms, ...}}`
- 收益：延迟优化从"盲调"变"精确打击"，且能让用户看到系统"到底慢在哪"

### 2. 检索质量的新维度（突破"跷跷板"困局）
之前一直在调排序参数，已达天花板（19/20，剩1条是数据问题）。专业上还有几个**排序之外**的杠杆：

- **HyDE（Hypothetical Document Embedding）**（🟠 可选，LLM 增强检索）
  - 用 LLM 生成「假设答案」再向量检索，对语义模糊查询有效
  - 但这是"加 LLM 调用"，与战略2（减负）冲突，**建议仅对"语义模糊 + BM25/图谱双零召回"这种精准场景启用**，作为兜底而非主链路

- **Multi-Query 召回**（🟠 可选）
  - 把一个 query 改写成多个角度再分别召回合并，提升召回率
  - 同样增 LLM 调用，建议默认关，用 Feature Flag 控制

- **Query 路由到专项召回**（P1，规则化收益）
  - 精确型号 → 走词典/FTS 精确匹配（已有 detect_exact_models）
  - 标准号 → 走标准号正则 + standard 实体导航（已有）
  - 材料/工艺 → 走图谱语义边扩展（uses_standard 刚补齐）
  - **把这个路由显式化**，每种 query 走最优召回路径，而非统一走 BM25+向量+图谱

### 3. 生成链路的两点专业补强

- **引用忠实度校验（Citation Fidelity）**（P1）
  - 生成后回验：LLM 给出的 [编号] 是否真出现在 context 里（build_citation_sources 已做正向校验）
  - 反向补强：检测答案里「看似引用但无编号」的模糊陈述，提示可能幻觉
  - 这是 RAG 可信度（Trustworthiness）的核心

- **多轮对话的上下文管理**（P2）
  - 当前 generate_chat 只取 history[-6:]，知识库模式甚至不传多轮历史
  - 专业做法：多轮 query 融合（把代词/省略补全），让 RAG 检索能利用多轮语境

## 四、健壮性/完善度的专业扩展

### 1. 三级降级链的「显式化 + 可观测」
当前降级链是隐式的（try/except 降级）。专业做法是**每个关键环节的降级都打点 + 统计降级率**：
- rerank 降级率、LLM provider 降级率、改写降级率
- 降级率是系统健康的"体温计"，超过阈值说明该环节配置有问题

### 2. 幂等性与可重入性（战略3 核心）
- 入库 Stage 是否幂等（重复跑不多插数据）？—— 已基本是（upsert/INSERT OR IGNORE）
- **任务断点续跑**：入库任务中断后能从失败 Stage 重跑，而非从头再来
- 这是"健壮"的关键：生产环境网络抖动/进程重启不产生脏数据

### 3. 数据一致性守护（周期性）
- 固化 `scripts/health_check.py`：孤儿 chunk、chunk_count 不一致、孤儿 entity/relation、FTS 与 chunks 行数一致、embedding 空值
- 定期跑（可挂 cron），发现漂移即告警
- 这是"避免旧框架腐烂"的治本之策

### 4. LLM 调用审计（成本 + 质量）
- 记录每次 LLM 调用的：环节、provider、输入输出 token 数、耗时、是否降级
- 收益：成本可度量、质量可回溯、能回答"这个查询为什么慢/为什么贵"

## 五、架构层面的前瞻性扩展（战略 3 的深层含义）

### 1. 检索链路的「可插拔 Stage 化」
当前入库是 Stage 化的，但**检索链路是硬编码的**（search 函数里顺序写死）。专业做法是把检索也做成 Stage 管线：
```
召回 Stage（bm25/vector/graph）→ 融合 Stage → 精排 Stage → 后处理 Stage
```
- 好处：新增召回源/重排器无需改 search 主函数，符合"避免堆补丁"的诉求
- 但要克制：**不建议立刻重构**，因为当前硬编码链路清晰且已验证 19/20。这是"演进方向"而非"当下必做"

### 2. 配置的「分层治理」
当前 .env 已有 30+ 开关，符合战略3 的担忧（配置爆炸）。专业做法：
- **运行时配置 vs 部署配置分离**：检索参数（top_k/权重/阈值）应可运行时调；密钥/路径是部署配置
- **配置变更审计**：谁改了哪个开关、何时改的，可追溯
- 目前够用，作为演进方向记录

## 六、明确的技术债清单（诚实项，不回避）

| 技术债 | 影响 | 建议 |
|--------|------|------|
| 检索链路硬编码 | 加召回源要改 search 主函数 | 中长期 Stage 化，近期不动 |

## 七、实施路线图（专业版，分四批）

### 第一批（1天，立竿见影，纯规则零风险）
1. A-检索阶段级耗时埋点（可观测性地基）
2. B-查询改写「规则优先 + LLM 兜底」
3. C-health_check.py 数据一致性脚本固化

### 第二批（1-2天，LLM 减负 + 健壮性）
4. D-入库后处理合并调用（summarize+tag 一次出）+ preindex 按需
5. E-降级率打点 + LLM 调用审计
6. F-语义缓存版本失效

### 第三批（1-2天，检索质量新杠杆）
7. G-Query 路由到专项召回（显式化）
8. H-引用忠实度校验
9. I-多轮 query 融合

### 第四批（演进，按需）
10. J-检索链路 Stage 化（前瞻重构，需充分评估）
11. K-HyDE/Multi-Query（可选，Feature Flag 控制，默认关）

## 八、反"旧框架臃肿"的护栏（贯穿所有批次）

1. 每个新增开关必须有**默认值 + 降级路径 + 文档说明**，否则不加
2. 每次改动先跑 `scripts/retrieval_benchmark.py`（19/20 基线）确认无回归
3. 每批结束跑 `scripts/smoke_test.py` 全链路冒烟
4. 不引入新的 LLM 调用点，除非是"规则/缓存均无能为力"的精准场景
5. 配置只增不减需评审；新增配置必须回答"为什么规则做不到"
