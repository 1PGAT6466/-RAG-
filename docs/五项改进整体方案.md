## 1. 对话能力：三模式智能路由

### 1.1 现状

`src/api.py → api_chat` 流程：

```
检索 search(query) → 无结果 → 直接返回「知识库中未检索到相关内容」
                  → 有结果 → generate(query, results) 强制基于上下文回答
```

`src/chat/engine.py` 的 `SYSTEM_PROMPT` 写死「只基于参考资料回答」，无任何自由对话或联网分支。

### 1.2 目标

用户提的三种能力都要，且**自动切换**：

| 模式 | 触发条件 | 行为 |
|------|----------|------|
| **RAG 模式** | 判断为知识库领域问题 | 检索 → 带引用回答（现逻辑） |
| **闲聊模式** | 判断为寒暄/通用对话（"你好""今天如何"） | 不检索，LLM 直接聊 |
| **联网模式** | 判断需要实时/外部信息（"天气""最新股价""新闻"） | 调搜索 API 取结果 → LLM 综合 |

### 1.3 技术方案

**核心：增加一个轻量「意图路由」步骤**，在检索前判断问题类型。

```
用户问题
   │
   ▼
意图分类（LLM 单轮快判 / 规则关键词兜底）
   │
   ├─ knowledge → 走现有 RAG 检索链路
   ├─ chat      → 直接调 LLM（自由对话，无检索上下文）
   └─ web       → 调搜索 API 取 top-K 结果 → 拼进 prompt → LLM 综合
```

**具体改动点：**

1. **`api_chat` 增加 `mode` 参数**（可选）：`auto`（默认，自动路由）/ `knowledge` / `chat` / `web`。前端聊天界面加一个模式开关（默认 auto）。

2. **意图分类**（`src/chat/router.py` 新增）：
   - 首选：LLM 单轮快判（用非推理模型 deepseek-v4-flash，很快很便宜），输出 `knowledge|chat|web` 三选一
   - 兜底：规则关键词（地名+时间+天气/新闻/股价等 → web；你好/谢谢/聊天 → chat；否则 knowledge）
   - 降级：LLM 分类失败时默认 `knowledge`（安全起见，宁可走 RAG 也不乱联网）

3. **联网搜索**（新增依赖）：
   - 接入一个搜索 API。推荐顺序：**Tavily**（专为 RAG 设计，返回结构化结果）> **Brave Search API**（免费额度 2000 次/月）> Bing Web Search
   - 新增 `src/chat/web_search.py` + config 加 `SEARCH_API_KEY / SEARCH_PROVIDER`
   - 搜索结果拼进 prompt，强制引用来源 URL（可标注但不做 `[编号]` 脚注，只列来源链接）

4. **闲聊模式**：去掉 RAG 上下文，用独立的 `SYSTEM_PROMPT_CHAT`（友好助手人格，不强制引用）。

### 1.4 风险与注意

- **联网需要额外 key**（Tavily/Brave 需注册），需你提供。若无 key，联网模式降级为「提示未配置」。
- 意图分类有误判风险 → 用「规则兜底 + 保守默认 knowledge」降低。
- 三模式切换要保证引用脚注在 RAG 模式仍正常工作，不能破坏现有功能。

## 2. 文档清洗：简体中文归一化

### 2.1 现状

`src/pipeline/parser.py` 已有：过滤 `=DISPIMG(...)`、纯 URL、空 tab。但**没有**语言归一化。繁体、英文、日文、乱码字符仍混入 chunk。

### 2.2 目标

清洗后的 chunk **只保留简体中文**（保留必要的型号/英文术语/数字）。繁体 → 简体。

### 2.3 技术方案

新增 `src/pipeline/language_filter.py`，在 chunk 生成后、入库前调用：

1. **繁转简**：用 `opencc`（OpenCC 库，标准简繁转换）把繁体转简体。
   - `pip install opencc-python-reimplemented`（纯 Python，无 C 依赖，Windows 友好）
   - 转换 `t2s`（繁体→简体）

2. **语言过滤**（按用户选择：繁转简 + 去英文等）：
   - 区块级：一个 chunk 内，若**非中文（英/日/韩/乱码）占比 > 阈值**（如 70%），整块剔除或只保留中文分段
   - 字符级白名单：保留 `简体汉字 + 数字 + ASCII 字母数字（型号用）+ 常见标点 + 单位符号`，剔除日文假名/韩文/特殊符号
   - **保留英文技术术语**：如 `PA66`、`GB/T`、`MLG12`、`UL94` 这类型号/标准号（它们由字母+数字组成，且通常紧邻中文上下文或符合型号正则）

3. **feature flag**：`RAG_LANG_FILTER=1`（默认开），可回退。

**关键实现细节：**
- 用 Unicode 范围判断：中文 `\u4e00-\u9fff`，日文假名 `\u3040-\u30ff`，韩文 `\uac00-\ud7af`
- 英文术语保留：不粗暴删所有 ASCII，而是判断「纯英文长句」才删；短英文字母数字串（疑似型号）保留
- 已入库的旧数据需重新上传才生效（沿用现有机制）

### 2.4 验证

- 用一份含繁体+英文+日文混排的测试文档，清洗后确认：繁体变简体、日文剔除、型号术语保留。

## 3. 知识图谱：实体关系网可视化优化

### 3.1 现状

`frontend/src/views/GraphView.vue`，d3 力导向图：
- 实体图 502 节点 / 4266 边 → `applyGraphTruncation` 截断到 300 节点
- 力导向布局密集凌乱，边重叠严重，不如 Obsidian 的图谱清晰
- 已有双图谱 Tab、类型/关系筛选、图例、点击反链抽屉

### 3.2 目标

让关系网**看得清、可用**，对标 Obsidian 图谱的简洁感。

### 3.3 技术方案（分层优化）

**A. 布局参数调优（低成本，见效快）**
- 力导向参数：增大 `.force('charge')` 斥力、增大 `.force('link').distance` 边距、减小碰撞半径
- 边淡化：`cooccur` 边透明度降到 0.12~0.15（Obsidian 风格，弱化高密度共现边）
- 节点尺寸压缩：度数映射更平缓，避免出现超大节点挤占空间

**B. 交互增强（对标 Obsidian 体验）**
- **hover 高亮邻接**：悬停节点时，高亮它及其直接邻居，其余节点/边透明化
- **点击聚焦**：点击节点后，只显示该节点 + k 跳邻居子图（渐进式展开），避免全图密集
- **拖拽固定 + 缩放**：已有拖拽/缩放，需确认在大图下流畅

**C. 布局算法升级（可选，工作量较大）**
- 若力导向仍不满意，可考虑换 **d3-force 的径向/聚类布局**，或引入 `d3-hierarchy` 的树/径向树表示实体层级
- 长期可评估 `sigma.js` / `Cytoscape.js`（更适合大图，但引新依赖）

### 3.4 风险

- 502 节点力导向在低配机器可能卡 → 默认「点击聚焦子图」而非全量渲染，从根上降低压力
- 截断逻辑保留（300 上限），但配合聚焦子图使用更自然

## 4. 插件体系：调用面板 + 对接现成市场

### 4.1 现状

- 自研插件协议：`src/plugins/`（registry + lifecycle + host），manifest 声明 + JSON-RPC + 子进程隔离
- 现有 2 个示例插件：`example-plugin`（tool 型）、`hook-demo`（workflow 型）
- **前端只有「管理页」（PluginsView）**：可启用/停用/卸载，但**没有调用插件的界面**
- **无插件市场**，获取插件只能手动放 `plugins/` 目录

### 4.2 目标

用户明确要：
1. **插件调用面板**（让 tool 型插件真的能用起来）
2. **对接已有成熟的插件市场**，只做接口，不自建市场

### 4.3 关于「对接现成市场」的关键结论

**可以对接，推荐走 MCP（Model Context Protocol）标准。**

业界已有多个成熟 MCP 插件市场，上面有成千上万个标准化插件（MCP server）：

| 市场 | 特点 |
|------|------|
| **mcp.so** | 社区最大，浏览器可逛，提供 mcp.json 配置 |
| **Smithery** | 提供 registry API，支持命令行安装 |
| **PulseMCP** | 目录 + 评测，可浏览 |
| **AgenticMarket** | 带 API、计费、健康度 |

这些市场的本质是「MCP server 的目录/注册表」。对接方式有两种：

**方案 A：MCP 客户端接入层（推荐）**
- 在伏羲里实现一个 **MCP 客户端**，能连任意 MCP server（stdio / SSE 两种传输）
- 通过市场的 registry API（如 Smithery 的 `smithery.dev` API）或直接按 mcp.json 安装
- 插件页变成「MCP 市场浏览 + 一键安装 + 工具调用」
- 优点：能直接用现成的海量插件，符合「只做接口」的需求
- 缺点：工作量中等（MCP 协议实现 + 市场 API 对接）

**方案 B：保留自研插件 + 桥接 MCP**
- 自研插件机制不动（已有 tool/workflow 两类）
- 新增一个「MCP 桥接插件」类型，让自研插件能包一个 MCP server
- 或反过来：把 MCP server 包装成自研 tool 插件
- 优点：改动最小，兼容现有
- 缺点：两套协议并存，维护成本高

**建议**：短期做**方案 B**（最小改动，先让「调用面板」可用），中期规划**方案 A**（完整 MCP 市场接入）。

### 4.4 技术方案（分阶段）

**阶段 1（本次可做）：插件调用面板**
- 前端 PluginsView 增加「调用」区：选中 tool 型插件 → 展示其 manifest 声明的 tools → 用 SchemaForm 渲染参数表单 → 点击「运行」调 `/api/plugins/{name}/invoke` → 展示结果
- 已有 SchemaForm/SchemaResult 组件（之前为插件声明式 UI 预留的），直接复用
- 后端 `/invoke` 端点已存在，无需大改

**阶段 2：内置一批实用插件**
- 基于现有自研协议，内置几个开箱即用的 tool 插件：
  - 文档翻译插件（调 LLM）
  - 摘要导出插件（导出为 markdown/docx）
  - 格式转换插件（pdf→图片/text）
  - 外部数据查询插件（天气、汇率等，可复用联网搜索能力）
- 放 `plugins/` 目录，启动即加载，用户可直接在调用面板使用

**阶段 3：MCP 市场接入（中期）**
- 实现 MCP client（stdio + SSE）
- 对接 Smithery/mcp.so 的 registry API
- 插件页加「市场上架浏览 + 一键安装」
- 需要评估许可证/安全（第三方插件是外部代码，需隔离沙箱，现有子进程隔离可复用）

### 4.5 安全注意

- 第三方插件/MCP server 是**外部代码**，必须沿用现有子进程隔离 + 超时 + 权限声明
- 安装来源需白名单，避免任意代码执行风险

## 5. 界面质感：设计系统升级

### 5.1 现状

纯 `global.css` + Element Plus 默认风格，朴素、留白多、层级弱。

### 5.2 目标

让界面「有质感」，可对标成熟产品（Notion / Linear / Obsidian 的设计语言）。

### 5.3 技术方案

**A. 配色与主题（最见效）**
- 定义一套完整的设计 token：主色、中性色阶、语义色（成功/警告/危险）、字体层级
- 深色模式支持（可选）
- Element Plus 主题定制（覆盖 `--el-color-primary` 等变量）

**B. 卡片与层级**
- 卡片加细腻阴影、圆角、边框，hover 提升
- 统一 spacing 规范（8px 网格）
- 页面 header 增加面包屑/标题层级，减少「空」感

**C. 细节质感**
- 图标统一（Element Plus Icons 已引入，补齐关键交互图标）
- 过渡动画（列表项 hover、页面切换、弹窗）微动效
- 空状态插画/文案优化（现在空状态只有文字，太空）
- loading / 骨架屏

**D. 布局优化**
- 侧边栏：分组、图标+文字、当前项高亮
- 文档卡片列表：增加缩略图/类型图标、更丰富的元信息展示

### 5.4 风险

- 视觉改动面广，需逐页验收，避免回归
- 建议「先 token + 全局，再逐页细化」，小步提交
