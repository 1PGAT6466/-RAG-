# 伏羲 RAG 运维手册

> 面向值班/维护人员。目标：**不看代码也能把系统看住、出了问题能自己定位**。
> 统一入口：`python scripts/ragctl.py <命令>`（在项目根目录 `E:\更新RAG框架` 执行）

---

## 0. 一分钟上手

```bash
cd E:\更新RAG框架

python scripts/ragctl.py status     # 现在正常吗？
python scripts/ragctl.py doctor     # 全面体检（有问题会给建议）
python scripts/ragctl.py logs 100   # 看最近日志
python scripts/ragctl.py backup     # 手动备份一次
```

**记住三句话**：
- 看状态 → `status`
- 出问题 → `doctor`，还搞不定 → `diag` 打包发人
- 怕丢数据 → `backup`

## 1. 日常三件事

### 1.1 看状态（每天瞄一眼）

```bash
python scripts/ragctl.py status
```

输出解读：

| 行 | 正常 | 异常含义 |
|---|---|---|
| 服务 | `运行中（PID: xxxx）` | `未运行` → `ragctl start` |
| HTTP | `ok  依赖: {'db': 'ok', ...}` | `不可达` → 进程在但没响应，查日志 |
| 数据库 | `4.65 GB` | `文件不存在` → 严重，查 data/ |
| 向量库 | `113.3 MB` | `目录不存在` → 若 RAG_CHROMA=1 则异常 |
| 入库任务 | `failed=0，pending=0` | `pending` 长期堆积 → 入库卡住 |
| 死信队列 | 不出现 | 出现 → `ragctl tasks --retry` |
| 磁盘剩余 | `> 5 GB` | `< 5 GB` 会告警 → 清理 |

### 1.2 看日志

```bash
python scripts/ragctl.py logs 100      # 最后 100 行（服务运行日志）
python scripts/ragctl.py history      # 查看当天运维报告（状态+体检）
```

**日志文件位置**：

| 内容 | 路径 |
|---|---|
| 服务运行日志 | `data/logs/server.log` |
| 服务化 stdout/stderr | `data/logs/service_out.log` / `service_err.log` |
| **运维日志与报告** | `E:\测试项目\自建知识库\伏羲运维手册\日志\<当天日期>\` |

### 运维归档目录（按天）

所有运维日志/报告统一归到：

```
E:\测试项目\自建知识库\伏羲运维手册\日志\
    2026921\                    ← 当天日期（不补零）
        combined_report.md      ← 状态+体检 合并报告（推荐看这个）
        status_report.md        ← 状态快照
        doctor_report.md        ← 体检报告
        ops_daily.md            ← 每日巡检报告
        diag_report.zip         ← 诊断包（脱敏）
```

- **全部为 Markdown 格式**（.md），带标题/表格/状态图标，Obsidian / VS Code / 记事本均可直接阅读
- **每天一个文件夹**，名称为当天日期（如 `2026921` = 2026-09-21）
- **当天多次运维检测，新结果覆盖旧结果**（不会无限堆积）
- 历史日期文件夹不受影响，可自行归档或清理
- 归档目录可用环境变量 `RAG_OPS_ARCHIVE` 覆盖（迁移/多环境）
- 归档盘不可用时自动回退到 `data/ops_archive/`，不影响主功能

**查看当天报告**：`python scripts/ragctl.py history`

**找错误**：日志里搜 ` ERROR ` 或 ` CRITICAL `。

### 1.3 备份（重要！）

```bash
python scripts/ragctl.py backup                # 一致性快照 + 自动校验
python scripts/ragctl.py backup --keep 14      # 保留最近 14 份
```

- 采用 **SQLite VACUUM INTO** 快照 —— 服务运行中也能安全备份，不会出现"半个数据库"
- 备份产物：`data/backup/backup_*.zip`（含 db + chroma + uploads + images + .env）
- **默认保留 7 份**，自动滚动清理
- ⚠️ 备份里含 `.env`（有密钥），别随手外发

## 2. 故障速查表

### 2.1 服务起不来

```bash
python scripts/ragctl.py doctor
python scripts/ragctl.py logs 100
```

| 现象 | 原因 | 处置 |
|---|---|---|
| `端口 8099 无监听` | 没启动 | `ragctl start` |
| `端口被 PID xxx 占用` | 有残留进程 / 起了两个实例 | `ragctl stop` 后再 start |
| 启动超时 | 初始化卡住（模型加载/迁移） | 看 `logs`，首启动加载 BGE 模型需 1-2 分钟属正常 |
| `db_unreadable` | 数据库损坏/被锁 | 停服务 → 用最近备份 `restore.py` 恢复 |
| `端口 8099 被别的程序占` | 冲突 | `netstat -ano \| findstr :8099` 看是谁，换端口改 `.env` 的 `PORT` |

### 2.2 检索变慢 / 结果不对

```bash
python scripts/ragctl.py status       # 看任务是否积压（积压会抢资源）
python scripts/ragctl.py metrics --token <JWT>
```

| 现象 | 排查 |
|---|---|
| 普遍变慢 | 看 `metrics` 的 p95/p99 延迟；是否大量 LLM 降级 |
| 检索为空 | `ragctl doctor` 看 FTS 一致性；必要时 `ragctl fts-reconcile` |
| 结果不准 | 跑 `python scripts/retrieval_benchmark.py` 对比基线 |
| 向量检索无效 | `ragctl doctor` 看向量库；必要时 `ragctl reset-vector` 后重启重建 |

### 2.3 入库卡住 / 失败

```bash
python scripts/ragctl.py tasks              # 看任务列表
python scripts/ragctl.py tasks --retry      # 重置失败/死信任务重跑
```

| 现象 | 处置 |
|---|---|
| 大量 `pending` 不消化 | 服务可能未运行；或入库线程卡死 → 重启 |
| `failed` 任务 | 看 `error` 列；`--retry` 重跑 |
| 死信队列（`!` 标记） | 超过最大重试，需人工看错误原因 |
| OCR 相关失败 | 检查 `RAG_PDF_OCR` 配置 |

### 2.4 磁盘满

```bash
python scripts/ragctl.py status        # 看磁盘剩余
```

清理顺序（**只删这些，别碰 data/rag.db**）：
1. `E:\测试项目\自建知识库\伏羲运维手册\日志\` 下**历史日期文件夹** —— 旧的（非当天）可删
2. `data/backup/` —— 保留最近 2-3 份，旧的删
3. `data/logs/` —— 服务运行日志（server.log），旧的可删
4. `data/uploads/` 里已被 DMS 接管的历史副本（**确认后再删**）

### 2.5 内存高 / 进程被杀

- Chroma + BGE 模型常驻约 2-4 GB，属正常
- `ragctl status` 看是否有大量任务积压（每个入库线程占内存）
- 重启可释放：`ragctl restart`

## 3. 红线（绝对不要做）

| ❌ 禁止 | 原因 |
|---|---|
| 直接删 `data/rag.db` | 全部知识库数据，删了就要靠备份 |
| 手改 `data/` 下的文件 | 数据库/向量库由程序管理，手改会损坏 |
| 同时跑两个服务实例 | SQLite 单写者，会锁死/损坏 |
| 改 `.env` 后不重启 | 配置只在启动时读取，改了不生效还会困惑 |
| `git push` 时把 `.env` 提交 | 密钥泄露（`.gitignore` 已排除，别强加） |
| 在 `.env` 里把 token 写进 git remote URL | 明文存进 `.git/config`（曾踩过，已修） |
| 用 `rmtree` 删 `data/chroma` 后不重启 | 会丢向量，需重启重建 |

## 4. 备份与恢复演练

### 4.1 备份

```bash
python scripts/ragctl.py backup --keep 7
```

### 4.2 恢复（谨慎！会覆盖现有数据）

```bash
python scripts/ragctl.py stop                       # 1. 先停服务
python scripts/restore.py data/backup/backup_xxx.zip # 2. 恢复
python scripts/ragctl.py start                      # 3. 启动
python scripts/ragctl.py doctor                     # 4. 验证
```

`restore.py` 会先创建回滚点，恢复失败可回退。

### 4.3 演练建议

**每季度做一次**：找一个测试环境（或确认有备份后），实际执行一遍恢复流程。没演练过的备份等于没有备份。

## 5. 服务化（让系统自己活着）

### 5.1 Windows：NSSM 注册为系统服务（推荐生产用）

```cmd
:: 需管理员权限的 cmd，且已安装 nssm.exe
scripts\install_service.cmd           :: 安装并启动
scripts\install_service.cmd remove    :: 卸载
nssm status FuxiRAG                   :: 查看状态
```

效果：崩溃自动重拉（延迟 5 秒）、开机自启、日志轮转 10MB。
**关键**：保持 `workers=1`（SQLite 单写者），守护 ≠ 多进程。

### 5.2 开发机：手动/VBS 静默启动

```cmd
scripts\start_service.cmd       # 双击启动（会弹黑窗）
scripts\launch_fuxi.vbs         # 静默启动（无窗口）
```

### 5.3 Linux：systemd

```bash
sudo cp scripts/fuxi-rag.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now fuxi-rag
journalctl -u fuxi-rag -f          # 看日志
```

## 8. ragctl 命令全表

| 命令 | 作用 |
|---|---|
| `start` / `stop` / `restart` | 启停服务 |
| `status` | 服务/任务/数据/备份/磁盘一览 |
| `doctor` | 全链路体检（进程/HTTP/DB/一致性/向量/FTS/配置/磁盘/日志错误） |
| `diag` | 打包诊断包（日志+快照+脱敏配置）成 zip |
| `health` | HTTP 健康（失败自动降级诊断） |
| `tasks [--retry]` | 查看入库任务 / 重置失败任务 |
| `backup [--keep N]` | 一致性备份 + 校验 |
| `logs [N]` | 查看日志尾 |
| `history` | 查看当天运维报告（归档目录）|
| `metrics --token <JWT>` | 拉取运行指标（QPS/延迟/LLM/缓存） |
| `fts-reconcile` | FTS 与 chunks 对账，清理孤儿 |
| `reset-vector` | 删除向量库（重启后重建） |

退出码：`0`=成功，`1`=失败（可被 cron/计划任务消费）。

## 10. 出问题怎么办（决策树）

```
系统不正常
    │
    ├─ 服务在不在？ ──── ragctl status
    │      ↓ 不在
    │   ragctl start → 还是起不来 → ragctl logs 100 → 按 §2.1 处置
    │
    ├─ ragctl doctor
    │      ↓ 有 FAIL
    │   按 doctor 给出的建议处置
    │      ↓ 看懂了但搞不定
    │   ragctl diag → 把 zip 发给维护人员
    │
    └─ 怕数据丢
        ragctl backup
```

**兜底原则**：任何操作前先 `ragctl backup`。有备份，就永远有退路。
