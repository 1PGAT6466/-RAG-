# 组件移植清单 — 从「RAG伏羲(旧)」到「更新RAG框架(新)」

> 目标：把旧框架中**真正稳定、可复用、无隐喻污染**的工程组件，移植到以 RAG 为核心链路的新框架。
> 对应 Excel 对照表：`docs/新旧框架对照表.xlsx`

---

## 0. 移植总原则

1. **取其工程组件，弃其架构神话**：只移植"无状态、零隐喻、纯函数"的模块，不连带 `SymbolBase` / `meridian` / `八卦五行` 那套抽象。
2. **每个组件独立落地**：单独一个 `.py` 文件 + 独立依赖，可单独测试、单独启停。
3. **优先补性能，再补精度，后补质量与安全**（对应下面的 P1→P2→P3）。
4. **优先级定义**：
   - **P1（最高）**：新框架数据量上来后会**直接崩溃/明显失准**的短板 → 立即做。
   - **P2（高）**：显著提升可靠性/准确性/安全性 → 尽快做。
   - **P3（低）**：锦上添花，可选 → 有需要再做。

## 1. P1 组件（最高优先级 — 先做）

### 1.1 ChromaDB 向量存储（替换 SQLite 暴力扫描）
- **旧源码**：`E:\RAG伏羲\src\db\vector_store.py`
- **核心对象**：`VectorStore` 类、`get_vector_store()` 单例
- **外部依赖**：`chromadb`
- **为什么要搬**：新框架用 SQLite BLOB 存向量 + 全表加载 + 逐条 `cosine_similarity`，chunk 到几千条后检索延迟线性增长，这是**最痛的性能隐患**。ChromaDB 自带 HNSW 索引 + `where` 过滤。
- **改动点**：
  - 删除 `EMBEDDER_URL` / 远程 embedder 相关 `embed_texts` 逻辑，向量生成仍走新框架现有的本地 `sentence_transformers`。
  - `chunk_id` 映射：新框架 SQLite 主键 `chunks.id` 作为 ChromaDB 的 `id`，`file_id` 作为 metadata（用于按文件删除）。
  - 去掉 `qdrant` 多后端分支，只保留 `chromadb`。
- **接入步骤**：
  1. `pip install chromadb`
  2. 新增 `data/chromadb/` 目录（加到 `.gitignore`）
  3. 新框架 `src/pipeline/ingest.py` 在 `add_chunks_batch` 后，同步 `vectors.add(...)` 写入 ChromaDB
  4. 新框架 `src/retrieval/search.py` 的 `_vector_search` 改为调 ChromaDB `query`，删除手动全表扫描
  5. `delete_file` 时同步 `vectors.delete_by_file(file_id)`

### 1.2 Rerank 四级降级链（填补精排空白）
- **旧源码**：`E:\RAG伏羲\src\taiyang\rerank.py`
- **核心函数**：`rerank()` → `rerank_with_siliconflow()` → `rerank_with_deepseek()` → `rerank_with_embedder()` → `rerank_local()`
- **外部依赖**：`jieba`、`aiohttp`
- **为什么要搬**：新框架**完全没有 rerank**，检索返回后直接丢给 LLM。加一层 rerank 是检索质量提升最直接、性价比最高的动作。
- **改动点**：
  - 降级链本身**几乎零改动**，只需确认以下密钥已在新框架 `.env`：`SILICONFLOW_API_KEY`、`DEEPSEEK_API_KEY`（均已存在 ✅）。
  - 第四级 `rerank_with_embedder` 依赖 `embedder_server` 独立服务，新框架没有该服务 → **直接跳过该级**，降级链改为「SiliconFlow → DeepSeek → 本地 TF-IDF」三级即可。
  - `document` 字段：旧代码取 `r["text"]`，新框架 chunk 字段是 `content`，需做字段适配。
- **接入步骤**：
  1. 复制 `rerank.py` 到 `src/retrieval/rerank.py`，改字段 `text → content`
  2. 新框架 `src/retrieval/search.py` 在 `_rrf_fusion` 后、返回前插入 `await rerank(query, merged, top_k)`
  3. 校验 `.env` 中 SiliconFlow / DeepSeek 密钥

### 1.3 动态融合权重 + 精确型号匹配（替换硬编码 0.5）
- **旧源码**：`E:\RAG伏羲\src\taiyang\dynamic_alpha.py`、`src\taiyang\fusion.py`（`weighted_fusion_adjust` / `exact_match_boost` / `dynamic_category_weight`）
- **核心函数**：`classify_query()`、`get_dynamic_alpha()`、`weighted_fusion_adjust()`、`exact_match_boost()`
- **外部依赖**：`jieba`、`re`（几乎纯函数）
- **为什么要搬**：新框架 `search.py` 里 `BM25_WEIGHT=0.5 / VECTOR_WEIGHT=0.5` 硬编码，无法针对"精确型号查询 vs 语义查询"区分。旧框架的 `exact_match_boost` 对工业型号（`GP-xx`、`Mini-FAKRA` 等）**极其契合**。
- **改动点**：
  - **型号正则需按你的领域重写**：旧代码正则是通用（`S7-\d+`、`LSW\d+`、`VLAN` 等），你的场景是连接器，建议改成 `Mini-FAKRA|FAKRA|GP-\d+|[A-Z]{2,5}-\d{2,6}` 等。
  - `dynamic_category_weight` 的分类关键词表（机械设计/模具/品质/SOP…）与你工业领域高度吻合，**保留并微调**，可作为分类/加权规则复用。
- **接入步骤**：
  1. 复制纯函数到 `src/retrieval/ranking.py`
  2. `search.py` 的 `_rrf_fusion` 后调用 `weighted_fusion_adjust` + `exact_match_boost`
  3. 调整型号正则 + 分类关键词表

### 1.4 jieba 全文检索（替换手写 bigram）
- **旧源码**：`E:\RAG伏羲\src\taiyang\fusion.py`（jieba 分词逻辑）+ `src/db/memory_store.py` 的 `keyword_search`
- **外部依赖**：`jieba`
- **为什么要搬**：新框架 `db.py` 的 FTS5 用 `unicode61` + 手写 `_to_fts_query` 做中文 2-gram，**中文召回不准**。用 jieba 是标准解法。
- **改动点**：
  - FTS5 需换自定义 tokenizer（jieba 分词后以空格连接）—— 这是**涉及 schema 的改动**，需重建 FTS 索引。
  - 或者更简单：保留 FTS5 表，但把 jieba 分词结果写入 `content` 字段（空格分隔），QUERY 也先 jieba 再查。
- **接入步骤**：
  1. `pip install jieba`
  2. `db.py` 中 `_to_fts_query` 改为 jieba 分词 + 空格 join
  3. 入库时 chunk `content` 额外存一份 jieba 分词版本（`content_fts`）
  4. 已入库数据需重跑一次 `reindex`

## 5. 与新框架「Agent + Workflow」设计的衔接建议

你提出的核心架构是：**以 RAG 为核心链路，Agent 内含 Workflow（稳定子任务固化），Workflow 节点可回退 Agent（处理非结构化输入），核心以 LLM 调度但基础链路工作流化**。

据此，组件落位建议：

| 组件 | 落位 | 类型 |
|---|---|---|
| 文档解析 → 分块 → 向量化 → 入库 | 固定 **Workflow**（无 LLM 判断，全确定性步骤） | 稳定流程，零 LLM |
| BM25 + ChromaDB 向量召回 + RRF 融合 | 固定 **Workflow** | 确定性 |
| 动态权重 + 精确型号匹配 | 固定 **Workflow**（规则引擎） | 确定性 |
| Rerank 降级链 | 固定 **Workflow**（降级是确定性逻辑） | 确定性 + 自愈 |
| 查询扩展（同义词/意图） | Workflow + **Agent 判断点**（意图不明时交由 LLM 改写） | 混合 |
| 事实性校验 / 质量评分 | **Agent 节点**（非结构化判断） | LLM 调度 |
| 知识图谱关系抽取 | **Agent 节点**（非结构化输入 → 结构化关系） | LLM 调度 |

这样设计后：**基础链路全部工作流化（可靠、可测、可回放），只在"意图识别、事实校验、关系抽取"等真正需要非结构化判断的节点才启动 Agent/LLM**，从而降低 LLM 调度、提升稳定性 —— 正好符合你的目标。
