# 专属化工业环境 — 元数据与检索精准度提升方案

> 版本：v1.0（2026-08-27）
> 定位：回答「怎样提升专属化工业环境中数据搜索精准度，是否需要建立对应元数据库」
> 结论先行：**不需要新建独立元数据库；需要补齐「文档类型权威等级」元数据层，并让权威等级进入检索排序链路。**

---

## 一、核心结论

### 1.1 你已经"有"元数据，缺的是"权威等级"这一层

当前系统已具备的元数据资产（SQLite 单一库内）：

| 资产 | 位置 | 现状 |
|------|------|------|
| 文档分类体系 | `files.category` + `src/classification.py` | 9 类工业题材 + 操作手册，成熟 |
| 实体体系 | `entities` / `entity_relations` | connector/material/param/standard + 语义边 |
| 实体↔文件关联 | `entity_files`（含 mention_count） | 天然可作"实体权威出处"信号 |
| 实体↔分块关联 | `entity_chunks` | 反链定位 |
| 标准号分类 | `standard_categories` | 已有，缺文档级归属 |

**结论：问题不在"有没有元数据库"，而在"元数据是否被检索链路消费"。**

当前检索链路（`search.py`）的召回 + 融合 + rerank + 置顶四层里，**没有任何一层使用"文档权威等级"或"文档类型"信号**。这才是导致：

- 「FAKRA连接器规格」被采购流水淹没（采购数据 6438 chunk，含几百条"FAKRA连接器"字样，BM25 词频碾压仅 4 chunk 的产线工艺文档）
- 「镀金层厚度要求」被通用机械手册（1585 chunk）碾压 Foxconn 专项手册（38 chunk）

### 1.2 工业检索精准度的本质

工业知识库检索的精准度提升，本质是**用领域约束收窄语义搜索的歧义空间**。

- 通用 RAG 依赖"语义相似度"，在工业场景会撞上"同词异义 / 同义异源"问题
- 工业场景的权威来源是**层级化**的：工艺规程 > 技术手册 > 选型目录 > 采购流水 > 操作手册
- 元数据正是这些层级约束的载体，让检索从"纯语义猜"变成"受约束的召回 + 排序"

## 二、元数据设计方案

### 2.1 总体原则

1. **不拆库**：在现有 SQLite 上扩展，杜绝跨库 JOIN 和数据一致性问题
2. **元数据必须被消费**：每个新增字段都要在检索链路里有一个明确的消费点，否则不建
3. **规则优先，零 LLM**：权威等级、文档类型全部用规则判定（对齐"LLM 减负"战略）
4. **最小侵入**：优先在"召回层补充 + 置顶层排序"，不破坏已验证的融合/rerank 逻辑

### 2.2 新增元数据层（三张表 / 两个字段）

#### 方案 A：文档权威等级（本期重点，ROI 最高）

在 `files` 表新增两列：

```sql
ALTER TABLE files ADD COLUMN doc_kind TEXT NOT NULL DEFAULT '未分类';
ALTER TABLE files ADD COLUMN authority INTEGER NOT NULL DEFAULT 0;
```

`doc_kind`（文档类型）取值与权威等级 `authority` 映射（规则判定）：

| doc_kind（文档类型） | authority（权威等级） | 判定规则（文件名/分类关键词） |
|---|---|---|
| `工艺规程` | 5 | 分类=工艺规程，或文件名含 工艺/工序/装配/检测/SOP/产线 |
| `技术手册` | 4 | 分类=连接器/材料选型/机械设计，或文件名含 手册/规范/标准 |
| `设计规范` | 4 | 分类=标准件，或文件名含 标准/规范 |
| `选型目录` | 3 | 分类=外购件选型 |
| `操作手册` | 2 | 分类=操作手册 |
| `采购流水` | 1 | 分类=外购件选型 且 文件名含 采购/订单/供应商 或 超大数据（chunk_count 异常大） |
| `品质报告` | 2 | 分类=品质管理 |
| `未分类` | 0 | 兜底 |

> 关键：**`采购流水` 的权威等级最低（1）**——这正是解决当前两条 FAIL 的关键。
> 采购数据记录"买过什么"，但"规格/工艺的权威定义"在技术手册/工艺规程里。

#### 方案 B：实体权威出处（中期，复用已有 entity_files）

新增 `entity_authority` 表（或直接复用 `entity_files` 的 mention_count 推导权威出处）：

```sql
CREATE TABLE IF NOT EXISTS entity_authority (
    entity_id INTEGER NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
    file_id INTEGER NOT NULL REFERENCES files(id) ON DELETE CASCADE,
    is_authoritative INTEGER NOT NULL DEFAULT 0,   -- 是否为该实体的权威出处
    weight REAL NOT NULL DEFAULT 1.0,
    PRIMARY KEY (entity_id, file_id)
);
```

判定规则：某实体在某文件里，若该文件 `doc_kind` 属于"工艺规程/技术手册/设计规范"，且 mention_count 最高，则该文件为该实体的权威出处。

#### 方案 C：结构化参数（长期，参数精确查询质变）

```sql
CREATE TABLE IF NOT EXISTS spec_kv (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    chunk_id INTEGER NOT NULL REFERENCES chunks(id) ON DELETE CASCADE,
    param_name TEXT NOT NULL,      -- 耐压 / 绝缘电阻 / 额定电压 / 材料牌号 ...
    param_value TEXT NOT NULL,
    unit TEXT NOT NULL DEFAULT '',
    confidence REAL NOT NULL DEFAULT 1.0,
    source TEXT NOT NULL DEFAULT 'rule'
);
```

用于把"耐压、绝缘电阻、额定电压"等参数从 chunk 文本里结构化抽出，支持精确参数查询（"耐压 > 500V 的连接器"）。

## 三、检索链路消费点（关键：元数据必须被用起来）

当前检索链路四层，标注每层如何消费权威等级：

```
query
  ├─ ① 意图/领域路由     → 新增：用 domain 收窄（中期）
  ├─ ② 召回层            → 新增：authority 作为召回过滤/加权（本期）
  │    BM25 + 向量 + 图谱 + 文件名
  ├─ ③ 融合 + rerank     → 新增：doc_kind 权重（工艺规程>手册>采购）（本期）
  └─ ④ 精确置顶          → 新增：entity_authority 强信号（中期）
       _recover_exact_match
```

### 3.1 本期（P1）消费点：`_recover_exact_match` 叠加权威等级

现在 `_recover_exact_match` 只按"chunk 内容含不含型号"置顶（priority=2），采购记录里也真实含"FAKRA"，所以被一起置顶。**修复：置顶时叠加 authority**。

```python
def _priority(r):
    authority = r.get("authority", 0)   # 召回时已补上 file.authority
    # 型号精确命中 + 高权威 → 最强
    if exact_models and _token_in(em, text):
        return 3 if authority >= 4 else 2   # 权威文档的型号命中置顶更高
    ...
```

### 3.2 本期（P1）消费点：融合层 doc_kind 权重

在 `weighted_rrf_fusion` / `_rrf_fusion` 后、rerank 前，按 `authority` 做一次轻量加权（或用 `post_rank` 补 authority 字段后在下游使用），让高权威文档在 rerank 之前就占据有利位置。

### 3.3 中期（P2）消费点：召回层 authority 过滤

在 `_dedup_by_file` 后，对 `authority = 0`（未分类）或 `采购流水`（authority=1）的结果降权/延后，避免词频碾压。

## 四、分阶段落地路线

| 阶段 | 内容 | 收益 | 成本 | 依赖 |
|---|---|---|---|---|
| **P1（本期）** | `files` 加 `doc_kind` + `authority` 两列 + 规则判定 + `_recover_exact_match` 消费 | 立即解决 FAKRA/镀金层两条 FAIL | 低 | 无 |
| **P1.5** | 数据回填：为已入库 63 个文件按规则自动标注 authority | 全库权威等级就绪 | 低 | P1 |
| **P2** | 融合层 doc_kind 权重 + 召回层 authority 降权 | 系统性清词频碾压 | 中 | P1.5 |
| **P3** | `entity_authority` 表 + 精确置顶用实体权威出处 | 型号/标准号精准定位权威来源 | 中 | P1.5 |
| **P4** | `spec_kv` 结构化参数抽取 + 参数精确查询 | 参数类查询质变 | 中高 | P3 |
| **P5** | 领域路由（domain）+ 跨领域过滤 | 领域级精准 | 中高 | P1.5 |

## 五、风险与权衡

| 风险 | 说明 | 缓解 |
|---|---|---|
| 权威等级规则误判 | 文件名规则可能把某文档归错类型 | 规则判定后允许管理员手动覆盖（`_recover_exact_match` 前读 DB 即可） |
| 权威权重过强压制长尾 | 若 authority 权重过大，采购流水的"真实检索需求"（查采购记录）被压制 | 权威权重只在"精确命中置顶"层生效，普通语义检索仍公平竞争 |
| 多一套元数据维护成本 | 新增两列一张表，需迁移 + 回填 | 规则自动判定，零人工；回填脚本幂等 |
| 与现有分类体系重叠 | doc_kind 与 category 有语义重叠 | doc_kind 是 category 的"权威度投影"，不是新分类，明确分工 |

---

## 六、需要你确认的落地决策

方案已成型，落地前需要你确认两点：

1. **本期（P1+P1.5）是否立即动手**：`files` 加两列 + 规则判定 + `_recover_exact_match` 消费 + 回填，这是解决两条 FAIL 的最小闭环。
2. **权威等级是否允许管理员手动覆盖**：方案默认"规则判定为主，允许手动覆盖"，如果你希望纯规则（零人工）可再简。

> 备选：如果你希望先只做"文档类型 + 权威等级"并把 P2（融合层消费）一起做完，我可以一次性交付 P1+P1.5+P2 的完整闭环。
