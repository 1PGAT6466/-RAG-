## 二、🔴 P0-1：检索质量修复（最重要）

### 问题证据（实测）
1. `连接器接触电阻` → top1 正确（Foxconn 手册）
2. `连接器接触电阻标准是多少` → top1 漂移到「非标准机械设计手册」（score 5.02，BM25 异常加权）
3. `镀金层厚度要求` → 召回「非标准机械设计手册」而非含镀金层的 Foxconn 手册
4. `怎么防锈` → top1 score 仅 0.01，几乎没命中

### 根因假设（需逐一验证）
- **A. query 改写副作用**：`rewrite_query` 每次调 LLM 改写，可能把「标准是多少」这类后缀改写偏题，导致 BM25 词项权重失衡。
- **B. BM25 权重对长查询失真**：加了查询词后，多词 OR 命中反而稀释了核心词（「接触电阻」）的权重，长文档（机械手册）靠词频优势反超。
- **C. RRF 融合权重静态**：BM25/Vector 固定 0.5/0.5，未按查询类型（型号精确 / 语义模糊 / 参数数值）动态调整。

### 优化措施
1. **改写安全网加严**（已有 token 重叠度阈值 0.4，可提高 + 增加「核心实体保留」校验）：改写结果必须保留原 query 中的实体（连接器型号、材料、标准号），否则弃用改写。
2. **BM25 长查询惩罚**：对查询词数 > N 的 query，降低 BM25 权重占比，提升 Vector 权重（语义更抗词项稀释）。
3. **精确型号/标准号 boost 前置**：若 query 匹配到实体（型号、标准号），直接走精确检索通路，跳过改写。
4. **rerank 必选 + 阈值**：rerank 后用 top-k 重排，若 top1 与 query 实体不匹配则回退 BM25 原始 top1。

**验收标准**：上述 4 条 query 的 top1 全部回到正确文档；新增 20 条工业检索用例，top1 准确率 ≥ 85%。

## 三、🔴 P0-2：检索性能优化

### 问题证据
- 恒定 1.5s：rewrite_query（一次 LLM 调用）+ rerank（一次 SiliconFlow 远程）每次都走网络，无缓存。

### 优化措施
1. **rerank 结果级缓存**（`(query, top_k)` LRU + TTL）：同 query 二次命中直接返回（实测 1.66s→0.76s 已有先例，见 MEMORY）。
2. **rewrite_query 语义缓存复用**：改写结果进 `semantic_cache`（现只缓存生成结果，未缓存改写中间态）。
3. **向量检索预热/常驻**：本地 bge 模型权重缺失问题（见 MEMORY）需补齐，否则每次都降级远程 embedding，拖慢。
4. **检索链路 profile**：加耗时埋点，定位 1.5s 里 rewrite / embed / fts / vector / rerank 各占多少。

**验收标准**：二次命中 < 0.5s；首次命中各阶段耗时可视、可定位瓶颈。

## 四、🟠 P1-1：存储与 DB 优化

### 问题证据（实测）
- 缺 `chunks(file_id, chunk_index)` 联合索引（按文件读 chunks、流式追加都需要）。
- `chunks.content` 无前缀索引（部分前缀匹配慢）。
- 请求级连接用 contextvar + threading.local 双层，存在隐蔽错配风险（见 AGENTS.md Gotcha #2）。

### 优化措施
1. 补 `CREATE INDEX IF NOT EXISTS idx_chunks_file_idx ON chunks(file_id, chunk_index)`。
2. 评估 `tasks` 表持久化但重启丢内存态（`_tasks` dict）——改为启动时从 tasks 表恢复未完成任务。
3. 连接管理：统一为「请求 contextvar 优先、后台线程 threading.local」，并加连接泄漏断言（请求结束强制 reset_conn，已在 server.py 中间件做了 finally close，需复查覆盖所有路径）。

## 五、🟠 P1-2：稳定性与可观测性

### 问题证据
- 日志仅 logging.basicConfig，无结构化、无请求链路 trace。
- 任务状态 in-memory（`_tasks`），重启即丢（AGENTS.md 明确标注）。
- 无健康检查统一口径、无关键指标采集。

### 优化措施
1. **任务持久化恢复**：入库任务落库（tasks 表已有），重启后恢复未完成/中断任务，而非静默丢失。
2. **结构化日志 + 请求 ID**：每请求带 trace_id，检索/对话/入库各阶段耗时埋点，慢查询告警。
3. **健康检查增强**：`/api/health` 增加依赖检查（DB 可达、Chroma 可达、LLM key 有效、磁盘剩余）。
4. **关键指标面板**（可选）：命中率、缓存命中率、LLM 调用次数/耗时、入库速度。

## 七、🟡 P2-2：安全与运维硬化

### 问题证据
- 本次已把服务暴露到内网 `0.0.0.0:8099`（172.25.30.11）。
- `.env` 含真实密钥，明文存储。

### 优化措施
1. **密钥治理**：`.env` 加入 `.gitignore`（确认已忽略）；建议密钥托管到环境变量/密钥管理，避免明文落盘。
2. **防火墙**：8099 端口入站规则（本次提到但未做）。
3. **HTTPS**：内网可先用自签证书或反代（nginx），避免明文传输 token。
4. **备份策略**：rag.db + uploads + chroma 定期备份脚本（当前无自动化）。
5. **登录安全**：确认登录限流（per IP）已生效；admin 默认密码 admin123 建议强制改密。
