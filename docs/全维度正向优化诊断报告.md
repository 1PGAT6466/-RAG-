## 一、LLM 权重再平衡（战略 2 的核心）

> 原则：LLM 只做「决策 + 生成」，检索/抽取/分类/排序这些**规则可判定的环节尽量走工作流（规则/缓存）**。

### A. 查询改写 —— 当前最大 LLM 压力点之一
- **现状**：每次对话 query 都走 `rewrite_query` LLM 调用（虽有 LRU 缓存 + 重叠度安全网 + 精确实体跳过）
- **优化**：
  1. **规则改写兜底**（P0）：先纯规则改写（同义词表 + 去停用词 + 关键词提取），规则命中就不调 LLM。仅规则无法改善时才走 LLM（约 70% 口语 query 可用规则覆盖）
  2. 精确实体跳过已有（`_query_has_exact_entity`），确认其覆盖完整（型号/标准号/材料/参数词）
  3. 缩短 prompt + max_tokens（改写只需关键词，100 token 已足够）

### B. 入库后处理 —— 当前 LLM 压力峰值
- **现状**：每文件入库后异步跑 summarize/tag/preindex 三个 LLM 阶段，preindex 一次调 4 次 LLM
- **优化**：
  1. **合并调用**（P1）：summarize+tag 合并成一次 LLM 调用（输出 JSON {summary, tags}），减少 1 次调用
  2. **preindex 延迟/降频**：preindex 是"预生成问题答案"的缓存，收益边际低，可默认关或按文件类型触发（仅工业手册，OA 操作手册不需要）
  3. 所有后处理已是异步（不阻塞入库），确认超时和大文件保护到位

### C. 保留 「LLM 决策」的正确位置
- ✅ 生成（chat/generate）：LLM 主导，不可替代
- ✅ 意图分类（classify_intent）：规则优先，LLM 可选降级，正确
- ✅ rerank：SiliconFlow 语义分，必要
- ✅ 实体 LLM 抽取：默认关（RAG_ENTITY_LLM=0），正确

## 二、RAG 核心链路的正向优化（战略 1）

### D. 检索链路耗时埋点（P0，可观测性基石）
- **现状**：只有请求级耗时（request_logger 慢查询>3s告警），无**阶段级**耗时
- **优化**：embed / fts / vector / graph / fusion / rerank 各阶段计时，产出 profile 日志
- **收益**：后续所有延迟优化都有据可依，避免盲调

### E. 检索质量天花板已到，剩余是数据侧（已确认）
- 19/20 基线，剩 1 条 `系统参数` 是文档本身内容缺失（需重新上传），非算法可解
- **不重复投入算法**，改为：数据健康检查脚本（检测"文件名含关键词但内容无该词"的病历文档，提示重新入库）

### F. 语义缓存失效策略（P1，健壮性）
- **现状**：semantic_cache 有 LRU + 阈值，但**检索逻辑大改后旧缓存答案会污染**（历史踩过坑）
- **优化**：缓存 key 加「检索链路版本号」，链路大改时 bump 版本自动失效
