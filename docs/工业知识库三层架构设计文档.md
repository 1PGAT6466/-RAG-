# 工业知识库「三层架构」设计文档

> 蓝图版本：v1.0
> 日期：2026-08-13
> 目标：以 RAG 为核心链路，将新框架建设成工业化本地物理服务器文档管理/使用系统，
>       达到并超越 Obsidian / WorkBuddy 在「知识图谱 + 文件管理」上的实用度。

---

## 0. 设计原则

1. **实体为本，文件为壳**：工业文档的真正价值在「实体（型号/材料/标准/工艺）及其关系」，不在「文件与笔记」。数据模型以实体为中心，文件仅作索引入口。
2. **Agent 内含 Workflow**：稳定子任务（解析/分块/向量化/入库/规则召回）固化为确定性 Workflow，零 LLM 调度；仅在「意图识别、实体抽取、关系判定、事实校验」等非结构化节点回退 Agent/LLM。
3. **单机零运维**：SQLite + ChromaDB（嵌入式），不引入 Neo4j / Elasticsearch / Redis 等重组件，贴合「本地物理服务器」。
4. **混合交互**：文件管理同时提供「目录树（目录浏览）+ 字段筛选（数据库式）」，图谱同时提供「实体关系图 + 文档引用图」。

---

## 1. 总体架构

```
┌─────────────────────────────────────────────────────────┐
│ L3 认知层（可视化 · 借鉴 Obsidian 图谱）                    │
│   · 实体关系图（点击→反链面板）                            │
│   · 文档引用图（相似度/显式引用）                          │
├─────────────────────────────────────────────────────────┤
│ L2 管理层（交互 · 借鉴 WorkBuddy 数据库）                  │
│   · 目录树（虚拟目录，由 category 生成）                   │
│   · 字段筛选（分类/型号/材料/日期/状态）                   │
│   · 多维表格卡片视图                                       │
├─────────────────────────────────────────────────────────┤
│ L1 基础层（核心 · RAG 链路）                              │
│   解析 → 分块 → 向量化 → 实体/关系抽取 → 三层入库           │
└─────────────────────────────────────────────────────────┘
```

> 依赖方向：L1 → L2 → L3，上层只增不改，底层 RAG 检索与图谱相互反哺。

## 2. 数据模型（L1 核心）

### 2.1 三层粒度

| 粒度 | 表 | 定位 | 状态 |
|---|---|---|---|
| 文件 File | `files` | 原始文档索引（hash + 元数据） | ✅ 已有 |
| 分块 Chunk | `chunks` | RAG 检索载体 | ✅ 已有 |
| 实体 Entity | `entities`（新增） | 可结构化的知识原子 | 🔨 待建 |
| 关系 Relation | `links`（复用）+ `entity_relations`（新增） | 实体/文档间的边 | 🔨 待建 |

### 2.2 新增表结构

```sql
-- 实体表：从 chunk 中 LLM 抽取的知识原子
CREATE TABLE IF NOT EXISTS entities (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,               -- 规范化名称（如 "Mini-FAKRA"）
    type TEXT NOT NULL DEFAULT 'unknown',  -- connector/material/standard/process/param/...
    aliases TEXT NOT NULL DEFAULT '[]',    -- 别名 JSON 数组
    description TEXT NOT NULL DEFAULT '',
    attributes TEXT NOT NULL DEFAULT '{}', -- 结构化属性（材料→电阻率、标准→编号）
    created_at TEXT NOT NULL DEFAULT (datetime('now','localtime')),
    UNIQUE(name, type)
);

-- 实体-分块关联：哪个 chunk 提到哪个实体（反向链接基础）
CREATE TABLE IF NOT EXISTS entity_chunks (
    entity_id INTEGER NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
    chunk_id INTEGER NOT NULL REFERENCES chunks(id) ON DELETE CASCADE,
    mention_count INTEGER NOT NULL DEFAULT 1,
    PRIMARY KEY (entity_id, chunk_id)
);

-- 实体-文件关联（聚合）
CREATE TABLE IF NOT EXISTS entity_files (
    entity_id INTEGER NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
    file_id INTEGER NOT NULL REFERENCES files(id) ON DELETE CASCADE,
    mention_count INTEGER NOT NULL DEFAULT 1,
    PRIMARY KEY (entity_id, file_id)
);

-- 实体间关系（比 links 更语义化）
CREATE TABLE IF NOT EXISTS entity_relations (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    source_id INTEGER NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
    target_id INTEGER NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
    rel_type TEXT NOT NULL DEFAULT 'cooccur',  -- cooccur/similar/hierarchical/ref
    weight REAL NOT NULL DEFAULT 1.0,
    context TEXT NOT NULL DEFAULT '',
    UNIQUE(source_id, target_id, rel_type)
);
```

> 索引：`entity_chunks(chunk_id)`、`entity_files(file_id)`、`entities(type, name)`。

## 3. 核心链路（Workflow 化）

### 3.1 入库 Workflow（确定性，零 LLM）

```
上传/监听 → 解析(parser) → 清洗(cleaner) → 分块(chunker)
   → 向量化(embedder → ChromaDB) → 入库(files+chunks)
   → [扩展节点] 实体抽取(Agent) → 关系构建(规则) → 图谱入库
```

- **确定性步骤**（无 LLM，失败可重跑、可回放）：解析/清洗/分块/向量化/入库。
- **Agent 节点**（仅在需要时启用）：
  - 实体抽取：LLM 从 chunk 抽实体（型号/材料/标准/工艺参数）→ 结构化入库。
  - 关系判定：实体共现 → 规则建边（cooccur）；相似度 → 文档边。

### 3.2 检索 Workflow（确定性 + 有限 Agent）

```
query → 意图分类(规则) → 查询扩展(规则+可选LLM)
   → 双路召回(BM25 + ChromaDB向量) → 动态α融合 → 精确型号加权
   → Rerank 三级降级 → Top-K
```

- 已在上一轮落地：动态融合 + 型号匹配 + Rerank（见 `src/retrieval/`）。
- 待落地：ChromaDB 替换向量暴力扫描、jieba 替换手写 bigram。

### 3.3 生成链路（LLM 调度 + Workflow 校验）

```
检索结果 → 上下文压缩(规则) → LLM生成 → 事实性校验(LLM) → 质量评分(LLM) → 返回
```

- 事实性校验、质量评分为 Agent 节点（非结构化判断）。
- 上下文压缩优先用零 LLM 的「句子级抽取」（`extract_relevant_sentences`）。

## 4. L2 管理层设计（混合模式）

### 4.1 布局

```
┌──────────┬──────────────────────────────────────────┐
│ 目录树    │  筛选栏：分类▾ 型号▾ 材料▾ 日期▾ 状态▾     │
│ 📁全部    │ ┌────────┐ ┌────────┐ ┌────────┐         │
│ 📁设计手册 │ │文档卡片 │ │文档卡片 │ │文档卡片 │         │
│ 📁连接器   │ │型号/材料│ │型号/材料│ │型号/材料│         │
│ 📁工艺规程 │ └────────┘ └────────┘ └────────┘         │
│ 📁标准件   │  （支持排序/分组/切换列表↔卡片）          │
└──────────┴──────────────────────────────────────────┘
```

### 4.2 目录树（虚拟目录）

- 目录由 `files.category` 字段**动态生成**，非真实文件夹。
- 一个文件可属于多分类（`tags` 扩展为多分类），避免 Obsidian 单目录的僵化。
- 支持自定义分类、拖拽归类。

### 4.3 字段

新增可筛选字段（落到 `files.metadata` JSON 或独立列）：

| 字段 | 来源 | 示例 |
|---|---|---|
| category | 现有 | 设计手册/连接器/工艺规程 |
| model（型号） | 实体抽取 | Mini-FAKRA / FAKRA |
| material（材料） | 实体抽取 | LCP / PA66 / 铜合金 |
| status（解析状态） | 入库状态 | 已解析/待解析/失败 |
| created_at / updated_at | 现有 | — |

### 4.4 持续新增（解决「两者都有」）

- **手动**：拖拽上传（现有）+ 支持文件夹上传（已有）。
- **自动**：`watchdog` 监听本地目录（如 `F:\公司知识平台\传入数据\原始文件\`），新文件自动入队处理。
- **版本/去重**：按 `file_hash` 去重，同 hash 新上传触发增量更新。

## 5. L3 认知层设计（双图谱）

### 5.1 实体关系图（工业核心价值）

- **节点** = 实体，按 `type` 着色（连接器=蓝 / 材料=绿 / 标准=橙 / 工艺=紫 …）。
- **边** = `entity_relations`（cooccur/similar/hierarchical/ref），粗细 = weight。
- **交互**：点击实体 → 右侧「反链面板」列出所有提到它的 chunk/文件（走 `entity_chunks` / `entity_files` 反查）。

### 5.2 文档引用图（Obsidian 双链的工业版）

- **节点** = 文档，按分类着色。
- **边** = 文档相似度（向量余弦，ChromaDB）/ 显式引用（手工或解析出的引用）。
- **交互**：点击文档 → 高亮相似文档，跳转详情。

### 5.3 前端基础（已具备）

现有 `GraphView.vue` 已用 D3 力导向图，具备缩放/拖拽/图例/点击跳转，只需**补充数据源 + 双图谱 Tab 切换**即可。

## 8. 与「Agent + Workflow」的对应关系

| 组件 | 类型 | 说明 |
|---|---|---|
| 解析/分块/向量化/入库 | **Workflow** | 确定性，零 LLM |
| BM25+向量召回 + 融合 + 型号加权 + Rerank | **Workflow** | 确定性 |
| 意图分类 / 查询扩展 | Workflow + 规则（必要时 LLM 改写） | 混合 |
| 实体抽取 | **Agent 节点** | 非结构化输入 → 结构化输出 |
| 关系判定 | Workflow（规则共现）+ Agent（语义关系） | 混合 |
| 事实性校验 / 质量评分 | **Agent 节点** | 非结构化判断 |

> 目标达成方式：基础链路全部工作流化（可靠/可测/可回放），只在真正需要非结构化判断的节点启动 LLM —— 降低 LLM 调度，提升稳定性。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 实体抽取成本（大量 chunk × LLM） | 批量 + 缓存 + 仅对新入库 chunk 抽取；抽取失败降级为规则抽取（型号正则/词典） |
| 图谱随数据增长变密集、难读 | 分 type 过滤、按 weight 阈值剪枝、局部展开而非全图 |
| XLSX/PDF 表格语义丢失 | 阶段 2 引入表格结构化解析（旧框架 table_parser 可借鉴） |
| 本地模型 CPU 向量化慢 | 大文件后台队列处理（已有 task_queue），不阻塞 API |
