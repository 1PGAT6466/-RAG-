# 插件系统设计文档（第 0 层 · 插件运行时）

> 版本：v1.0
> 日期：2026-08-13
> 定位：三层架构的「第 0 层」，为 L1/L2/L3 提供可插拔扩展能力。
> 目标：让后续接入的插件能**稳定使用** —— 稳定 = 隔离 + 契约 + 生命周期。

---

## 0. 设计原语

插件系统稳定性不取决于"能不能写插件"，而取决于三个支柱：

| 支柱 | 解决的问题 | 本设计落地手段 |
|---|---|---|
| **① 隔离（Sandbox）** | 插件崩溃/死循环/恶意代码不能拖垮主进程 | 子进程隔离 + 超时 + 资源限制 |
| **② 契约（Contract）** | 插件与主框架接口约定 + 版本兼容 | manifest 声明 + api_version 严格校验 |
| **③ 生命周期（Lifecycle）** | 安装/加载/停用/卸载有明确状态机 | 显式状态机，禁用即回退，禁止半加载 |

> 与旧框架（`RAG伏羲`）的根本区别：旧框架插件用 `importlib` 直接 import 进主进程、注册主进程的 `APIRouter` —— 插件一旦异常/死循环/泄露，直接拖垮整个 FastAPI 服务。**本设计改为子进程隔离，插件状态与主进程解耦。**

---

## 1. 插件分类（呼应 Agent + Workflow）

按稳定性从高到低，支持两类（用户已确认"两者都要"）：

### A. Workflow / Skill 型插件（推荐，最稳）
- 本质：**固定流程**，纳入确定性的入库/检索链路。
- 形态：`SKILL.md`（说明 + 何时触发）+ `scripts/`（确定性脚本）+ `references/`（参考资料）。
- 运行方式：被主框架的 Workflow 编排器在**确定节点排队调用**，输入输出结构化，失败可重跑/回放。
- 类比：WorkBuddy 的 Skill；OpenClaw 的 skill。

### B. Tool 型插件（给 Agent 调用的工具）
- 本质：**能力单元**，供 LLM/Agent 在判断节点调用（如查数据库、算公式、导文件）。
- 形态：manifest 声明 `tools`（名称/参数 schema/描述），Agent 通过 function-call 协议调用。
- 类比：MCP tool；OpenAI function-calling。

> 核心原则：**优先让插件以「Workflow 固定流程」接入，而非「任意脚本」接入。** 固定流程是确定性的，出问题可定位、可回放、可降级 —— 这是"稳定"的根本。

## 2. 插件目录与 manifest 契约

### 2.1 目录结构

```
plugins/
└── <plugin-name>/
    ├── manifest.json      # 契约：身份 + 版本 + 入口 + 类型
    ├── SKILL.md           # (Workflow型) 说明 + 触发条件
    ├── main.py            # (Tool型) 工具实现入口
    ├── scripts/           # (Workflow型) 确定性脚本
    └── references/        # (Workflow型) 参考资料
```

### 2.2 manifest.json 契约

```jsonc
{
  "name": "data-exporter",           // 唯一标识（字母/数字/连字符）
  "version": "1.0.0",                // 语义化版本
  "api_version": "1",                // 主框架插件 API 版本（严格匹配，不匹配拒绝加载）
  "kind": "tool" | "workflow",       // 插件类型
  "display_name": "数据导出器",
  "description": "...",
  "author": "...",

  "entry": "main.py",                // Tool型入口 / Workflow型主脚本

  // Tool型：声明可被 Agent 调用的工具
  "tools": [
    { "name": "export_csv", "description": "导出为CSV",
      "parameters_schema": { "type": "object", "properties": { "query": {"type":"string"} } } }
  ],

  // Workflow型：声明可挂载的确定性节点
  "workflow_hooks": ["ingest.after", "search.before"],

  "requires": ["openpyxl>=3.1"],     // 依赖约束（可选项，影响安装）
  "config_schema": { "max_rows": {"type": "number", "default": 10000} }
}
```

> `api_version` 是稳定性的关键：主框架升级时若插件声明旧版本，直接**拒绝加载并明确报错**，而不是"勉强加载导致崩溃"。

## 3. 运行时架构

```
┌──────────────────────────────────────────────┐
│ 主框架（FastAPI 进程）                        │
│                                              │
│  PluginManager（唯一线程安全入口）            │
│    ├─ Registry (SQLite: 插件状态/版本)        │
│    ├─ Loader (校验 manifest + api_version)    │
│    ├─ Lifecycle (状态机)                      │
│    └─ Host  (子进程管理 / 超时 / 资源限制)     │
│                                              │
└──────────────┬───────────────────────────────┘
               │ 通过 stdin/stdout(JSON-RPC) 或 unix socket 通信
               ▼
┌──────────────────────────────────────────────┐
│ 插件子进程（每个插件独立进程）                 │
│   · 隔离的内存/文件描述符                      │
│   · 超时 kill（默认 30s，可配）               │
│   · 资源限制（CPU/内存上限，防止死循环/泄露）  │
│   · 崩溃不影响主进程，Host 检测后自动重启/标记 │
└──────────────────────────────────────────────┘
```

### 3.1 隔离机制（关键）

| 措施 | 说明 |
|---|---|
| **子进程隔离** | 插件跑在 `subprocess` 子进程，不共享主进程内存，崩溃/死循环不拖垮主服务 |
| **超时 kill** | 每个插件调用设超时（默认 30s），超时强制终止 |
| **资源限制** | 限制 CPU 时间 / 内存（Windows 用 Job Object 或简单监控）|
| **标准 I/O 协议** | stdin/stdout 走 JSON-RPC（结构化），不 import 插件代码进主进程 |

### 3.2 生命周期状态机

```
installed ──enable──▶ enabled ──disable──▶ disabled
   │                    │                     │
   └────uninstall───────┴───────(reload)───────┘
```

- **严格单向**：只允许 `installed → enabled → disabled → uninstalled` 显式流转。
- **禁用即回退**：disable 后立即从所有 Workflow hook / Agent tool 列表移除，不留半加载状态。
- **禁止运行时热替换**：升级 = disable → 卸载旧版 → 装新版 → enable，全程有明确中间态。

### 3.3 Tool 型插件调用协议（Agent 调用）

```
Agent 决策节点判断需要工具 → 查询 Registry 注册的 tools
  → 主框架 Host 转发 JSON-RPC 到插件子进程
  → 插件执行 → 返回结构化结果
  → 超时/异常/崩溃 → 主框架捕获，返回 "tool_error" 给 Agent（不崩溃）
```

## 4. 最小可行内核（阶段交付）

只做 3 个组件，不做旧框架的臃肿 plugin_manager：

| 组件 | 职责 | 文件 |
|---|---|---|
| **Registry** | SQLite 记录插件状态/版本/manifest | `src/plugins/registry.py` |
| **Lifecycle** | 状态机 + install/uninstall/enable/disable | `src/plugins/lifecycle.py` |
| **Host** | 子进程隔离 + 超时 + JSON-RPC 通信 | `src/plugins/host.py` |

**不做的**（避免旧框架过度设计）：
- ❌ 不复制旧框架的 plugin_analyzer / auto_integrator / plugin_sandbox 等 10+ 个文件
- ❌ 不做插件热替换
- ❌ 不做插件市场/在线安装
- 先做「本地目录扫描 + manifest 加载 + 两类插件运行」的最小闭环

## 5. 前端插件页面（前后端闭环）

> 关键原则：**前端不能为每个插件手写一份 Vue 页面**（插件一多前端就不可维护）。正确姿势是「manifest 声明驱动 UI 自动渲染」——插件声明自己的参数 schema 与界面类型，前端用一套**通用渲染器**自动生成表单/面板。这样插件接入是**声明式、零前端手工代码**，才能稳定扩展。

### 5.1 前端插件清单页（Plugin 中心）

侧边栏新增「插件」入口（紧邻「知识图谱」）：

```
MainLayout 侧边栏
├─ 对话
├─ 文档管理
├─ 知识图谱
├─ 插件          ← 新增，路由 /plugins
└─ 退出
```

插件中心页（`PluginsView.vue`）三块：
1. **插件卡片列表**：名称/图标/版本/类型/状态（enabled/disabled）/描述，含「启用/停用/卸载」操作。
2. **插件详情面板**：点击卡片展开 —— 配置项（由 `config_schema` 驱动渲染）+ 运行日志 + 版本信息。
3. **工具调用页**：Tool 型插件的工具列表，可手动触发一次调用看结果（调试用）。

### 5.2 声明式 UI 渲染（核心机制）

插件在 manifest 里声明两类 UI 描述，前端通用渲染器据此自动生成，无需为插件写页面：

**A. Tool 型 —— 参数表单自动生成**

```jsonc
"tools": [{
  "name": "export_csv",
  "description": "导出为 CSV",
  "parameters_schema": {              // 直接复用 JSON Schema
    "type": "object",
    "properties": {
      "format":   { "type": "string", "enum": ["csv","xlsx","json"], "default": "csv" },
      "max_rows": { "type": "integer", "default": 10000 },
      "query":    { "type": "string", "ui": "textarea" }
    },
    "required": ["query"],
    "ui:order": ["query", "format", "max_rows"]
  }
}]
```

→ 前端用 `SchemaForm` 通用组件，把 JSON Schema 渲染成 Element Plus 表单（string→input、enum→select、integer→input-number、`ui:textarea`→textarea）。

**B. Workflow 型 —— 面板/流程可视化**

```jsonc
"workflow": {
  "hook": "ingest.after",
  "ui": "panel",                       // panel / table / status
  "config_schema": { "...": "..." }   // 配置项，同上 SchemaForm 渲染
}
```

→ 前端用 `PluginPanel` 通用组件渲染配置面板 + 最近运行状态/日志。

### 5.3 前端调用链路

```
用户操作插件页表单 → POST /api/plugins/{name}/invoke  (带参数)
   → 主框架 Host 转发到插件子进程
   → 返回结构化结果
   → 前端 SchemaResult 通用组件按返回 schema 渲染结果
```

- 长任务（如导出）走**任务队列 + 轮询进度**（复用现有 upload 的 task_id/进度机制）。
- 崩溃/超时 → 前端统一提示「插件调用失败」，不影响其它插件。

### 5.4 前端需新增的文件

| 文件 | 职责 |
|---|---|
| `views/PluginsView.vue` | 插件中心（列表/详情/工具调用）|
| `components/SchemaForm.vue` | 通用 JSON Schema 表单渲染器 |
| `components/SchemaResult.vue` | 通用结果渲染器 |
| `components/PluginPanel.vue` | Workflow 插件配置/日志面板 |
| `stores/plugins.js` | 插件状态 Pinia store |
| `api/plugins.js` | 插件 API 封装（list/invoke/enable/disable）|
| `router.js` 新增 `/plugins` | 路由与侧边栏入口 |

### 5.5 后端配套 API

| 端点 | 用途 |
|---|---|
| `GET /api/plugins` | 插件列表（含 manifest/状态/类型）|
| `POST /api/plugins/{name}/invoke` | 手动调用插件（Tool/Workflow）|
| `POST /api/plugins/{name}/enable` / `disable` | 启停（回退机制）|
| `POST /api/plugins/{name}/uninstall` | 卸载 |
| `GET /api/plugins/{name}/status` | 运行状态/日志/进度 |

## 6. 与三层架构的衔接

| 插件类型 | 后端挂载点 | 前端呈现 | 影响层 |
|---|---|---|---|
| Workflow 插件 | `ingest.after` / `search.before` / `chat.before` 等确定性节点 | 插件中心配置面板 + 运行日志 | L1 基础层 |
| Tool 插件 | Agent 的 function-call 工具列表 | 插件中心工具调用调试页 | 生成链路（LLM 调度节点）|

> 这样插件就自然落入你「Agent + Workflow」的分层：Workflow 插件补确定性链路，Tool 插件补 Agent 判断能力，二者都不破坏主链路稳定性；前端则用「声明式 SchemaForm 渲染」实现零手工页面的稳定扩展。

## 7. 稳定性验收标准（定义"稳定"）

插件系统上线前需满足：

1. 一个插件**无限循环 / 内存泄露 / 抛异常**，主服务响应时间不受影响（隔离生效）。
2. 插件声明 `api_version` 不匹配，**拒绝加载并给出明确报错**，而非崩溃。
3. `disable` 插件后，其 hook/tool **立即从所有调用路径消失**，无残留状态。
4. 插件升级失败，能**回退到上一可用版本**。
5. 所有插件交互有**超时**，单点卡死不超过 30s。
6. **前端可声明式渲染**：新增插件**无需手写一行前端代码**，仅靠 manifest 即自动生成表单/面板/工具调用页。
7. 插件缺失/损坏时，前端插件页**优雅降级**（显示"不可用"而非白屏/报错堆栈）。

## 8. 实施顺序

| 步骤 | 内容 |
|---|---|
| 1 | 定义 manifest 契约 + api_version 规范（本文档 §2）|
| 2 | Registry + Lifecycle（本地目录扫描 + 状态机）|
| 3 | Host 子进程隔离 + JSON-RPC + 超时 |
| 4 | 打通 Workflow hook（挂到 ingest/search 节点）|
| 5 | 打通 Tool 注册（挂到 Agent function-call）|
| 6 | 前端插件中心页 + SchemaForm 声明式渲染器 |
| 7 | 一个 example 插件跑通端到端（含崩溃隔离 + 前端渲染验证）|

> 建议插件机制与「阶段 1（ChromaDB+jieba）」并行或紧随其后，因为它对 L1 之后所有环节都是基础设施。
