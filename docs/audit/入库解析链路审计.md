# 伏羲 RAG 入库/解析链路 缺陷审计报告

> 审计范围：`src/pipeline/*`（parser / chunker / embedder / ingest_stages / engine / ocr_engine / language_filter / image_extractor）
> 审计方式：逐行精读源码 + 结合 config 默认值交叉验证
> 审计结论：**不做任何代码修改，仅输出缺陷清单与模块式借鉴建议**
> 日期：2026-09-08

---

## 一、总览：格式转化成功率低的根因归纳

入库链路的核心风险集中在 **解析层（parser）**，其次是 **分块层破坏表格/语义结构** 与 **向量化的远端硬编码模型不一致**。格式转化失败的高频根因可归纳为四类：

1. **依赖缺失/环境依赖**：`.ppt`(OLE)、`.xls`(旧版)、扫描件 OCR、`.doc`(旧版) 都依赖外部二进制（LibreOffice / rapidocr / word 旧格式库），环境未装即静默降级为「返回提示串」或「只索引文件名」，表面"解析成功"实则**内容为空或残缺**。
2. **格式区分不彻底**：`.xls` 与 `.xlsx` 共用 `_parse_xlsx`，但 `openpyxl` 根本不支持 `.xls`（OLE），会直接抛异常；`.md`/`.csv`/`.log` 全部走 `_parse_txt`，`.csv` 丢失行列结构而沦为纯文本。
3. **表格/图片/公式信息丢失**：所有解析器（除 XLSX 的 tab 拼接外）均只抽文本，PPT/PDF/DOCX 的表格、图片、公式、页眉页脚、文本框顺序信息全部丢弃，导致结构化检索（"第 3 列的电压值是多少"）无从谈起。
4. **错误吞噬过度**：解析层广泛 `except ... pass/warning`，失败被静默吞掉，统计系统无从感知真实失败率，且会把「空内容」当成功入库。

## 二、逐文件缺陷清单

### 2.1 `parser.py`（文档解析）

#### 【高】`_parse_txt` 硬编码 `utf-8` + `errors="replace"`，GBK/GB2312 中文文件乱码不可逆（L379-381）
- **根因**：`with open(filepath, "r", encoding="utf-8", errors="replace")`。许多工业文档/TXT/CSV/LOG 是 GBK 或 GB18030 编码（尤其从 Windows Excel/记事本导出）。errors="replace" 会把无法解码的字节替换成 `�`，**且一旦替换即数据永久丢失**，后续 OCR/检测/分块全部基于乱码文本。
- **影响**：GBK 编码的 `参数表.txt`、`料号清单.csv`、`工艺日志.log` 入库后中文全崩，检索命中率趋近 0，且无法挽回（原始字节未保留）。
- **借鉴建议**：对标 **LangChain `TextLoader` / llama_index `SimpleDirectoryReader`** 的 `autodetect_encoding=True`（chardet/charset-normalizer 探测，回退 utf-8→gbk→gb18030→latin-1）。或 **Unstructured** 的 `encoding` 自适应 + 保留原始 bytes。应改为：先 `errors="replace"` 读 bytes，再用 charset-normalizer 二次探测，或至少增加 GBK/GB18030 多编码回退。

#### 【高】`.csv` 走 `_parse_txt`，行列/表头结构完全丢失（L37 / L39）
- **根因**：`parse_file` 中 `.csv` 指向 `_parse_txt`，仅当纯文本整读，无 `csv` 模块行列解析，无表头/字段语义。
- **影响**：CSV 是结构化数据（BOM/料表/测试数据），纯文本拼接后列之间无分隔语义，分块器按空行/段落切分会把一整张表切成语义断裂的碎片；表头与数据分离，检索「某列字段值」几乎不可能。
- **借鉴建议**：对标 **Unstructured `CSVPartitioner` / LlamaIndex `CSVReader`**：按行列解析，保留列名→值映射，生成带列语义的文本或直接走 Table 结构（见 2.4）。

#### 【高】`.xls`（旧版 OLE）与 `.xlsx` 共用 `_parse_xlsx`，但 `openpyxl` 不支持 `.xls`（L37 / L239）
- **根因**：`parse_file` 中 `".xls": _parse_xlsx`；而 `_parse_xlsx` 首行 `openpyxl.load_workbook(filepath)`。openpyxl 只支持 xlsx/xlsm（OOXML），打开 `.xls`(BIFF/OLE) 会抛 `InvalidFileException`。且 `_stage_parse` 无 try，异常会一路抛到 engine，该文件直接 **failed**。
- **影响**：所有旧版 Excel 文件上传即失败，这是"格式转化成功率低"的**直接命中的常见失败点**。
- **借鉴建议**：对标 **pandas `read_excel`（engine 显式指定）**：用 `xlrd`（.xls）或 LibreOffice 转 xlsx 兜底；或 **Unstructured `XLSXPartitioner`** 不支持旧版时显式报错而非误导。应在 dispatcher 层面分支：`.xls` → xlrd / LibreOffice 转换路径，`.xlsx` → openpyxl。

#### 【高】`_parse_docx` 只读 `doc.paragraphs`，表格/页眉页脚/文本框全部丢失（L237-239）
- **根因**：`"\n\n".join(p.text for p in doc.paragraphs)` 仅遍历 body 段落，**跳过 `doc.tables`、header/footer、文本框、以及段落内的图片**。工业文档（规格书/测试报告）大量关键数据在表格里（参数表、公差表、检测项）。
- **影响**：DOCX 表格内容完全不入库，检索"XX 参数"命中不到表格单元格数据；这是工业知识库最致命的丢数据场景之一。
- **借鉴建议**：对标 **python-docx 官方 `Document` 完整遍历（paragraphs + tables 递归）/ Unstructured `DocxPartitioner`**：按文档顺序遍历 body 元素，表格转成 markdown 表格文本（`|---|`），保留 cell 文本与行列结构。

#### 【高】`_parse_pptx` 只读 `shape.text_frame`，表格/图片/备注/smartArt 全丢（L179-189）
- **根因**：只遍历 `shape.has_text_frame` 的段落；**`shape.has_table`、图片、备注页（notes slide）、SmartArt、组合 shape 内嵌文本框** 全部未处理。PPT 的技术要点经常在表格和备注里。
- **影响**：PPTX 表格、演说备注中的关键参数/结论不进库。
- **借鉴建议**：对标 **python-pptx 递归遍历 + Unstructured `PptxPartitioner`**：处理 `shape.has_table`（列名+单元格）、`slide.notes_slide`、递归 `GraphicFrame`/`GroupShape`。

#### 【高】`_parse_ppt`（旧版 OLE）：LibreOffice 缺失时静默降级到关键词过滤/返回提示串，内容残缺（L195-239）
- **根因**：LibreOffice 未装 → 走 OLE 二进制提取 + `tech_kw` 关键词白名单过滤，**只保留含 60 来个技术词汇的行**，其余内容全部丢弃；若过滤后 `<200` 字，直接 `return "[文件...] 旧版 .ppt 格式不支持..."` 这条提示串被当作"解析结果"入库。
- **影响**：旧版 PPT 要么大量丢内容，要么把"不支持"提示串当正文入库污染向量库；`_stage_parse` 只校验 `len(text.strip()) < 50` 才报错，此提示串 >50 字，会**成功入库一条垃圾 chunk**。
- **借鉴建议**：对标 **LibreOffice UNO headless / Unstructured**：依赖缺失时应**显式标记文件为"待转换/不支持"而非塞提示串**；且提示串"不支持"不应作为可检索正文。关键词白名单方案应改为结构化的 OLE 文本抽取（`olefile` + 记录流解析）或直接要求转换为 PDF。

#### 【中】`_parse_pdf` 整本缓冲进 `io.StringIO`（L66-79），大 PDF 全量驻内存，且与流式两套逻辑并存
- **根因**：非流式路径 `fit._parse_pdf` 把整本 `get_text()` 全拼进内存 StringIO；`_extract_pdf_text` 也全量列表拼接。几百上千页 PDF 文本全量驻内存。虽然 engine 对大 PDF 走了 `_run_streaming_pdf`，但 `.pdf` 判定 `_use_streaming` 依赖 `RAG_STREAM_MIN_PAGES`(默认20) 且只有 pdf 走流式，**其它格式（大 DOCX/PPT）仍整本驻内存**。
- **影响**：大文本文件内存峰值高；多任务并发时 OOM 风险（engine 每任务一个 daemon 线程，无并发上限，见 2.5）。
- **借鉴建议**：对标 **PyMuPDF 逐页迭代 + 生成器式解析（LlamaIndex PagedFileNodeParser）**，统一走流式/分页产出，避免全量 StringIO。

#### 【中】`_parse_pdf_ocr` 的 `get_pixmap(dpi=150)` 每页整页渲染，无 adaptive DPI / 无 alpha 通道判断（L158-178）
- **根因**：固定 dpi=150，每页全图 OCR，未根据页面内容复杂度降采样；`img.shape[2]==4` 只处理了 RGBA，但 `.n` 可能为 1（灰度）时 `numpy` reshape 会引发行数不匹配（`pix.n==1` 时 `reshape(h,w,1)` 仍 OK，但 `.shape[2]` 访问在灰度 `pix.n>=3` 假设下可能越界）。此外 CPU 无 GPU 时 OCR 极慢，无批处理/预缩放。
- **影响**：OCR 大 PDF 耗时线性爆炸，灰度/特殊色彩空间页可能抛异常被 `except` 吞掉导致该页文本丢失。
- **借鉴建议**：对标 **PaddleOCR 文档分析（layout + 文本块检测）**，先 layout 分区再 OCR 只识别文本块；或 Unstructured 的 `hi_res` 策略按版面分块 OCR，避免整页全图识别。

#### 【低】`_text_garbled_check` 用 jieba 分词做「多字词命中率」判定，英文/编号密集页会被误判或漏判（L107-144）
- **根因**：判断依据是「含 ≥2 字词的占比」，对技术文档中大量**型号/编号/英文术语页**（如含大量 `GB/T 23456`、`M8×1.25` 的页）多字中文词占比天然偏低，可能误判为乱码→触发整本 OCR（浪费 GPU/时间）；反之纯乱码但恰好混入少量成词页可能漏判。
- **影响**：误判导致正常 PDF 被整本重新 OCR（慢且可能引入 OCR 噪声）；漏判导致乱码 PDF 直接入库污染检索。
- **借鉴建议**：对标 **Unstructured / pdfplumber 的 `extract_text` 结合字体 ToUnicode 元数据检测**（优先看字体 CMap 是否含 ToUnicode，比文本启发式更可靠），或 combined 检测（字形 + 字数分布 + 词命中率）降低误判。

#### 【低】`parse_file` 对未知扩展名回退到 `_parse_txt`，二进制文件被当文本读会产出乱码 chunk（L41-42）
- **根因**：`parsers.get(ext, _parse_txt)`——任何未列出的扩展名（`.doc` 旧版、`.rtf`、`.wps`、`.epub`、图片、二进制）都会走 `_parse_txt`，二进制文件读出来是一堆 `\x00`/乱码。
- **影响**：旧版 `.doc`、`.rtf`、`.wps` 等常见格式被当纯文本硬解析，产出大量无用 chunk 并入库，污染向量空间。
- **借鉴建议**：对标 **magic/`python-magic` MIME 嗅探**（llama_index 对未知类型会拒绝或走结构化分区器），未知扩展名应先判 MIME 再决定解析器，二进制应拒绝或走对应分区器。

### 2.2 `chunker.py`（分块）

#### 【高】纯按「段落/标题」切分，**不识别表格结构**，表格会被拦腰切断（L30-90）
- **根因**：`chunk_text` 只按 `HEADING_PAT` + 空行段落切分；`CHUNK_OVERLAP=0`。对 XLSX 解析出的 `\t` 拼接行、DOCX 表格（若未来补上）、CSV 表格，这些内容**没有空行分隔**，会被 `_split_paragraphs` 当成一个超长段落，然后触发「单段落超长强制按 400 字硬切」（L45-58），把一行表格数据从中间切开，列对应关系断裂。同时 `re.sub` 类的表格清洗丢列后相邻列粘连。
- **影响**：表格的「行 = 一条完整记录」被切成多个无关联 chunk，或一行里列值错位；检索"某规格对应的某参数"时，参数值和它所属行/列分离。
- **借鉴建议**：对标 **LlamaIndex `SemanticSplitterNodeParser` + Table 结构识别**，或 **Unstructured 的 `by_title` 分块（对 Table/Title/ListItem 分别处理）**。表格源应先按「行」分块并保留表头，或转为 markdown 表格再按行切，避免跨行截断。

#### 【中】`CHUNK_OVERLAP=0` 与 `CHUNK_SIZE=400` 组合，长文档语义被硬截断（L15-16, L45-58）
- **根因**：`CHUNK_OVERLAP=0`，单段落 >400 字时 `range(0, len(para), CHUNK_SIZE)` 硬切，前后 chunk 无任何重叠，段落首尾句常被拦腰斩断；且注释声称"重叠不提升检索"援引 Chroma 2024 报告，但该结论适用于**语义分块**场景，对**固定字符数硬切**并不成立。
- **影响**：跨 chunk 的完整句/定义被切断，检索时需命中「句子的另一半」时召回失败；无重叠也导致实体/标准号被切到 chunk 边界。
- **借鉴建议**：对标 **LangChain `RecursiveCharacterTextSplitter`（带 overlap）** 或 llama_index `SentenceSplitter`，在固定切分之上增加 sentence-level 边界感知 + 适度 overlap。

#### 【中】`_split_by_heading` 用 `HEADING_PAT.split` 会丢失分隔符位置信息，且标题模式仅覆盖中文/`#`，英文标题、编号标题（如 `1.2.3`、`Appendix A`）不识别（L95-126）
- **根因**：`re.split` 用捕获组时标题本身会成为独立元素，但代码用「先判断 `parts[0]` 是否标题」的偷懒逻辑，对「正文开头无标题」「连续两个标题」等边界容易错位；`HEADING_PAT` 只匹配 `#` 及中文序号/「第X章」，不匹配 `1.2.3 标题`、`1) xxx`、英文 `1. Introduction` 等。
- **影响**：带数字编号标题的文档（大量技术报告/标准），标题不被识别，heading 元数据为空，Contextual Retrieval 的章节上下文前缀失效，分块边界混乱。
- **借鉴建议**：对标 **Unstructured `detect_title` / docx 的 heading 样式**，直接用文档原生 heading 层级（PDF 的字体大小/书签、docx 的 Heading 样式、md 的 `#` 层级），而非脆弱的正则。

#### 【低】Contextual Retrieval 前缀写进 `content` 而非独立 metadata，污染原始正文（L70-82）
- **根因**：`RAG_CONTEXT_PREFIX=="1"` 时把 `[文件名 | 章节] ` 前缀直接改写 `c["content"]`。向量化基于「被污染后的 content」，检索命中后展示的也是带前缀的文本；且前缀长度截断 `_CONTEXT_PREFIX_LEN=80` 可能截断章节名。
- **影响**：BM25/向量都对「加了前缀」的文本建模，与用户真实提问用词分布错位；原文展示带冗余前缀。Anthropic 方案是把上下文放**独立字段**参与索引而非污染正文。
- **借鉴建议**：对标 **Anthropic Contextual Retrieval 原文做法**/LlamaIndex 的 `MetadataExtractor`：上下文应存 chunk 的 `metadata['context']`，检索时拼接，而非覆写 content。

#### 【低】`normalize_chunks` 后 chunk 数量变化，但 `index` 未重排（L84-98）
- **根因**：`normalize_chunks` 丢弃非中文 chunk 后，剩余 chunk 的 `"index"` 字段仍是归一化前的序号，出现空洞。入库时 `store` 用 `c["index"]` 作为 chunk 序号（见 ingest_stages），可能导致 index 与真实顺序不一致（影响按序渲染/相邻 chunk 关系）。
- **影响**：可读模式/相邻 chunk 引用/去重逻辑基于 index 时错位。
- **借鉴建议**：归一化后应重排 `index`；或 index 由入库时统一按插入顺序分配（见 2.4）。

### 2.3 `embedder.py`（向量化）

#### 【高】本地模型默认 `bge-large-zh-v1.5`（1024 维），远端**硬编码** `bge-large-zh-v1.5`（1024 维），但注释与 config 存在**维度不一致风险**（L117 / L167 / config）
- **根因**：`_encode_remote` 硬编码 `"model": "BAAI/bge-large-zh-v1.5"`；`_encode_local` 用 config `EMBEDDING_MODEL`（默认 bge-large-zh-v1.5，1024 维）。当前一致，但**一旦用户改 `EMBEDDING_MODEL` 为 small(bge-small, 512 维) 或其它模型，本地 512 维、远端仍 1024 维**，本地/远程混用同一批数据产出维度不同的向量，ChromaDB/SQLite 存储维度不一致 → 相似度计算/检索崩溃或静默错误。
- **影响**：切换本地/远程（>300 chunks 切远程，失败降级本地）时，同一知识库出现混维向量，检索召回严重失准甚至报错；且远程阈值 `EMBED_REMOTE_THRESHOLD=300` 触发后，大文档走远程 1024 维、小文档走本地，**长期混库**。
- **借鉴建议**：对标 **sentence-transformers 统一 `EmbeddingDimension` 契约** / LlamaIndex 的 `Embedding` 抽象：本地与远程必须锁定**同一模型主、同一维度**，远端模型名应从 config 派生而非硬编码；入库时校验维度一致性并拒绝混维写入。

#### 【中】`encode` 的降级链存在静默失败与「失败后无兜底」的分支（L189-238）
- **根因**：`encode` 逻辑：
  1. `n > REMOTE_THRESHOLD` 走远程，失败降级本地，本地再失败 → `raise`（L207-213 的 `except: pass` 后 `raise`，**原本远程异常被吞**，最终抛本地异常，掩盖根因）。
  2. `n <= 阈值` 且无本地模型或本地失败 → 走远程。
  3. 若本地无模型 + 远程无 API key（`SILICONFLOW_API_KEY` 空），`_encode_remote` 直接 `raise ValueError("缺少 SILICONFLOW_API_KEY")`，**没有任何本地兜底或友好降级**。
- **影响**：离线/无 API key 环境下，所有 embedding 失败，文件无法入库；`SILICONFLOW_API_KEY` 为空时 `_encode_remote` 报"缺少 key"而非尝试本地，逻辑与「本地优先」注释矛盾。
- **借鉴建议**：对标 **LangChain `Embeddings` 多 provider fallback 链**：显式建模「本地→远程→报错」的降级矩阵，并在缺少远程 key 时不切远程而是保留本地路径；错误信息保留根因（不要 `except: pass` 吞远程异常）。

#### 【中】`_encode_remote` 硬截断 `MAX_CHARS=400`，长 chunk 被静默截断丢失语义（L178-181）
- **根因**：`texts = [t[:MAX_CHARS] for t in texts]`，`MAX_CHARS=400`。`bge-large-zh` max_seq_length=512 token（中文约 1 字 1 token），400 字其实**低于 512 上限**，过度截断；且截断是「硬切前 400 字」，chunk 的**后半段关键参数/结论被丢弃**。
- **影响**：>400 字的 chunk（chunker 单段落超长会切到 400，但正常 chunk 可能拼到接近 400+），其尾部信息不参与向量，语义不完整。
- **借鉴建议**：对标 **sentence-transformers `truncate_dim`/模型 max_seq_length 精确对齐 + 截断位置可配**；或用模型的 tokenizer 精确算 token 再截断，而非按字符粗略截断。

#### 【低】`_encode_local` 的 `_embedder` 单例 + `_embedder_lock` 只保护初始化，`encode` 本身**非线程安全**（L127-162）
- **根因**：`_embedder` 是模块级单例，`_encode_local` 内多线程并发 `_embedder.encode(...)` 时，sentence-transformers 模型对象在同一 device 上并发推理可能线程不安全（尤其 CPU 并发 + pytorch 内部分片）。engine 每个任务一个 daemon 线程（L2.5 提到无并发上限），多文件并发 embedding 会共享此单例。
- **影响**：并发入库时向量化可能偶发错误或结果错乱；CPU 并发下性能劣化、显存/内存争抢。
- **借鉴建议**：对标 **sentence-transformers 官方推荐「每线程一个模型」或加 encode 级互斥锁**；或用 `ThreadPoolExecutor(1)` 序列化本地 encode 调用。

#### 【低】`_get_local_path` 的路径探测逻辑脆弱（标准/legacy/legacy2 三套 + 权重存在性校验），易受 HF 缓存结构变化影响（L28-95）
- **根因**：硬编码 HF 缓存路径结构 `models--{name}/snapshots/{hash}`，并兼容 legacy1/legacy2；`_has_weights` 靠文件名白名单 + `>1KB` 判重。HF 缓存目录结构随版本变化时探测失效。虽有 `_LOCAL_CHECKED` 缓存，但首次探测失败后 `_LOCAL_UNAVAILABLE` 会永久禁用本地（进程内）。
- **影响**：模型路径结构变化导致本地模型"找不到"→ 静默切远程（可能无 API key 直接失败）。
- **借鉴建议**：对标 **sentence-transformers 的 `snapshot_download` / HuggingFace `try_to_load_from_cache`** 官方缓存解析 API，而非手写路径探测。

### 2.4 `ingest_stages.py`（入库 Stage）

#### 【高】`_stage_parse` 对「解析返回提示串/空内容」的校验阈值 `<50` 过于宽松，垃圾内容可入库（L44-54）
- **根因**：`if not text or len(text.strip()) < 50: raise ValueError`。但 `_parse_ppt` 在 LibreOffice 缺失时返回的提示串 `"[文件: xxx] 旧版 .ppt 格式不支持直接解析，请用 PowerPoint 另存为 PDF 后重新上传。"` 长度 >50 字，会**通过校验**，把这句"不支持提示"当正文入库；CAD 文件的 `"[工程文件] 文件名: xxx"` 同理也会入库。
- **影响**：污染向量库的内容条目；用户检索时命中"请另存为 PDF"这类无意义提示。
- **借鉴建议**：解析器应区分「真实内容」与「降级提示」两种返回（如返回 `(text, status)` 或 `None` 表失败），Stage 据此决定是否入库；对标 Unstructured 的 `elements` 空列表即判失败，不塞占位串。

#### 【中】`_stage_store` 的 `add_file` → `add_chunks_batch` → `sync_chunk_count` 非事务，与 `_stage_embed` 分工导致中间态可残留（L62-82）
- **根因**：`store` 先 `add_file` 建记录，再 `add_chunks_batch` 写 chunk，若 `add_chunks_batch` 失败（SQLite 锁/OOM），file 记录已存在但 chunk 为空；`sync_chunk_count` 失败时 chunk 数与实际不一致。且 `_stage_embed`(critical) 与 `_stage_store`(critical) 之间若 embed 成功但 store 失败，已算的 embedding 浪费。
- **影响**：出现「文件已入库但 0 chunk」的脏数据，检索该文件永远空；重复上传无法幂等去重（无文件指纹/去重键）。
- **借鉴建议**：对标 **LlamaIndex / 数据库事务式入库**：file + chunks 应原子提交（同一事务/或先写 chunk 再提交 file 状态）；文件内容 hash (MD5/SHA256) 作为去重键，避免重复入库。

#### 【中】ChromaDB 写入仅 `try/except` 吞掉异常且**无重试/无一致性校验**（L78-84）
- **根因**：`store` 和流式路径对 ChromaDB `add_batch` 失败都 `logger.warning` 忽略，SQLite 已写入 chunk 但 Chroma 未写入，两库数据不一致且无重试、无对账。
- **影响**：向量检索（依赖 Chroma）与 BM25/FTS 检索（依赖 SQLite）结果不一致，部分文件"BM25 能搜到、向量搜不到"。
- **借鉴建议**：对标 **ChromaDB 的 `add` + 断点续传/重试**，或引入对账任务周期比对 SQLite 与 Chroma 的 chunk 集合差异并补齐。

#### 【低】`_stage_embed` 的 `token_counts = [max(1, len(c)//2)]` 是粗略估算，非真实 token 数（L64）
- **根因**：用「字符数//2」近似 token，中英文/数字/符号 token 比例差异大，估算偏差可能数倍。若下游按 token 计费/截断，会失真。
- **影响**：token 数元数据不准，影响成本统计与后续截断决策。
- **借鉴建议**：对标 **tiktoken/HF tokenizer 精确计 token**，或至少用分词的词数而非字符数。

### 2.5 `engine.py`（引擎编排）

#### 【高】每任务一个 daemon 线程，**无并发上限/无队列**，大量文件并发上传会线程爆炸 + 内存/CPU 打满（L184-252）
- **根因**：`enqueue` 直接 `threading.Thread(target=_run, daemon=True).start()`，无 `ThreadPoolExecutor`/信号量/任务队列。上传 N 个大 PDF 就同时起 N 个线程，每个线程可能持有整本文本 + embedding + OCR 引擎。
- **影响**：并发上传规模一大，GB 级内存占用 + 共享 embedding 单例争抢 + OCR/python GIL 争抢，极易触发 OOM/gateway 卡死（对应 AGENTS.md 里记录的「subagent 并行超 3 个内存暴涨」同理）。
- **借鉴建议**：对标 **Celery/RQ 任务队列 / `concurrent.futures.ThreadPoolExecutor(max_workers=N)`** 限流；入库天然是重 I/O+CPU 任务，建议独立 worker 进程 + 有界队列 + 背压。

#### 【中】`_run_sync` 对 critical stage 失败 `raise`，但对普通 stage 失败仅 `logger.warning` 继续，**失败信息不进 task.error**（L243-273）
- **根因**：普通 sync stage（如 classify/extract）失败被吞，任务最终仍标 `done`，用户看到"成功"但实际分类/实体抽取缺失；`task.error` 字段仅在最外层 `_run` 的全局 except 才写，stage 级失败不记录。
- **影响**：入库「表面成功，功能残缺」——分类缺失、实体未抽取、摘要为空，但状态显示完成，难以定位真实失败。
- **借鉴建议**：对标 **Airflow/Prefect 的 task 级状态**：每个 Stage 独立记录 status/skipped/failed 到任务详情，`done` 但有 stage 降级时应暴露 warning 到前端。

#### 【中】`_finish_sync` 先置 status=done(95)，再异步后处理，最后置 done(100)，但**异步后处理失败/未完成时状态仍显示 100% 完成**（L275-314）
- **根因**：`_run_async_stages` 是独立 daemon 线程，`_finish_sync` 立刻把状态更新为 done(100) 并持久化；异步 Stage（摘要/标签/预索引/语义边）是否完成、是否失败，主状态流不感知（只在 `_worker` 里 `except: pass`）。
- **影响**：用户看到"完成"后摘要/标签其实还在跑或已失败，缺乏「后处理进行中 vs 完成」的区分；且 daemon 线程随进程退出会**中断未完成的后处理**（进程重启后 recover_tasks 只把 running 标记 failed，已标 done 的不重跑，后处理永久缺失）。
- **借鉴建议**：对标 **任务状态的「基础入库完成」与「后处理完成」分阶段建模**，后处理结果持久化并可补跑（如 recover 时检查摘要为空则重跑）。

#### 【中】`_run_streaming_pdf` 的 `add_chunks_batch` 在 `on_batch` 回调内执行，**每批一次 DB 提交**，且 `chunk_index` 用 `global_chunk_idx` 手动累加，中途失败无回滚（L344-414）
- **根因**：每 flush 页就 `add_chunks_batch` 一次（RAG_STREAM_FLUSH_PAGES=20），大 PDF 有几十上百次提交；`global_chunk_idx` 非原子累加，若中途异常，已写入的 chunk 保留、file 记录保留，但 `sync_chunk_count` 未执行，chunk 数与实际不符，且无「部分入库」的状态标记。
- **影响**：大 PDF 入库频繁 DB IO 慢；中断后出现「部分 chunk 已进去但 chunk_count 不准」，重复上传进一步叠加。
- **借鉴建议**：对标 **批量事务 + 断点续传**（每批在一个事务里提交 file_id 关联，或先攒满再批量 flush）。

#### 【低】`_evict_old_tasks` 淘汰已完成任务时会 `delete_task`，但只淘汰内存 `_tasks` 中的，DB 可能残留（L46-67）
- **根因**：`_evict_old_tasks` 只处理内存 dict 里的 finished 任务；`recover_tasks` 从 DB `load_tasks` 加载回内存，若 DB 里历史任务未同步删干净，重启后又塞回内存形成抖动。
- **影响**：长期运行任务状态内存/DB 不一致，重启后历史冗余任务重新加载。
- **借鉴建议**：对标 **统一的任务存储清理策略**（内存与 DB 同步淘汰，或 DB 只做冷数据、内存做热数据）。

#### 【低】`_prepare` 用 `shutil.copy2` 复制到 UPLOAD_DIR，**重名文件直接覆盖**，无命名冲突处理（L274-282）
- **根因**：`dest = UPLOAD_DIR / ctx["filename"]`，同名文件（如两个不同部门都上传 `参数表.xlsx`）后覆盖前，`target_path` 相同导致 `add_file` 的 path 字段撞车。
- **影响**：同名文件覆盖导致前一个文件的原始文件被替换，`file_id` 指向的 path 内容变成后一个文件，可读模式/重解析读到错文件。
- **借鉴建议**：对标 **UUID/时间戳重命名存储**（存储层文件名加唯一后缀，逻辑名存 metadata），避免覆盖。

### 2.6 `ocr_engine.py`（OCR 引擎）

#### 【中】`build_ocr` 每次调用重新初始化 OCR 引擎，pptx/pdf 逐页复用前**无单例缓存**（L18-50）
- **根因**：`build_ocr` 每次被 `_parse_pdf_ocr` / `parse_pdf_streaming` 调用都会 `RapidOCR(params=...)` 重新加载模型（重、耗时，模型权重加载秒~十秒级）。parser 里 OCR 路径每次解析一个 PDF 就 init 一次，虽同一 PDF 内复用一个引擎，但**多文件并发/依次入库时反复加载**。
- **影响**：批量入库大量扫描件时，OCR 模型装载开销被放大，整体吞吐骤降。
- **借鉴建议**：对标 **PaddleOCR 的引擎单例复用**：`build_ocr` 结果模块级缓存（lazy singleton），仅首次初始化；不同 det_cap 配置分层缓存。

#### 【低】`ocr_page_text` 对 v4/v6 输出格式兼容用 `except TypeError` 探测，脆弱（L52-75）
- **根因**：靠 `engine(img)` 是否抛 TypeError 判断 v4/v6 签名，v6 的 `RapidOCR` 返回值类型依赖 rapidocr 包版本，版本升级可能改变返回值结构，TypeError 探测失效。
- **影响**：rapidocr 版本变动导致 OCR 文本解析失败，静默返回空串。
- **借鉴建议**：对标 **显式版本适配**（在 build_ocr 已知版本分支内直接调用对应解析逻辑），而非运行时异常探测。

### 2.7 `language_filter.py`（语言归一化）

#### 【中】`should_drop_chunk` 的「中文词豁免」正则 `[\u4e00-\u9fff]{2,}` 过于宽松，**含 2 个连续汉字的任意英文/数字段都会保留**（L150-190）
- **根因**：豁免规则只要文本含「连续 ≥2 个汉字」就不丢弃，导致大量中英混排但实质是英文/型号内容的 chunk 被保留（如 `GB/T 123 紧固件 M8 材质 ...` 中"紧固件""材质"触发豁免），与「非中文内容过滤」的初衷相悖；同时该豁免会保留本应丢弃的乱码+极少汉字段落。
- **影响**：部分英文/噪声内容未被过滤，混入向量库污染检索；过滤精度不足。
- **借鉴建议**：对标 **langdetect/fasttext 语言识别**（整 chunk 判定主语言），或提高豁免门槛（要求连续 ≥4 字中文词 + 中文字符占比阈值）。

#### 【低】繁简转换「保守映射表 + 歧义字保护」导致**大量繁体字根本不转**，繁简混存影响检索（L30-118）
- **根因**：`_SAFE_TC_TO_SC` 手写映射覆盖不全（大量常用繁体缺失），且 `_AMBIGUOUS_TC` 保护集（乾幹髮發後…）直接保留繁体原字。OpenCC 未装时（`_get_opencc` 返回 None），转换降级到保守映射，繁体残留严重。
- **影响**：繁体文档入库后查询需同时命中繁/简，若查询端未做同样归一化会漏召回；检索质量对繁体文档偏低。
- **借鉴建议**：对标 **OpenCC 标准 t2s**（业界权威繁简映射），直接依赖 OpenCC 而非手写映射表；歧义字保护可保留但应作为特例而非主流路径。

### 2.8 `image_extractor.py`（图片提取）

#### 【中】`_extract_pdf` 整页扫描过滤阈值 `cover_w>0.9 and cover_h>0.9`，会误过滤「大图但也含文字」的页面（L80-130）
- **根因**：凡图片 bbox 覆盖页面宽高 >90% 即判定扫描背景跳过，但技术文档中**整页大示意图**（如总装图、大电路图）常接近填满页面，其本身有价值却被跳过。
- **影响**：大图/整页电路图不提取，可读模式下此页图文为空。
- **借鉴建议**：对标 **图文并存判定**（检测页面是否有独立文本层：有文本层则保留图，纯扫描页才过滤），而非仅用 bbox 面积。

#### 【低】`_extract_xlsx`/`_extract_docx` 图片 `page=0`、`width/height=0`，无坐标/顺序语义（L150-210）
- **根因**：xlsx/docx 直接从 `xl/media`、`word/media` 提取，图片与所在 page/位置脱钩（都标 page 0），尺寸不解析。
- **影响**：可读模式下图片无法按文档位置穿插渲染，只能堆在开头。
- **借鉴建议**：对标 **python-docx 的 `inline_shapes`/关系解析** 获取图片在段落中的位置；xlsx 用 `openpyxl` 的 `ws._images` 定位 sheet+锚点。

## 五、优先级排序建议（修复顺序）

1. **P0（阻断性/数据丢失）**：
   - `_parse_txt` 多编码探测（GBK 中文文件乱码不可逆）

2. **P1（高影响）**：
   - 解析器区分「真实内容 vs 占位提示」，占位串不入库

   - stage 级失败状态可见
   - `_parse_ppt` 依赖缺失显式降级（不塞提示串）
3. **P2（体验/精度）**：
   - CSV 结构化解析
   - chunk overlap/标题识别增强

   - 图片位置锚定
