# 解析链架构重构方案 —— 对标 GitHub 高完成度项目

> 目标：让伏羲的「解析（parse）→ 清洗（clean）→ 切块（chunk）」链路，从「一堆平铺 if-elif」升级为「对标 MinerU / docling / unstructured 的三层架构」，同时**不引入重模型全家桶、不降低稳定性、不破坏对齐度**。
> 原则：只改函数内部实现与模块边界，不改 Stage 接口签名、不改 chunk 数据结构、不改调用方。
> 依据：GitHub 实测（star 数 / 目录树 / README 架构说明，2026-09-08 抓取）。

---

## 一、三个标杆项目的构造（脱敏后的共性）

| 项目 | star | 语言 | 核心构造 |
|------|------|------|---------|
| opendatalab/MinerU | 79.4k | Python | `backend/`（pipeline·vlm·office 三引擎）+ `model/`（layout·table·ocr·mfr 可插拔）+ `data/`（统一数据模型） |
| DS4SD/docling | 66.1k | Python | `backend/`（docx·pdf·latex·iwork 按来源）+ `datamodel/` + `chunking/` 独立 |
| Unstructured-IO/unstructured | 15.4k | Python/HTML | `partition/`（一格式一分区器）+ `cleaners/` + `chunking/` + `documents/`（统一 Element） 三/四段解耦 |
| Layout-Parser | 5.8k | Python | 深度学习版面分析 |
| PaddleOCR | 89.1k | Python | OCR 引擎 |

**殊途同归的三条法则：**

1. **`backend` 抽象层**：解析器按「引擎能力 / 输入来源」分层，不是按「文件扩展名」堆 if-elif。
2. **双引擎可降级**：轻量 pipeline（CPU、快、无幻觉）兜底 + 重引擎（VLM/版面模型）提精度。
3. **parse / clean / chunk 三段解耦**：每段单一职责，可独立替换。

## 二、伏羲现状（真实代码测绘）

### 2.1 parser.py（22741 字节，单文件承担「分发 + 全部解析器」）

```
parse_file(filepath) → 扩展名分发
  ├─ CAD_EXTENSIONS 工程文件只索引文件名
  ├─ parsers dict：.pdf/.ppt/.pptx/.xlsx/.xls/.docx/.txt/.md/.csv/.log
  └─ 未知扩展名 → 二进制 null 嗅探 → _parse_txt 兜底

解析器函数（全部平铺在此文件）：
  _parse_pdf    （fitz 文本层 + CMap 乱码检测 + OCR 兜底）
  _parse_pdf_ocr
  _parse_pptx / _parse_ppt（LibreOffice 兜底 + OLE 二进制提取）
  _parse_xlsx / _parse_xls（xlrd → LibreOffice 兜底）
  _parse_docx   （段落+表格按 body 顺序）
  _parse_txt    （多编码探测）
  _parse_csv    （csv.Sniffer + 列名=值）
  parse_pdf_streaming （流式路径，独立一套）
```

**问题**：
- `parse_file` 的 `parsers` dict 就是「按扩展名堆 if」的另一种写法，与标杆项目的 `backend/` 抽象是两回事。
- `_parse_pdf` 里已经**硬编码兜底链**（文本层→OCR），但没有「按文档复杂度选引擎」的路由。
- `_parse_ppt` / `_parse_xls` 各自内联一段**重复的 LibreOffice 查找逻辑**（三处重复，见下文）。
- `deep_parse.py`（MinerU 可选增强）已经存在，但它跟 `parser._parse_pdf` 的耦合是「在 `_parse_pdf` 开头 if 判断」——这其实是**半成品 backend 抽像**，但只做了 PDF 一种格式。

### 2.2 chunker.py + language_filter.py（切块与清洗已耦合）

```
chunk_text(text, source_name)
  ├─ _split_by_heading  → 按标题拆
  ├─ _split_paragraphs  → 按空行拆
  ├─ 按 CHUNK_SIZE=400 拼块
  ├─ Contextual Retrieval 前缀（RAG_CONTEXT_PREFIX）
  └─ normalize_chunks(chunks)  ← 语言清洗在这里被「硬塞」进 chunker 尾部
```

**问题**：`chunker.chunk_text` 把「切块」和「语言清洗（normalize_chunks）」绑死在一个函数里，与标杆项目的 `cleaners`（独立）理念冲突。且 `normalize_chunks` 返回空时，chunker 内部还要「回退原始 chunk」——这段回退逻辑本质是「清洗层的事」却写在「切块层」。

### 2.3 ingest_stages.py（解析→切块→嵌入的编排）

```
_stage_parse  → parse_file(target) → ctx["text"]
_stage_chunk  → chunk_text(text, source_name) → ctx["chunks"]
_stage_embed  → encode(...)
_stage_store  → add_file + add_chunks_batch + Chroma
```

**问题**：`parse` 和 `chunk` 之间没有独立的 `clean` stage，清洗被塞进了 chunker 尾部——导致「解析产出的文本」和「清洗后文本」无法分观察、分替换。

## 三、重构方案（落到具体文件）

> 核心改动只在一个新文件 `backends.py` + 对 `parser.py` / `chunker.py` 的**函数内部重构**，Stage 签名、chunk dict 结构、调用方**完全不变**。

### 3.1 新增 `src/pipeline/backends.py` —— 引入 backend 抽象（对标 MinerU/docling）

**目的**：把「一个扩展名 → 一个解析函数」升级为「一个 backend → 一组格式」。让后续换解析引擎 = 换一个 backend 类，不动 `parse_file`。

```python
# backends.py（结构示意，非最终代码）
class ParseBackend:                      # 统一接口（对齐 deep_parse 的契约）
    def parse(self, filepath: str) -> str: ...   # 返回纯文本，失败抛 ValueError

class TextBackend(ParseBackend):         # .txt/.md/.log/.csv（多编码 + csv 语义）
class OfficeBackend(ParseBackend):       # .docx/.xlsx/.xls/.ppt/.pptx
    # 内部统一 LibreOffice 查找（消除现在 3 处重复的 soffice 探测）
class PdfBackend(ParseBackend):          # .pdf（文本层→CMap检测→OCR→MinerU 四级链路）
class CadBackend(ParseBackend):          # .mi/.step/.stp/.dwg/...（只索引文件名）
```

**关键收益**：
- **消除重复**：现在 `_parse_ppt` / `_parse_xls` 里各有半段「查找 LibreOffice」的复制代码，收进 `OfficeBackend` 的一个 `_find_libreoffice()`。
- **MinerU 接入对齐**：现有 `deep_parse.py` 就是 PdfBackend 的「增强后端」，抽成 backend 后，`RAG_PDF_DEEP_PARSE` 开关只管 PdfBackend 内部四级链路，不再污染 `parse_file` 入口。

> ⚠️ 注意：这一步**不强制搬函数**。为了守住「不盲目大改」，`parser.py` 里现有的 `_parse_*` 函数**原地保留**，`backends.py` 只是新增一个「分发壳」去调用它们。后续要换某个后端（如换 PDF 引擎）时，才把对应 `_parse_*` 挪进 backend。**先立骨架，再按需填肉**，避免一次性大迁移的风险。

### 3.2 改造 `parser.py` 的 `parse_file` —— 从 dict 分发切到 backend 分发

**现状（23 行）**：
```python
parsers = {".pdf": _parse_pdf, ".ppt": _parse_ppt, ...}
parser = parsers.get(ext)
...
return parser(filepath)
```

**改为（只动函数内部，签名/返回不变）**：
```python
from .backends import EXT_BACKEND  # {ext: backend 类}，在 backends.py 维护
backend = EXT_BACKEND.get(ext, TextBackend)   # 未知扩展名走 TextBackend（保留 null 嗅探在 TextBackend 内）
return backend().parse(filepath)
```

**对齐度承诺**：`parse_file` 对外签名 `parse_file(filepath: str) -> str` 不变，`_stage_parse` 不用改。CAD 工程文件的「只索引文件名」判断挪进 `CadBackend`，行为完全一致。

### 3.3 改造 `chunker.py` —— 把「语言清洗」从切块层剥离（对标 unstructured cleaners）

**现状**：`chunk_text` 尾部硬调用 `normalize_chunks` + 空回退逻辑。

**改为**：把「清洗」抽成一个**独立函数** `clean_chunks(chunks)`，`chunk_text` 保持纯切块（切块 → Contextual Retrieval 前缀 → 返回），清洗由**调用方**决定是否执行：

```python
def chunk_text(text, source_name="") -> list[dict]:
    ...  # 只做切块 + 前缀，删掉 normalize_chunks 调用

def clean_chunks(chunks) -> list[dict]:   # 新增，纯清洗层
    from .language_filter import normalize_chunks
    result = normalize_chunks(chunks)
    return result if len(result) > 0 else chunks  # 空回退逻辑归位到清洗层
```

**为什么这样拆**：
1. 对齐标杆 `cleaners` 独立范式 —— 清洗可单独测试、单独替换（以后换 OpenCC、加专业术语清洗，只动 `clean_chunks`）。
2. 空的「非中文回退」逻辑从切块层挪到清洗层，职责清晰。

**衔接**：`ingest_stages._stage_chunk` 改为：
```python
chunks = chunk_text(ctx["text"], source_name=ctx["filename"])
chunks = clean_chunks(chunks)   # 新增一行，行为与现状完全一致
```
> 这一行是**唯一**的调用方改动，且是「显式化」而非「改行为」——chunk 产出与现在完全一致。

### 3.4 `ingest_stages.py` —— 保持「解析→清洗→切块」三段语义可见

不改 Stage 数量（避免动引擎的 `_sync_stages` 顺序、`critical` 标记）；只把清洗显式化到 `_stage_chunk` 内部（见 3.3 的那一行）。**不新增 `clean` stage**——因为 stage 是「编排粒度」，而 clean/chunk 是「chunk 阶段的内部两小步」，新增 stage 反而会让引擎状态机更啰嗦、破坏现有进度上报语义。这符合「模块式而非缝补」但更符合「不盲目大改」。

## 四、边界与「不做」清单（守住稳定性）

| 不做 | 理由 |
|------|------|
| ❌ 不引入 MinerU/PaddleOCR/docling 全家桶 | 重模型依赖、GPU 假设、下载模型，与你上一轮担心的「臃肿/降速/降稳定」直接冲突 |
| ❌ 不改 `_stage_*` 的 stage 顺序/名称 | 引擎编排与进度上报是已验证的核心链路 |
| ❌ 不改 chunk dict 结构（content/index/heading/source/markdown） | 下游 embed/store/检索全依赖 |
| ❌ 不搬移现有 `_parse_*` 函数本体 | 先立 backend 骨架，函数原地保留，后续按需迁移，避免大迁移风险 |
| ❌ 不新增 VLM/深度解析路由（双引擎「提精度」那一半） | 优先级低，等 OA 文档重新导入、确认复杂度后再单独评估 |

## 六、结论

- 三个标杆项目的真正含金量是**「backend 抽象 + 双引擎降级 + parse/clean/chunk 解耦」**，不是它们的重模型。
- 伏羲的这三样**全都可以用现有的 fitz + RapidOCR + 本地 BGE 实现**，零新依赖。
- 本方案 = 新增 1 个 `backends.py` + 改 `parse_file` 内部 + 拆出 `clean_chunks` + `_stage_chunk` 加一行，**接口、数据结构、Stage 编排、调用方零破坏**。
