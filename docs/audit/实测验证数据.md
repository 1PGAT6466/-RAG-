> 记录日期：2026-09-08
> 说明：本文件记录「实测验证」得到的第一手数据，与三个子代理的「静态代码审计」互为印证。

## 一、向量库残缺度量化（已实证）

### 数据
| 指标 | 数值 |
|------|------|
| SQLite `chunks` 有 embedding 的 chunk 数 | 12190 |
| ChromaDB `embeddings` 表实际存储数 | 9488 |
| **缺失向量数** | **6438** |
| 缺失占比 | ~53%（12190 的 53%）|

### 缺失分布（按 file）
| file_id | 文件名 | 缺 chunk 数 |
|---------|--------|-----------|
| 120 | 非标准机械设计手册.pdf | 3469 |
| 122 | 2026年1月-6月采购数据_供应商分类.xlsx | 2897 |
| 123 | Foxconn_连接器设计手册.ppt | 72 |

### 根因闭环（已实证）
1. 启动时 `server.py` lifespan 调 `chroma_store.ensure_synced()`。
2. `ensure_synced()` 查出 6438 条 SQLite 有、Chroma 缺的向量，一次性 `add_batch()` 补齐。
3. Chroma HNSW `max_batch_size = 5461`，6438 > 5461，**整个批次抛错，一条都没写入**。
4. 日志记录 `Chroma 补齐失败（不影响主服务）: Batch size 6438 exceeds maximum batch size 5461`。
5. **后果**：file 120/122/123 三个大文档的向量完全缺失，纯向量检索时这 3 个文档完全搜不到。注释写「不影响主服务」是错误认知——影响的是检索召回完整性。

### 严重程度：高（检索召回完整性受损，且自欺「不影响主服务」）

## 二、表格型文档解析 + 分块破坏表格结构（已实证）

### 现象
`file 122` = `2026年1月-6月采购数据_供应商分类.xlsx`（采购数据大表），chunk 内容已完全错乱：
- chunk[0]：表头（供应商简称/采购订单单号/品号/品名/规格...）与第一行数据混在一起
- chunk[1..7]：是表格被「横切竖切」后的碎片，单元格值乱序拼接，语义不可读

### 根因（初步）
`_parse_xlsx` 把每行按 `\t` 拼接成纯文本，然后交给 `chunker.chunk_text` 按固定字符数切块。
表格特有的「行列二维结构」在纯文本化后已丢失，再按字符数硬切，导致：
1. 列头与数据分离（chunk[0] 表头 + 数据残片，后续 chunk 全是无序数据）
2. 一行数据被腰斩到不同 chunk
3. 数字/日期/品号等字段失去列语义

### 影响
- 检索时无法按「字段=值」语义召回（如「以太网连接线 X227」查不到精确记录）
- LLM 拿到的上下文是乱序碎片，回复标准度差

### 严重程度：高（表格类文档转化成功率与检索质量双受损）

### 模块式借鉴方向
对标 **RAGFlow（深度文档理解，保留表格结构）/ MinerU（表格识别）/ Unstructured**，
将表格文档改为「结构感知解析」——保留行列结构，chunk 边界对齐表格行，而非按字符硬切。
