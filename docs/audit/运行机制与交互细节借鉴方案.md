# 运行机制与交互细节借鉴方案

> 背景：用户要求不止借鉴「大功能模块」，更要学习 GitHub 完成度高的项目在
> **细节构造、设计理念、运行方式**层面的做法。本方案以今天暴露的两个真实缺陷为锚点
> （删除文档卡死、超大 PDF 入库拖垮服务），延伸到同类「运行机制」隐患，并对标
> LightRAG / RAGFlow / LlamaIndex / Dify 的成熟做法，给出「模块式借鉴」清单。

---

## 一、今天暴露的两个真实缺陷（诊断锚点）

### 缺陷 A：删除文档「程序崩溃」

**现象**：用户在伏羲内删除 file 1（6438 chunk），前端卡死，表现为「程序崩了」。

**根因链**：
1. `delete_file` 的 Chroma 清理是 `for (cid,) in chunk_ids: delete(cid)` —— **逐条循环**
2. 每次 `delete(cid)` 触发 ChromaDB 内部 HNSW 索引重建/持久化
3. file 1 有 6438 个 chunk → 6438 次循环 → 进程 CPU 拉满、HTTP 无响应 → 前端「崩溃」
4. 杀掉进程后，SQLite 已删干净、但 Chroma 循环被中断 → 残留 **5295 个孤儿向量**（5442 → 147）

**已做的临时修复**：`delete_file` 改为 `delete_where(ids=[...])` 批量删除（`chroma_store.py` 新增 `delete_where`），分 `_CHROMA_BATCH_LIMIT=4000` 分批。

**⚠️ 临时修复的局限**：只是「把逐条改成批量」止血，没有解决背后的**架构性问题**（见下文缺陷清单）。

### 缺陷 B：超大 PDF 入库拖垮服务

**现象**：导入 144MB / 1423 页 PDF，走流式入库，卡在 11%~13%，服务 68 分钟 + 3.3GB 内存，导致后续导入全部超时显示「失败」。

**根因链**：
1. 流式入库逐批 embed（20 页/批），单批 chunk 数远小于 `EMBED_REMOTE_THRESHOLD(300)`
2. 触发不了「超阈值走远程」，1423 页全程**本地 CPU embedding**（BAAI bge-large）
3. 已做的修复：`encode()` 加 `force_remote`，`_run_streaming_pdf` 开头 fitz 拿总页数 ≥ `RAG_EMBED_FORCE_REMOTE_PAGES(100)` 时强制远程

## 二、对标结论：成熟项目怎么做（实测抓取）

### LightRAG（最直接对标，图增强 RAG + 删除/重建机制）

| 做法 | 伏羲现状 | 差距 |
|------|----------|------|
| **删除是「异步 + 批量」** | `delete_file` 是**同步阻塞**，前端等 HTTP 返回 | 伏羲所有删除都卡在请求线程，大文件必卡 |
| **Smart Cleanup**（删文档时识别「仅属本文档」的实体/关系，共享知识保留） | 伏羲删文档只删 chunks/FTS/Chroma，**不清理 entity/relation** | 图谱层残留脏数据，可能污染图谱召回 |
| **Cache Optimization**（删除时清相关 LLM 缓存） | 伏羲删除**不清语义缓存** | 已删 chunk 可能仍命中缓存返回「陈腐答案」 |
| **Incremental Rebuilding**（从剩余文档重建受影响描述） | 无此机制 | 批量删除后图谱/摘要退化 |
| **文档 ID 作为删除粒度** | 有，但走同步 | 对齐不足 |

### RAGFlow（最对标整体，90k+ star）

- **文档级状态机**：`UNSTART / RUNNING / DONE / FAIL / CANCEL`，删除/重建是**任务而非同步请求**
- **Task Executor 抽象**：所有长任务（解析/切块/嵌入/索引）进任务队列，UI 轮询进度，**绝不阻塞 HTTP 请求线程**
- **对象存储 + 元数据库分离**：原始文件、解析产物、向量索引三层解耦

### LlamaIndex / LangChain（工程抽象层）

- **VectorStore 统一接口**：`add_documents(ids=[...])` / `delete(ids=[...])` 全是**批量接口**，无逐条循环
- **删除语义统一为「按 ID 批量」**，文档删除 = 一次 `delete(ids=chunk_ids)`

### Dify / kotaemon（前端交互）

- **任务进度可视化**：上传/导入/删除都有独立的任务面板 + 实时进度条 + 可取消
- **删除二次确认 + 后台执行 + 完成通知**，而非同步 loading 转圈

## 三、缺陷清单（按严重度排序，锚点 + 延伸）

> 标 ⭐ 的为「今天已触发或即将触发」的紧急项；其余为同类运行机制隐患。

### 🔴 P0（紧急，已触发或极易触发）

1. **⭐ 删除/批量操作 → 同步阻塞 + 逐条循环**
   - `delete_file` 已止血（批量），但**仍是同步阻塞**：前端删除大文件（万级 chunk）时 HTTP 请求线程被占，其他请求排队超时。
   - **借鉴**：LightRAG/RAGFlow 的「异步任务 + 后台执行」，删除返回任务 ID，前端轮询进度。

2. **⭐ 删除不清理图谱实体/关系 + 语义缓存**
   - 删文档后 `entity_chunks / entity_files / links` 的清理不完整（`links` 有清理，但 `entities`/`relations` 层无 Smart Cleanup）。
   - **借鉴**：LightRAG「Smart Cleanup」——识别仅属本文档的实体删除，共享实体保留并重建描述。

3. **⭐ 删除不完全 → 「shadow copy 阴影副本」**
   - 今天实测出现 5295 个孤儿向量，即 LightRAG 社区 #1676 描述的「文档删除后向量/元数据残留」通用问题。
   - **借鉴**：删除做成**原子事务**（先删向量、再删元数据、最后提交，或引入软删除 + 后台对账）。伏羲已有 `cleanup_chroma_orphans.py` 对账脚本，但**无自动触发**。

### 🟠 P1（高价值，运行机制不健壮）

4. **⭐ 超大文件 embedding 无「规模感知」**
   - 已做 `force_remote` 止血，但只覆盖 PDF 流式路径。Office/文本大文件（如万行 CSV）走非流式 embed，仍可能本地 CPU 卡死。
   - **借鉴**：LlamaIndex/RAGFlow 的「按总 chunk 数预判 → 选择本地/远程 embedding」统一策略，而非只有 PDF 一个入口判断。

5. **长任务无统一取消/超时机制**
   - 流式入库那个 running 任务跑了 68 分钟无人干预。无「取消任务」「任务超时报错」「任务重试」。
   - **借鉴**：RAGFlow 的 Task 状态机（含 `CANCEL`、超时自动 `FAIL`）。

6. **tasks 表脏数据不清理**
   - 实测定 `tasks` 表 8 行，含 4 个 `test.txt`、1 个 `x`、1 个已删文档的 failed 记录，永久残留。
   - **借鉴**：RAGFlow/Dify 的「任务历史保留窗口」策略（如只保留最近 N 条 / 定期清理 failed）。

### 🟡 P2（体验细节，前端交互）

7. **删除/导入缺「后台执行 + 进度 + 可取消」交互**
   - 现在删除是同步 loading，大文件时前端「假死」。
   - **借鉴**：Dify/kotaemon 的任务面板：操作 → 入队 → 进度条 → 完成/失败通知 → 可取消。

8. **错误提示不明确**
   - 「导入失败」无具体原因（今天根因是服务被拖垮，但用户只看到「失败」）。应区分「文件过大」「服务繁忙」「格式不支持」等。

## 四、借鉴方案（模块式替换，非缝补）

### 方案 1：删除/重建 → 异步任务化（对标本 LightRAG `adelete_by_doc_id`）

把 `delete_file` 的调用链路从「同步 HTTP 阻塞」改为「异步任务」：

```
DELETE /api/documents/{file_id}
  → 立即返回 {"task_id": "...", "status": "queued"}
  → 后台线程执行：删 chunks → FTS → Chroma(批量) → 实体 Smart Cleanup → 缓存失效
  → 前端轮询 GET /api/tasks/{task_id} 显示进度
```

**模块来源**：LightRAG 的「删除是异步操作」+ RAGFlow 的 Task Executor。

### 方案 2：删除原子性 + 对账（解决阴影副本）

- **软删除**：`files` 加 `deleted_at` 字段，删除标记而非物理删；后台对账任务定期清物理残留 + 清 Chroma 孤儿。
- **或**：删除事务化——先 `delete_where(向量)` 成功，再删 SQLite 元数据，任一失败回滚。
- **自动对账**：把 `cleanup_chroma_orphans.py` 逻辑内置为「启动时 + 定期后台」自动跑，而非手动脚本。

### 方案 3：统一「规模感知 embedding」入口

把「总 chunk 数预判 → 本地/远程 embedding 选择」从「仅 PDF 流式」提升为**全局 embed 决策层**：

```
embed(contents, force_remote=None)
  → 若 force_remote 未指定，按 len(contents) 或文件规模自主判断
  → 覆盖：流式 PDF、Office 大文件、批量导入
```

### 方案 4：任务状态机（取消/超时/清理）

对齐 RAGFlow 的 `UNSTART/RUNNING/DONE/FAIL/CANCEL`：
- 加 `cancel_task(task_id)`（设置取消标记，循环内检查）
- 加任务超时（如 2h 自动 FAIL）
- tasks 表加「保留窗口」定期清理 failed/陈旧记录

### 方案 5：前端任务面板 + 明确错误

- 删除/导入/重建统一走「任务面板」：进度条 + 取消 + 完成通知
- 错误分类：`FILE_TOO_LARGE` / `SERVICE_BUSY` / `FORMAT_UNSUPPORTED` 等，前端给可执行提示

## 五、建议执行顺序

| 顺序 | 方案 | 理由 | 风险 |
|------|------|------|------|
| ① | 方案 1（删除异步任务化） | 直接解决今天崩溃，最高频操作 | 中（改动删除链路） |
| ② | 方案 2（原子性 + 自动对账） | 根治孤儿向量，防「阴影副本」复发 | 低（已有对账脚本，只需内置） |
| ③ | 方案 3（规模感知 embed） | 覆盖 Office/批量大文件，补全止血 | 低 |
| ④ | 方案 4（任务状态机） | 提升整体运行健壮性 | 中 |
| ⑤ | 方案 5（前端交互） | 体验细节，价值高但可后置 | 低 |
