## 第二部分：🔴 架构级根因（这是「天天修 bug」的真正原因）

### 根因：FastAPI `async def` 路由里直接调同步阻塞代码 → 事件循环被独占

**伏羲现状**：几乎所有路由都是 `async def`，内部直接调**同步阻塞**的 SQLite 查询、embedding、Chroma 删除、SeedDMS 写入：

```python
# src/api/documents.py — api_upload 是 async def
async def api_upload(...):
    ...
    dms_doc_id = upload_document(...)   # 同步写 SeedDMS SQLite + 文件系统 ❌ 阻塞事件循环
    ...
# api_delete_file 同理：delete_file() 里同步删 Chroma 6438 次 ❌
```

**这是今天「删除崩溃」「导入超时」的**唯一根因**，也是之前所有补丁（批量删除、force_remote）没解决的架构问题。**

### GitHub 成熟项目的一致性结论（三个独立证据）

| 来源 | 结论 |
|------|------|
| CSDN FastAPI 性能陷阱压测 | `async def` + 同步阻塞：10 并发 QPS ≈ **1**（事件循环被完全阻塞）；正确异步 50+；纯 `def` 线程池 8~15 |
| whisperX-FastAPI 案例 | 「Load test 证明 ~20 并发就崩」，根因「async def 里直接 session.query 阻塞单线程事件循环 + SQLite 无真写并发」；解法「**双引擎 + 阻塞任务丢 `run_in_executor` 线程池**」 |
| FastAPI 官方讨论 #13101 | 「在 async 函数里跑阻塞代码是错的，要用 `run_in_executor` / `asyncio.to_thread`，或直接让端点是 `def`」 |

### 成熟解法（对标 whisperX-FastAPI「Dual-Engine Async Architecture」）

```
规则（快记）：
1. I/O 密集 + 可异步 → 用原生 async（httpx.AsyncClient、aiosqlite）
2. CPU 密集/同步库（embedding、Chroma、SeedDMS 写、sqlite3）→ await run_in_threadpool()
3. 拿不准 → 端点直接写 def（FastAPI 自动丢线程池，而不是 async def 里裸调阻塞）
```

**伏羲落地**：`src/api/*.py` 所有 `async def` 里直接调 `src.storage.*` / `src.pipeline.*` 同步函数的地方，统一用 `fastapi.concurrency.run_in_threadpool` 包裹，或把「纯同步端点」改成 `def`。

## 第三部分：后端链路深挖（模块 → 接口 → 细节）

### 3.1 入库链路（pipeline）— 今天崩溃重灾区

| 阶段 | 现状问题 | GitHub 对标 | 改造 |
|------|----------|-------------|------|
| 上传 | `api_upload` 同步写 DMS 阻塞 | RAGFlow 上传即返回 task_id，写库走任务队列 | 后台化 |
| 解析 | parser 467 行 if/else 分发 | （已做 backend 抽象层，✅） | — |
| 切块 | chunker 里混了清洗逻辑 | unstructured 独立 cleaners 层 | （已做 clean_chunks ✅） |
| 嵌入 | 流式逐批触发不了远程阈值 | LlamaIndex「规模感知」统一决策 | 已补 force_remote，但只覆盖 PDF |
| 存储 | Chroma 逐条删除死锁 | LangChain `delete(ids=[...])` 批量 | 已补 delete_where ✅ |

**核心待办**：
1. **任务状态机补全**：`_tasks` 内存 dict + tasks 表双轨，但缺 `cancel` / `timeout` / `retry`（RAGFlow 有 `CANCEL` + 超时自动 `FAIL`）。
2. **规模感知 embed 全局化**（不只 PDF 流式）：按总 chunk 数预判本地/远程，覆盖 Office/批量导入。
3. **tasks 表脏数据清理**（今天实测 8 行里有 6 个 test 残留）。

### 3.2 检索链路（retrieval/search.py 594 行）

- **四路召回 + RRF 融合 + rerank** 架构成熟，但 `search()` 是同步函数，在 `async` 路由里裸调会阻塞。需 `run_in_threadpool` 包裹。
- rerank 已分批（缺陷 15 ✅），但 `rerank_with_deepseek` 仍是同步 httpx.Client。

### 3.3 LLM 生成链路（chat/orchestrator.py + engine.py + cache.py）

- 已是 async（httpx.AsyncClient）✅，这是正确的。
- **但** `_persist_stream` 里 `add_conversation_message` 是同步 SQLite 写，虽然已「try/except 降级」，但仍在事件循环里同步执行——应丢线程池或改 `def`。

### 3.4 存储层（storage/db.py）— SQLite 并发模型

- 用了 `threading.local()` + `contextvars.ContextVar` **双轨**，这是 MEMORY 里记过的「async 上下文 DB 连接陷阱」。
- **对标 whisperX-FastAPI**：SQLite 在 async 上下文「NullPool 每次请求新建连接」，避免 `database is locked`。
- **伏羲落地**：要么全链路 `def`（线程池，每个线程独立连接，threading.local 正确），要么用 aiosqlite 重写 async 层。**推荐前者**（改动小，与 threading.local 兼容）。

### 插件/MCP 稳定性（重点，对标 LightRAG/LangChain MCP client）

**关键发现**：伏羲自己的插件系统（`src/plugins/host.py`）已经实现了**子进程池 + 方法白名单**，但 **MCP 这条路（`src/mcp/client.py`, `manager.py`）没有复用**这套进程池机制——每次 `list_mcp_tools` / `call_mcp_tool` 都重新拉起 stdio 子进程。这是「模块式借鉴」的最佳素材：**把 MCP 的 stdio 连接也纳入 host.py 的进程池管理**，而非另起一套。

## 第六部分：关键结论

1. **今天所有崩溃的根因是同一个**：FastAPI `async def` 里裸调同步阻塞代码，独占事件循环。这是架构问题，不是「哪个 bug」——之前补丁治标不治本。

2. **「模块式借鉴」最直接的两块素材**：
   - FastAPI 并发模型 → 直接抄 whisperX-FastAPI 的「阻塞任务进线程池」模式
   - MCP stdio 稳定性 → 直接复用伏羲自己已经有的插件进程池（host.py）

3. **落地优先级**：先做「阶段 0」的 4 项（都是止血 + 稳定），这 4 项做完，伏羲就能上测试版而不会再「一删就崩、一导就卡」。
