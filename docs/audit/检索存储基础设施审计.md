# 伏羲 RAG 系统 —— 检索/召回链路 & 存储/基础设施 审计报告

> 审计范围：`src/retrieval/*`、`src/storage/*`
> 审计日期：2026-09-08
> 审计方式：纯静态代码精读，未改动任何代码
> 严重程度分级：🔴 高危（会导致错误结果/数据丢失/崩溃）｜🟠 中危（质量/性能/一致性问题）｜🟡 低危（健壮性/工程规范）

---

## 一、总览与结论

| 分层 | 成熟度评价 | 核心问题数 |
|------|-----------|-----------|
| 检索/召回链路（search/ranking/rerank/graph_recall） | 中等，方向正确但存在多处「魔法数字」「双路径分叉」「融合量纲混乱」 | 12 |
| 存储/SQLite 层（db/chunks/files/entities） | 中等，FTS5 双虚拟表一致性、并发模型是最大隐患 | 8 |
| 向量存储（chroma_store） | 偏弱，已知 HNSW 持久化被「禁用」属治标，按行 upsert 效率低 | 5 |
| 分词（tokenizer） | 基本可用，词典缺失、bigram 回退不一致 | 3 |

**一句话结论**：这套系统的「召回广度」做得不错（四路召回 + 文件名兜底 + 看门狗 + 置顶保序），但「融合/打分」层存在系统性缺陷——**RRF 权重量纲不统一、多份冗余且互相矛盾的置顶/加权逻辑并存、rerank 分数和融合分数被混用**，导致排序结果在开启/关闭动态开关、开关 rerank 时行为不一致、不可复现。

## 二、缺陷清单（按层分类）

---

### 2.1 混合检索融合算法（RRF）

#### 缺陷 1 🔴 RRF 权重对不同召回源使用「原始排名倒数」但源之间「召回长度差异」未归一化，导致评分量纲不一致

- **位置**：`search.py:527-600`（`_rrf_fusion`）、`ranking.py:236-291`（`weighted_rrf_fusion`）
- **根因**：RRF 公式 `weight / (k + rank + 1)` 中，`rank` 是各召回源各自的排名序号。但四路召回源的召回数量/排序质量差异巨大：
  - BM25 召回 200 → 经 `_dedup_by_file` 每文件截断到 8，**排名序号（rank）被截断后失效**——原本第 9~200 名的 chunk 若其所在文件的前 8 名被保留，它们实际被丢弃，但保留的 chunk 其 `rank` 仍是截断前的全局 rank，**少文件文档第 1 名（rank=0）与大文档第 9 名（rank=8 但实际是文件内第 1）权重差距被放大**。
  - 向量召回 50 名、图谱/文件名召回各 ≤50 名，rank 上限不同。
- **影响**：BM25 的 rank 分布空间（0~199）与向量（0~49）不同，融合时 BM25 尾部项的 `1/(k+rank)` 会更小，但实际上 `_dedup_by_file` 之后 BM25 结果已经重排，**rank 已不是真实召回排名**。融合分不可解释、不可复现。
- **借鉴建议**：对标 **RAGatouille / ColBERT 的标准 RRF 实现**和 **Cohere Rerank 的 rank fusion**——先对各源结果做「分数归一化（min-max / z-score）」再融合，或对所有源统一用 `1/(k+rank)` 但 rank 必须是**每个源独立重排后的真实序号**。更稳妥的方案是直接采用 **LlamaIndex `FusionRetriever`** 的 `reciprocal_rank_fusion`，它对每个 retriever 的 top-k 做归一化 RRF，语义正确。

#### 缺陷 2 🟠 动态权重 vs 固定权重两套实现分支，行为不一致且难以测试

- **位置**：`search.py:200-210`（`if _use_dynamic_ranking(): ... else: _rrf_fusion(...)`）
- **根因**：`weighted_rrf_fusion`（ranking.py）和 `_rrf_fusion`（search.py）是两份几乎重复的实现，维护成本高；且 `_rrf_fusion` 固定用 `BM25_WEIGHT=0.5 / VECTOR_WEIGHT=0.5`，而动态版用 `get_dynamic_alpha` 返回的 `(vector, bm25)` 元组——**注意两处权重参数顺序相反**（`_rrf_fusion` 内 BM25 在前，动态版 `alpha_map` 返回 `(vector, bm25)` 但 `get_dynamic_alpha` 的 docstring 也是 `(vector_weight, bm25_weight)`），极易在使用/调试时搞反。
- **影响**：关闭 `RAG_DYNAMIC_RANKING` 后，四路召回权重退化回固定 0.5/0.5/0.5/max(0.5,0.5)，与默认行为完全不连续；两个开关组合产生 4 种融合行为，难回归测试。
- **借鉴建议**：统一为单一 `weighted_rrf_fusion`，通过权重参数注入（默认 `get_dynamic_alpha`），移除 `_rrf_fusion` 副本。对标 **Haystack `DocumentRanker` / `JoinDocuments`** 的单一入口设计。

#### 缺陷 3 🟡 RRF 常数 k=60 偏大，削弱排名差异

- **位置**：`config.py:138`（`RRF_K=60`）、`ranking.py:236`（`k: int = 60`）
- **根因**：RRF 常数 k 越大，排名靠前的项相对权重差距越小（第 1 名 vs 第 10 名：`1/61` vs `1/70`，差异仅 15%）。业界常用 k=60 是 Meta 原始论文值，但那是针对海量候选；对本文档集（召回 50~200），k=60 会过度平滑，削弱「排名第 1 应该显著优于第 10」的信号。
- **影响**：检索结果对排名不敏感，头部排序可能被 noise 项污染。
- **借鉴建议**：对标 **Weaviate / Vespa 的 hybrid fusion**，将 k 降到 20~30，或引入可配置的 `k` 并做离线召回率评测。

### 2.2 BM25 / FTS5 中文分词与检索质量

#### 缺陷 4 🔴 FTS5 双虚拟表（chunks_fts + chunks_fts_tri）一致性无法保证，存在孤儿/脏数据风险

- **位置**：`db.py:44-45`（两个 VIRTUAL TABLE 定义）、`chunks.py:31-50`（`add_chunks_batch` 逐条写两个 FTS）、`chunks.py:63-104`（`fts_search` 双表查询）
- **根因**：
  1. 两张 FTS 表（`unicode61` 词级 + `trigram` 三元组）都是**外部内容表**（virtual table 无 content= 挂靠，rowid 与 chunks.id 手动对齐），靠 `INSERT OR REPLACE INTO ... (rowid, content)` 手动维护。**FTS5 外部 content 表不自动同步**，任何一处遗漏写/删就会产生孤儿行。
  2. `delete_file`（files.py:210-214）显式逐个 `DELETE FROM chunks_fts WHERE rowid=?` 和 `chunks_fts_tri` 清理，但**依赖 `chunk_ids` 先查出来**；若历史数据因程序崩溃在 `add_chunks_batch` 事务提交前中断（`with conn:` 内多行），FTS 可能落盘而 chunks 未落盘（或反之）。
  3. 代码注释里已自曝「trigram 孤儿数据」「IntegrityError: constraint failed」问题（chunks.py:42-44），说明**历史上已发生过脏数据**，属「打补丁」而非根治。
- **影响**：检索结果可能包含「不属于任何 chunk」的 FTS 命中（JOIN chunks 时被过滤掉，但 rank 计算仍含脏行）；或漏检（FTS 未写入）。删除文档时若清理遗漏，产生孤儿向量/FTS 行，长期累积导致召回质量下降和磁盘膨胀。
- **借鉴建议**：对标 **Meilisearch / Tantivy** 的「单一索引 + 内置 tokenizer 管理」模型。SQLite 方案应优先考虑：
  - 改用**正常的 FTS5 内容表**（`CREATE VIRTUAL TABLE chunks_fts USING fts5(content, content='chunks', content_rowid='id', tokenize=...)`），让 FTS 自动跟随 chunks 增删；
  - 或放弃 trigram 双表，用 **jieba 搜索引擎模式（`jieba.cut_for_search`）** 单一索引解决子串匹配，避免双表同步（对标 **Elasticsearch 的 ik_max_word 单一 analyzer**）。

#### 缺陷 5 🟠 trigram 双表方案造成「一词双命中」，取分逻辑 `rank` 越小越优但两表 rank 量纲不同

- **位置**：`chunks.py:90-104`（trigram 合并）、`chunks.py:71`（主查询 `ORDER BY rank`）
- **根因**：`fts_search` 先查 `chunks_fts`（jieba 词级），再查 `chunks_fts_tri`（trigram 整句短语匹配）。两表 tokenizer 不同（unicode61 vs trigram），BM25 `rank` 绝对值不可横向比较。合并时 `if r["score"] < results[rid]["score"]: results[rid]["score"] = r["score"]` 直接取小值，**把两个不同统计口径的 BM25 分数混比**。
- **影响**：trigram 命中（整句短语）会覆盖主索引（词级）的 BM25 分，最终排序不稳定。且主查询 `ORDER BY rank LIMIT ?` 只取前 `limit` 条，trigram 再去补，**主索引把「大文档词频碾压」时，小文档靠 trigram 进来但分数被主索引主导**。
- **借鉴建议**：对标 **Elasticsearch 的 `bool` + `should` 多字段查询**，为两个索引分别计算独立归一化分后再加权合并，而非直接取 rank 较小值。

#### 缺陷 6 🟠 FTS 查询字符串存在 SQL 注入面（虽已转义，但通配符/列标记过滤不完整）

- **位置**：`tokenizer.py:84-107`（`_sanitize_fts_term`、`to_fts_query`）
- **根因**：`_sanitize_fts_term` 只剥离 `* ^ : { }` 和转义双引号，但 FTS5 还有特殊语法：`(` `)` `AND`/`OR`/`NOT` 关键字、`"` 短语、`-` 排除、数字列过滤 `col:...`（本表无多列，风险低，但 `:` 已剔）。更关键：`to_fts_query` 里 `OR` 拼接后，若 `segment()` 分词出来含 `"` 或特殊字符，`_sanitize_fts_term` 已处理双引号，但 **`OR` 本身作为用户输入被分词成独立 token 时**（英文查询 "or"），会被当作 FTS 逻辑操作符而非字面词。
- **影响**：恶意/异常 query（含 `(`、`NOT`、`NEAR` 等）可能导致 FTS 报错或语义执行，虽不会 SQL 注入（参数化），但会改变检索语义。
- **借鉴建议**：对标 **Whoosh 的 QueryParser 官方实现**，用完整的词元过滤/转义，并对 FTS5 语法关键词（AND/OR/NOT/NEAR）单独加引号。

### 2.3 ChromaDB 向量存储

#### 缺陷 7 🟠 HNSW 原生化持久化被「禁用」，属治标不治本，重启即丢索引

- **位置**：`chroma_store.py:35-49`（`_get_collection` 中 `hnsw:sync_threshold=1000000000`）
- **根因**：注释坦诚「Chroma 0.6.3 在 Windows 下 hnswlib 写 index.bin 损坏，重启 load_index 报 Cannot open header file」，于是把 `sync_threshold` 设成 10 亿来禁用原生化落盘。后果是索引**只存 chroma.sqlite3**，重启需从 sqlite 全量重建 HNSW。
- **影响**：数据量大时启动时间线性增长；纯靠 sqlite 存储向量（每向量 1024 维 float 存 sqlite）体积巨大、读写慢；且这是「规避 bug」而非「修复 bug」，一旦 Chroma 升级或换平台，行为反转。
- **借鉴建议**：对标 **Milvus / Qdrant** 的成熟向量存储，或至少升级/降级 ChromaDB 版本解决 hnswlib Windows 落盘 bug；短期可在 `ensure_synced` 之外增加「启动时异步后台重建 + 健康探针」。若要彻底摆脱，建议迁移到 **Qdrant（支持本地持久化、HNSW 稳定跨平台）**。

#### 缺陷 8 🟠 按行/按小批 upsert，无并发控制，入库时未做 max_batch_size 分片

- **位置**：`chroma_store.py:52-76`（`add` / `add_batch`）、`chunks.py:24-50`（`add_chunks_batch` 调用处）
- **根因**：
  1. `add_batch` 一次性 `col.upsert`，若 `rows` 超过 Chroma 内部限制（ChromaDB 已知 `max_batch_size` 默认 5461，超限会报错），**没有分片**，大文档（如机械手册 1585 chunk 虽未超，但批量重灌或全库补录 `ensure_synced` 时可能一次性上万条）会直接抛异常。
  2. `upsert` 无锁、无事务，若多线程/多进程同时写同一 collection，Chroma 的 sqlite 会有并发写冲突。
  3. `add_batch` 里的 `_unpack` 逐条解 pack、逐条 `tolist()`，效率低（大数组反复转 list）。
- **影响**：大批量入库（尤其 `ensure_synced` 补录）可能崩溃；并发入库可能损坏索引。
- **借鉴建议**：对标 **Qdrant 官方 client 的 `upload_collection`/分批 upsert**，实现 `max_batch_size` 分片 + 重试；向量直接用 `np.frombuffer` 一次解出，避免逐条 `struct.unpack + tolist`。

#### 缺陷 9 🟡 Chroma 元数据 `content[:500]` 截断，检索回填的内容被截断，影响 rerank 质量

- **位置**：`chroma_store.py:55、72`（`"content": content[:500]`）
- **根因**：写入 Chroma 时只存 content 前 500 字符作为 metadata，`search()` 也只回填这 500 字。但下游 `rerank`（SiliconFlow 取 `_text_of` 前 512 字）和 `_recover_exact_match`（用 content 做词边界匹配）都依赖完整/较多内容。长 chunk（如超大表格块，注释提到「导轨」被稀释到 1/4507）只回填前 500 字，**精确命中置顶、rerank 都可能找不到关键词**。
- **影响**：长 chunk 在向量召回后内容被截断，`search.py` 的 `_recover_exact_match`（依赖 content 命中型号）可能失效，rerank 输入信息不足。
- **借鉴建议**：对标 **LlamaIndex `VectorStoreIndex`** 的做法——向量存储只存 id，content 从主库（chunks 表）按 id 实时回填；不要重复存 content 到 Chroma metadata。

#### 缺陷 10 🟡 `_get_collection` 全局单例 + 无读写锁，异步环境下潜在竞态

- **位置**：`chroma_store.py:18-19`（`_client`/`_collection` 全局变量）、`search.py:_vector_search`
- **根因**：`_client`/`_collection` 是模块级全局，`search()` 是 `async` 函数却在同步线程里调用 `col.query`（Chroma 客户端是同步阻塞 API），在 FastAPI 事件循环里**同步阻塞**会卡住整个事件循环。
- **影响**：并发检索时 Chroma 查询阻塞 asyncio 事件循环，导致整个服务卡顿。
- **借鉴建议**：对标 **Qdrant async client / Milvus async**，检索路径用 `asyncio.to_thread` 或异步客户端包裹；`_get_collection` 加 `threading.Lock` 防双初始化。

### 2.4 SQLite 并发与连接模型

#### 缺陷 11 🟠 双连接隔离模型（contextvars + threading.local）存在潜在连接泄漏/串用风险

- **位置**：`db.py:139-165`（`_get_conn`）及 `search.py` 大量 `_get_conn()` 调用
- **根因**：`_get_conn` 优先级「contextvars → threading.local」。但：
  1. `_rerank_cache_db_ensure_table`/`_rerank_cache_db_set`（rerank.py:271-296）在 `async` 函数里直接 `_get_conn()`，若当前线程没有 contextvar 注入，会落到 `threading.local`——**uvicorn 线程池里的后台线程复用 `_local.conn`，跨请求/跨任务串用同一个连接**。
  2. `close_thread_conn` 只清 `_local.conn`，而 contextvar 连接的关闭依赖中间件显式调用 `reset_conn`，**若异常路径漏调 reset_conn，contextvar 连接泄漏**（contextvar 在当前 task 结束后不自动关闭 sqlite 连接）。
  3. `check_same_thread=False` + 连接在线程间共享，SQLite 连接对象非线程安全，并发操作同一连接可能损坏。
- **影响**：高并发下可能「database is locked」或连接泄漏；异步函数内同步 sqlite 阻塞事件循环。
- **借鉴建议**：对标 **SQLAlchemy 的 scoped_session / connection-per-request** 成熟模式：彻底用 `asyncio` + `aiosqlite`，或每请求显式短连接（`with` 块），移除 threading.local 持久连接。至少给 `_get_conn` 加「当前是否在 async 上下文」判断。

#### 缺陷 12 🟠 `fts_search` 的字符串拼接 `f"WHERE chunks_fts MATCH '{fts_query}'"` 未参数化，FTS 查询字符串可被注入

- **位置**：`chunks.py:71`（`f"WHERE chunks_fts MATCH '{fts_query}'"`）、`chunks.py:96`（`f"WHERE chunks_fts_tri MATCH '\"{safe_query}\"'"`）
- **根因**：FTS5 的 `MATCH` 右侧是字符串，不能像普通 SQL 一样用 `?` 参数化（SQLite 限制），因此只能拼接。虽然 `_sanitize_fts_term` 做了转义，但 `to_fts_query` 用 `OR` 拼接多个 `"..."`，若某分词词含单引号 `'`，会提前闭合 SQL 字符串字面量。
- **影响**：单引号/特殊字符 query 可导致 SQL 语法错误或（结合其他）注入。属 FTS5 的经典注入面。
- **借鉴建议**：对标 **SQLite 官方 FTS5 文档**推荐的「将 MATCH 值作为绑定参数传递」的变通方案（FTS5 实际上支持 `MATCH ?` 绑定）。务必用 `?` 占位，把整个 `fts_query` 作为参数传入，而非 f-string 拼接。

#### 缺陷 13 🟡 `add_chunks_batch` 用 `with conn:` 隐式事务，但 `conn.execute` 未提交前 FTS 与 chunks 非原子

- **位置**：`chunks.py:33-50`
- **根因**：`with conn:` 开启事务，但内部的 `INSERT INTO chunks`、两个 FTS `INSERT OR REPLACE` 是**三条独立语句**，SQLite 单个事务内是原子的（要么全提交），这点没问题。真正的问题是：**FTS5 的 `INSERT OR REPLACE` 在事务内虽回滚，但 chunk 的 `lastrowid` 若因并发自增错乱，FTS rowid 与 chunk id 会错位**。`+注释` 已提到用 `INSERT OR REPLACE` 覆盖残留 rowid，说明历史上有 rowid 错位。
- **影响**：极端并发下 FTS 索引指向错误 chunk，检索出错误内容。
- **借鉴建议**：对标 **外部 content FTS5 表**（`content='chunks', content_rowid='id'`），彻底消除手动 rowid 对齐，让 FTS 由 SQLite 自动维护。

#### 缺陷 14 🟡 `WAL` 模式开启但未设置 `synchronous` / 未做 checkpoint 管理，长写可能卡锁

- **位置**：`db.py:131`（`PRAGMA journal_mode=WAL`）
- **根因**：开了 WAL 但未设 `PRAGMA synchronous=NORMAL`（默认 FULL，写放大）、未管理 `wal_checkpoint`。批量入库（大量 chunk）时 WAL 文件持续增长，未 checkpoint 会导致读变慢、磁盘膨胀。
- **影响**：长时间运行后 WAL 文件过大，检索读性能下降。
- **借鉴建议**：对标 **SQLite 生产配置 checklist**，设置 `synchronous=NORMAL`、定期 `PRAGMA wal_checkpoint(TRUNCATE)`，`busy_timeout` 已设 5000ms 合理。

### 2.5 重排序质量与效率

#### 缺陷 15 🟠 rerank 三级降级链中，DeepSeek LLM 打分只取前 30 文档且 `top_n` 与候选数错位

- **位置**：`rerank.py:88-94`（`documents[:30]`）、`rerank.py:92`（`f"[{i}] {d[:400]}"`）
- **根因**：`rerank_with_deepseek` 只对 `candidates[:30]` 打分，但 `search.py` 传入的是 `top_k * RERANK_TOP_K_MULTIPLIER`（top_k=10 时 = 40）个候选，**第 31~40 名候选根本没被 DeepSeek 打分就被丢了**。且 `index` 与 `documents` 长度不一致时，`scores[i]` 越界（已用 `if i < len(scores) else 0.0` 兜底，但顺序错位）。
- **影响**：rerank 候选池被截断到 30，`RERANK_TOP_K_MULTIPLIER=4` 的设计意图（给 rerank 更大候选池）在 DeepSeek 兜底路径失效。
- **借鉴建议**：对标 **Cohere Rerank v3 / Jina Reranker 的 top_n 语义**，确保 `documents` 与打分循环严格对齐，并对 >30 候选做分批打分再合并。

#### 缺陷 16 🟠 rerank 结果级缓存 key 用 `(query, top_k, 候选id指纹)`，但 top_k 在调用点被放大，缓存命中率低

- **位置**：`rerank.py:205-214`（`cache_key = (query, top_k, fp)`）、`search.py:207-208`（`top_k=max(top_k * RERANK_TOP_K_MULTIPLIER, top_k)`）
- **根因**：`search()` 里 `rerank(query, merged, top_k=top_k*4)`，导致缓存 key 的 `top_k` 是放大后的值（40），但用户实际关心的 `SEARCH_TOP_K=10` 未入 key。同一 query 在不同 top_k 请求下产生多份缓存，且**缓存的是 top_k*4 的排序结果，最终 `merged[:top_k]` 只取前 10**，缓存粒度不合理。
- **影响**：缓存碎片化、命中率低；持久化缓存表 `rerank_cache` 膨胀。
- **借鉴建议**：对标 **Redis 缓存 key 设计**——先按固定候选池 rerank，再做用户 top_k 截断，缓存 key 只含 `(query, 候选指纹)`，top_k 不入 key。

#### 缺陷 17 🟡 `rerank_local` 的 TF-IDF 打分是「词频/文本长度」而非真 TF-IDF，无 IDF 项

- **位置**：`rerank.py:149-185`（`rerank_local`）
- **根因**：`score += count / text_len * 1000`，只算 `count/text_len`（词频/长度），**没有 IDF（逆文档频率）**——高频词（如「的」「是」虽被 jieba 停用词过滤，但「系统」「参数」等高频业务词）会错误得高分。注释说「归一化 TF-IDF」但实际无 IDF。
- **影响**：降级到本地重排时，排序质量差，高频噪声词主导。
- **借鉴建议**：对标 **sklearn `TfidfVectorizer`** 的真 TF-IDF，或至少对候选集内计算 IDF（`log(1 + N/(1+df))`）。

#### 缺陷 18 🟠 rerank 用 `score` 主字段覆盖融合分，与「置顶保序」策略冲突，且 `_pre_rerank_score` 保存后无消费方

- **位置**：`rerank.py:58-63、118-120、171-174`（`r["score"] = round(...)`）、`search.py:_recover_exact_match`
- **根因**：rerank 把相关性分写入 `score` 主字段。但 `_recover_exact_match` 用「置顶保序」（不加减分，只调顺序）来保护精确命中——**这二者设计哲学冲突**：rerank 已把 score 改成 [0,1] 的相关性，`_recover_exact_match` 的 `_priority` 又是离散 0/1/2/3，最后 `sort(key=_priority)` 用离散等级覆盖，但 `score` 字段保留的是 rerank 分，**返回给前端的 score 与最终排序的优先级不一致**，前端按 score 排序会得到不同结果。
- **影响**：score 字段含义混乱（RRF 分 → rerank 分 → 又被离散优先级排序覆盖），前端展示/排序不可信。
- **借鉴建议**：对标 **RAG管道最佳实践**——明确分离「ranking score（展示用）」「排序依据（内部用）」，rerank 后不应再有多层离散重排；精确命中保护改为「在 rerank 前注入高权重候选」而非「rerank 后硬置顶」。

### 2.6 图谱召回准确性

#### 缺陷 19 🟠 图谱召回 score = `mention_count × 实体类型权重`，mention_count 是累加值且无归一化，跨实体不可比

- **位置**：`graph_recall.py:96-118`（`_entity_to_chunks`、`graph_recall`）、`entities.py:119-130`（`add_entity_chunk` 累加）
- **根因**：`add_entity_chunk` 每次 `ON CONFLICT ... mention_count = mention_count + excluded.mention_count` **无限累加**。同一实体在不同 chunk 的 mention_count 会随重复入库线性增长，且不同实体被提及的基数不同（热门实体如「不锈钢」mention_count 天然远高于冷门型号），`score = mention_count × weight` 后，**图谱召回结果基本被高频实体主导**，冷门但精确的型号（weight 高）反而排不到前面（因为 mention_count 小）。
- **影响**：图谱召回无法体现「精确型号 > 泛化材料」的设计意图，`_entity_type_weight` 被 mention_count 的量级差异淹没。
- **借鉴建议**：对标 **Neo4j 图检索的 PageRank / 节点重要性**，score 应使用「归一化 mention_count（如 per-file 相对频次）+ 类型权重」，或直接按实体精确度（standard/connector 类）优先于材料类做分层召回，而不是乘法混合。

#### 缺陷 20 🟠 `_neighbor_chunks` 一跳邻居扩展「按边界遍历」但无方向/去环控制，可能引入无关 chunk

- **位置**：`graph_recall.py:72-95`（`_neighbor_chunks`）
- **根因**：`get_entity_relations(ent_id, rel_types=[spec/uses_standard/compatible_process])` 返回该实体作为 source 或 target 的所有边，邻居取「另一端」。但对高连接度实体（如「不锈钢」），一跳邻居可能几十个，遍历 `neighbors[:30]` 后每个再 `get_entity_chunks(nb_id)` 且 `len(results) >= limit` 就返回——**limit=8 太小，可能只采到前几个邻居的 chunk，而这些邻居本身可能是噪音**。
- **影响**：邻居扩展的召回质量依赖「邻居恰好相关」，无相关性打分，纯靠 mention_count，容易把无关共现混入。
- **借鉴建议**：对标 **LightRAG / GraphRAG 的关系遍历**，一跳邻居要对边权 `weight`（`entity_relations.weight` 是累加的，本身可作为相关性信号）做排序/阈值，而非按 id 顺序取前 30。

#### 缺陷 21 🟡 图谱召回 `_entity_type_weight` 的 `param=0.8` 高于 `material=0.7`，但 `detect_query_entities` 对 param 的识别依赖词典，可能误召回

- **位置**：`graph_recall.py:160-168`（`_entity_type_weight`）、`graph_recall.py:32-35`（`detect_query_entities` 的 nav_types）
- **根因**：`param`（参数名）被纳入可导航类型且权重 0.8，但参数名（如「阻抗」「耐压」）是高频通用词，`entity_extractor.extract_rule` 若对参数名识别过宽，会大量命中 param 实体，图谱召回被参数名簇拥。
- **影响**：query 含通用参数词时，图谱召回返回大量低相关 chunk，污染融合候选。
- **借鉴建议**：对标 **实体链接（Entity Linking）的置信度阈值**，对 param/process 等泛化类型设召回阈值或降权，精确导航只保留 standard/connector。

### 2.7 其他工程问题

#### 缺陷 22 🟡 `_last_profile` 是模块级全局 dict，并发检索时会互相覆盖，profile 不可信

- **位置**：`search.py:22-29`（`_last_profile`、`get_last_profile`）
- **根因**：`search()` 是并发执行的异步函数，`_last_profile` 全局变量在并发下被后完成的请求覆盖，`get_last_profile()` 返回的是「最后一个完成的 query」的 profile，非当前关注 query 的。
- **影响**：性能诊断拿到的耗时分布可能张冠李戴。
- **借鉴建议**：对标 **OpenTelemetry 的 Span**，profile 应随请求返回或写入结构化日志/指标系统，而非全局变量。

#### 缺陷 23 🟡 大量 `except Exception` 静默降级 + `logger.warning/debug`，失败被掩盖，难排查

- **位置**：全篇多处（`search.py:305、314、355`、`rerank.py` 多处、`chroma_store.py` 多处）
- **根因**：几乎所有外部依赖（Chroma、SiliconFlow、DeepSeek、jieba、图谱）的异常都被 `except Exception` 吞掉降级为 `[]` 或 `debug` 日志。降级策略本身合理（保证服务可用），但**无告警、无降级计数、无 metrics**，某一路召回长期失败不会被发现。
- **影响**：召回源静默失效（如 Chroma 挂了，只有 BM25 在工作），检索质量劣化但无人知晓。
- **借鉴建议**：对标 **Prometheus metrics / Sentry**，为每次降级记录 counter/metric，超阈值告警；关键路径（Chroma、rerank）失败应提升日志级别。

#### 缺陷 24 🟡 `detect_exact_models` 的正则 `_MODEL_PATTERNS` 会误匹配普通英文缩写/数字（如 `AR1`、`LSW1`）

- **位置**：`ranking.py:68-80`（`_MODEL_PATTERNS`）
- **根因**：`r"\b[a-z]{2,5}[\s-]?\d{2,6}([\s-]?\w+)?\b"` 会匹配大量非型号的字符串（如「section 20」→ 不会，但「form 10k」「page 123」会），而 `r"\b[a-z]{2,5}\b"` 类模式不设边界会误伤普通英文词。`_MODEL_PATTERNS` 里 `r"(?<![a-z0-9])fakra"` 无正向边界，会匹配 `fakradaptor` 的前缀（虽然后续 `detect_exact_models` 去子串只处理 mini-fakra）。
- **影响**：正常查询里的英文缩写被误判为「精确型号」，触发 `_recover_exact_match` 硬置顶，错误地把无关 chunk 提到最前。
- **借鉴建议**：对标 **Stanford NER / 规则引擎的最佳实践**，型号正则需配合白名单/词典约束，避免裸正则误报。
