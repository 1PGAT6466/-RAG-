# 前端交互借鉴与增强方案（三项）

> 版本：v1（2026-09-08）
> 状态：**待审**（未动任何代码）
> 定位：对标成熟 RAG/知识库产品（Dify、RAGFlow、Perplexity、Coze 知识库），
> 从中**只借交互模式，不照搬产品形态**，落到伏羲「工业精工」设计体系内。

---

## 0. 一句话结论

三项里：
- **第 3 项（对话操作条）** 是你拍板「反馈要直接反哺检索排序」的核心，也是**工作量最大、唯一触碰检索链后端**的一项。
- **第 1 项（检索命中测试面板）** 后端起手成本低（复用已有 `search()` 的 profile 打点），价值最高。
- **第 2 项（文档↔引用双向联动）** 需要引进「chunk 被引用关系」的新数据基础，工作量大、收益偏「锦上添花」，建议**降级或延后**。

**建议落地顺序**：第 1 项 → 第 3 项的前端部分 → 第 3 项的反馈反哺（单独评估）→ 第 2 项（可选）。

## 1. 检索命中测试面板（对标 Dify 知识库「召回测试 / Hit Testing」）

### 1.1 借鉴什么
Dify 知识库提供「召回测试」：输入 query，实时看命中了哪些 chunk、每个 chunk 的相似度/排序分。这是知识库产品的**核心可观测能力**——用户/管理员能判断「我的 knowledge base 到底有没有吃进我要的内容」。

### 1.2 现状（已摸清，关键利好）
`src/retrieval/search.py` 已经埋了阶段级 profile 打点，但**只对内**（`_last_profile` 全局变量 + `get_last_profile()`），没有对外接口，也没有存「每路召回明细」。

好消息是检索链本身已经高度结构化，改造点很清晰：

| 召回路 | 函数 | 明细可提取性 |
|--------|------|------------|
| BM25（FTS5） | `_bm25_search` → `fts_search` | ✅ score + source |
| 向量 | `_vector_search` → chroma / sqlite | ✅ score + source |
| 图谱 | `_graph_recall` → `graph_recall` | ✅ 有 source 标记 |
| 文件名召回 | `_filename_recall` | ✅ 有 `_fn_hits` / source=filename |
| 融合/rerank | `weighted_rrf_fusion` → `rerank` | ✅ 有 `_rerank_score` / `_pre_rerank_score` |

**核心痛点**：现在的 `search()` 是「黑盒」，外部只能拿到最终 top_k 的 `[{id, content, file_name, score, source}]`，看不到「某个 chunk 是 BM25 第一、向量第三、rerank 后掉到第五」的全过程。

### 1.3 改造方案

**后端（新增调试接口，不改主检索语义）**：

新增 `GET/POST /api/search/debug`，复用 `search()` 但开启「明细采集」：
- 让 `search()` 返回时，除了最终结果，附带 `stages`（已有）**以及每路召回的原始明细**（可选，通过参数控制是否采集，避免污染正常检索路径）。
- 关键设计决策：**默认关闭明细采集**，只有 debug 接口 `collect_detail=True` 时才记录每路召回，避免正常检索多付内存/序列化成本。

接口返回结构：
```json
{
  "status": "ok",
  "data": {
    "route": "exact|material|semantic|general",
    "stages": { "bm25": 12.3, "vector": 8.1, "graph": 0.4, "rerank": 154.2 },
    "recalls": {
      "bm25":   [{ "id": 123, "file_name": "x", "score": 12.5, "chunk_index": 4 }],
      "vector": [{ "id": 999, "file_name": "y", "score": 0.82, "chunk_index": 0 }],
      "graph":  [...],
      "filename": [...]
    },
    "merged": [{ ... chunk, "score": 0.9, "_rerank_score": 0.75, "_pre_rerank_score": 3.2 }]
  }
}
```

**前端（新增「检索调试」视图/面板）**：
- 一个输入框 + 一个结果表格/时间线，按「召回路 → 融合 → rerank → 最终」分层展示排名变化。
- 可复用 `GraphView` 既有的 D3/表格风格，但建议**先做成轻量表格/列表**（对齐工业精工，不引入复杂可视化），后续再考虑 Sankey/瀑布图。

### 1.4 风险与依赖
- **风险低**：新增接口，不改 `search()` 主语义（明细采集走独立参数分支）。
- **依赖**：`search()` 内部需把「每路召回结果」暂存并透传出来。当前 `search()` 是单函数串联，需要**小幅重构**——把四路召回的返回值在函数内先收集到一个 `_recalls` 结构，命中 `collect_detail` 时一并返回。
- **不碰**：融合/rerank 逻辑本身。

## 2. 文档 ↔ 引用双向联动（对标 Perplexity 引用溯源）

### 2.1 借鉴什么
Perplexity/Dify 的信任核心是「答案每个断言都能追溯到原文」。伏羲已做到**单向**（对话引用卡片 → 跳文档详情 + `?chunk=` 锚点），缺**反向**（在文档详情里看「这段被哪些对话/查询引用过」）。

### 2.2 现状与缺口
现有 `goToSource(s)` 只做「引用 → 文档」。反向需要「chunk → 历史查询/对话」的映射，**目前没有任何数据基础**：
- `conversation_messages.sources` 存的是 JSON 字符串（`[{ref, file_name, chunk_index, ...}]`），但**没有存 chunk_id**（当前 sources 里实际上不带 `id`，只有 `file_id` + `chunk_index`）。
- 要反向联动，必须先让 `sources` 落库时带上 `chunk_id`，否则只能按 `file_id + chunk_index` 反查，脆弱。

### 2.3 改造方案
1. **后端**：`generate_stream` 产出的 sources 里补 `chunk_id` 字段（检索结果里本来就有 `id`，只是落库时没带）。新增 `GET /api/chunks/{id}/refs` 反向查询接口（扫 `conversation_messages.sources`，但更建议新增一张 `chunk_references` 关联表，写入时同步）。
2. **前端**：`DocumentDetail.vue` 的每个 chunk 加「被引用 N 次」角标，点击展开历史引用/查询。

### 2.4 判断
**建议延后或降级**。理由：
- 收益是「可观测性/信任感」的提升，但对**检索质量、检索效率**没有直接帮助。
- 需要新增一张关联表 + 改造落库链路 + 前端两处联动，工作量不小。
- 若你真要「反馈反哺」，更该把精力放在第 3 项，而不是第 2 项。

## 3. 对话操作条（重新生成 / 复制 / 点赞点踩反馈）

### 3.1 借鉴什么
ChatGPT / Perplexity / Dify 对话的 assistant 消息下方都有一排操作按钮：重新生成、复制、点赞、点踩。这是对话产品的**标配**。

伏羲现状：assistant 消息**完全没有操作条**，只有「参考来源」列表和脚注跳转。

### 3.2 你已拍板的决策
> **「反馈要直接反哺检索排序」**

这是一个**关键的方向性决策**，我必须先诚实告诉你它带来的架构复杂度，避免方案把你带偏。

### 3.3 ⚠️ 技术真相：点踩「直接降权」在伏羲融合架构下并不简单

伏羲的检索是「多路召回 → RRF 融合 → rerank 精排 → 精确命中置顶」四段式。一个 chunk 落点踩，要在**哪个环节**降权，效果和风险完全不同：

| 介入环节 | 做法 | 效果 | 风险 |
|---------|------|------|------|
| **A. rerank 前置过滤** | 点踩较多的 chunk 直接从候选池剔除 | 彻底、干净 | 误伤：点踩可能是因为「答案措辞差」而非「chunk 无关」，错杀以后再也搜不到 |
| **B. RRF 融合分惩罚** | 融合阶段对点踩 chunk 乘惩罚系数 | 温和、可逆 | 需在 `weighted_rrf_fusion` 里按 chunk_id 查惩罚表，增加一次查询 |
| **C. rerank 后重排惩罚** | rerank 分出来后，对点踩 chunk 扣分再排序 | 最贴近「排序」语义 | 与 `_recover_exact_match` 置顶逻辑可能打架（精确型号命中 vs 点踩惩罚谁优先？） |
| **D. 文档权威分惩罚（authority）** | 点踩 aggregated 到**文件级**，降低文件 authority | 符合伏羲已有 authority 机制 | 粒度太粗（一个文件里可能只有 1 个坏 chunk，整篇降权威会误伤好 chunk） |

**我的建议（诚实）**：**先落 D 的「文件级」或 B 的「chunk 级惩罚」，但用「指数衰减 + 时间窗口 + 阈值」而非「一次点踩就永久降权」**。理由：
- 单个用户的一次点踩信号噪声很大，直接硬降权会越用越差（尤其伏羲是**单用户/小团队**场景，样本量小，信号→权重放大要克制）。
- 必须有「衰减」和「撤销」，否则点错一次就永久损伤检索。

### 3.4 建议的落地设计（分两阶段，先轻后重）

#### 阶段一（本轮可做，低风险）：操作条 UI + 反馈落库
- **前端**：assistant 消息下方加操作条：`重新生成` / `复制` / `👍` / `👎`。
  - 「重新生成」：复用当前 query + 同 mode + 同 history，重新调一次（注意：要去掉上一条 assistant 消息，或 append 新的一条）。
  - 「复制」：`navigator.clipboard` 复制纯文本答案（不是 html）。
  - 「👍/👎」：点击后调 `POST /api/feedback`，落库。
- **后端**：新增 `feedback` 表 + `POST /api/feedback`（记录 `user_id / message_id / chunk_ids / kind(up|down) / query`）+ 可选 `DELETE /api/feedback`（撤销）。

#### 阶段二（反馈反哺，需单独评审）：把 feedback 接入检索
- 在 `search()` 的**融合阶段（B）或 rerank 后（C）** 加惩罚，具体环节 + 衰减策略**需单独出一个评审文档**，因为：
  1. 涉及检索链核心，回归风险高（167 个测试里有大量检索断言）。
  2. 「点踩降权」与「精确命中置顶」「authority 置顶」的**优先级冲突规则**需要明确定义。
  3. 衰减/阈值/时间窗口几个超参数需要你定（或先给默认值跑一段时间再调）。

### 3.5 风险
- **阶段一**：低风险，纯新增前端 + 新增表，不碰检索链。
- **阶段二**：**中高风险**，触碰 `search.py` 核心链路，需要严格回归 + 单测补充。

## 5. 需要你补充拍板的 3 个问题

1. **执行范围**：是否同意「本轮只做 第 1 项 + 第 3 项阶段一」，第 3 项阶段二和第 2 项延后？

2. **反馈反哺的介入环节**（若你坚持阶段二尽快做）：你倾向上面 A/B/C/D 哪一档？
   我的建议是 **B（chunk 级融合惩罚）+ 指数衰减 + 阈值**，最平衡。但你若想要「简单粗暴见效快」，可选 **D（文件级 authority 降权）**，代码量最小。

3. **「重新生成」的语义**：是「覆盖当前这条 assistant 消息」，还是「新增一条**重新回答**的消息」？
   - 覆盖：界面干净，但丢失之前的回答（除非也存历史）。
   - 新增：能对比两次回答，但消息列表会变长。
   我建议**覆盖 + 可撤销**（点踩/点赞已落库，重生成前不丢反馈）。
