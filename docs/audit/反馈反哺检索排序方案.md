> 版本：v1（2026-09-08）
> 状态：**待审**（评审通过后才落代码）
> 前置：阶段一已完成（feedback 表 + `chunk_penalty_stats` + 对话操作条 + 落库/撤销）

---

## 0. 目标与一句话结论

把用户的「点踩」反馈，以**温和、可逆、有衰减**的方式作用到检索排序，让「被多次点踩的 chunk」在后续检索中适度降权，又不至于因单次误点/噪声而永久损伤检索。

**推荐方案：B 方案（chunk 级 RRF 融合分惩罚）+ 指数衰减 + 阈值门槛。**

---

## 1. 为什么是「B 方案」而不是其他

回顾四档介入环节（已在前一方案文档 3.3 列过），本节给出**明确取舍理由**：

| 环节 | 结论 | 理由 |
|------|------|------|
| A. rerank 前置过滤（剔除） | ❌ 否 | 「点踩」≠「chunk 无关」，可能是「答案措辞差」「用户没看懂」；硬剔除有不可逆误伤 |
| **B. RRF 融合分惩罚** | ✅ **采用** | 在融合阶段对点踩 chunk 的 RRF 分乘惩罚因子，温和、可逆、不与 rerank 覆盖冲突（rerank 前就压低，rerank 会保留相对劣势） |
| C. rerank 后重排惩罚 | ⚠️ 备选 | 与 `_recover_exact_match` 置顶逻辑冲突风险高（精确型号命中 vs 点踩惩罚谁优先？需额外定义优先级） |
| D. 文件级 authority 降权 | 参考/可选 | 粒度太粗（一篇文档里 1 个坏 chunk 会误伤同文档的其他好 chunk），仅作兜底不考虑 |

**关键：B 的惩罚作用在 RRF 融合分，而非 rerank 分。** 这样即使 rerank（SiliconFlow BGE）把它的语义分打得高，融合阶段的「历史点踩」劣势仍会传递下去（rerank 的输入顺序/候选本身就被融合分影响）。

## 2. 惩罚公式与衰减策略

### 2.1 核心公式

对某个 chunk `cid`，定义其**点踩惩罚因子** `penalty(cid) ∈ [0, 1]`：

```
penalty(cid) = 1 / (1 + α · down_effective(cid))
```

其中：
- `down_effective(cid)` = 该 chunk 的「有效点踩数」= 按时间衰减累加的加权点踩次数
- `α` = 强度系数（默认 `0.5`，可配 `RAG_FEEDBACK_PENALTY_ALPHA`）

**作用方式**：在 `weighted_rrf_fusion` / `_rrf_fusion` 计算完某个 chunk 的 RRF 融合分 `score` 后，乘以 `penalty(cid)`：

```
score_final(cid) = score(cid) × penalty(cid)
```

### 2.2 指数衰减（时间窗口）

单次点踩不能永久生效，否则一次误点永久降低权重。用**半衰期衰减**：

```
down_effective(cid) = Σ over 每次点踩  exp(-ln2 · Δt / T_half)
```

- `Δt` = 距当前时间的时长
- `T_half` = 半衰期（默认 `7 天` = 7×86400 秒，可配 `RAG_FEEDBACK_HALF_LIFE_DAYS`）
- 物理含义：7 天前的一次点踩，其影响衰减为现在的 1/2；14 天前衰减为 1/4。

### 2.3 阈值门槛（防噪声）

单次点踩不生效，只有「有效点踩数」超过阈值才开始惩罚：

```
if down_effective(cid) < THRESHOLD:  penalty = 1.0（不惩罚）
```

- `THRESHOLD` 默认 `1.0`（即 ≥1 次才生效，但配合半衰期让单次点踩影响很小）
- 更强的抗噪：把 THRESHOLD 提到 `2.0`（≥2 次点踩才惩罚），适配「伏羲是单用户/小团队、样本量小」的现实——**建议默认 2.0**。

### 2.4 点赞的反向补偿（可选，默认不做）

为对偶，点赞可做「加权重置」：若某 chunk 既有点踩也有点赞，净效果 = 点踩惩罚 × (1 + 点赞因子)。**阶段二先不做点赞反哺**（避免双向反馈叠加引入新的跷跷板），只做点踩惩罚；点赞仅落库供未来分析。

## 3. 接入点与数据流

### 3.1 数据加载（每请求，但带缓存）

检索是高频路径，不能每次请求都全表扫 `feedback` 表。设计：

```
get_chunk_penalties(chunk_ids: set[int]) -> dict[int, float]
```

- **实现**：读 `feedback` 表 `kind='down'` 的记录，解析 `chunk_ids`，按 chunk 聚合 + 时间衰减，返回 `{chunk_id: penalty}`
- **缓存**：进程级 TTL 缓存（如 60s），因为反馈写入频率远低于检索频率，无需每次请求实时读全表。反馈新增/删除时主动失效缓存（调 `remove_feedback`/`add_feedback` 时清缓存）。
- **只查候选集合**：`search()` 在融合阶段拿到的候选 chunk id 集合有限（≤200），只对这有限集合查惩罚，避免全表扫描。

### 3.2 插入位置（精确）

在 `search()` 的第 4 步「融合」之后、第 4.5 步「精确命中置顶」之前：

```
merged = weighted_rrf_fusion(...)   # 或 _rrf_fusion
merged = _apply_feedback_penalty(merged, query)   # ← 新增：只乘 RRF 分，不改详情
merged = post_rank(query, merged)   # （原逻辑，若走动态分支）
```

但**注意**：`post_rank` 目前只补 category 字段不做分数加法（见注释），所以惩罚放在 `post_rank` 前后均可。为了清晰，放在**融合函数返回后立刻**、`post_rank` 之前。

### 3.3 与 rerank / 置顶的关系（优先级冲突规则）

这是评审的重点，必须明确：

1. **融合惩罚先于 rerank**：融合分被惩罚后，rerank 仍会基于「被惩罚后的候选」做语义精排。惩罚不会丢失，但语义极强相关的 chunk 仍有机会靠 rerank 分回升——这是**可接受**的（点踩≠绝对封杀，语义强相关仍可召回）。

2. **惩罚 vs 精确型号置顶（`_recover_exact_match`）**：
   - 精确型号命中是「硬事实」，理论上不该被点踩推翻。
   - 但若用户明确点踩了某个含精确型号的 chunk（如「这个型号参数是错的」），惩罚应能压过置顶。
   - **规则**：`_recover_exact_match` 是「置顶保序」（不改分，只调顺序，优先级离散 3/2/1/0），而惩罚是「改分」。二者作用域不同——惩罚已经在融合分上生效，置顶逻辑后续会再把「优先级 3 的精确命中」提到前面。
   - **决策**：**保留 `_recover_exact_match` 的置顶优先**（硬事实可信），但若该 chunk 的有效点踩数 ≥ `RAG_FEEDBACK_HARD_DOWN`（默认 3，表示「多人/多次明确反对」），则**穿透置顶**——即惩罚到「不再给它置顶优先级」。这样既保护硬事实，又让强烈负面反馈能纠正错误硬事实。

3. **惩罚 vs authority 置顶**：同理，authority 高的文档不应被一次点踩压过；只有有效点踩 ≥ 硬阈值才穿透。

## 4. 配置项（新增到 config.py + .env）

| 配置键 | 默认值 | 含义 |
|--------|--------|------|
| `RAG_FEEDBACK_ENABLE` | `"0"` | 总开关（阶段二实现后默认先关，灰度） |
| `RAG_FEEDBACK_PENALTY_ALPHA` | `0.5` | 惩罚强度系数 α |
| `RAG_FEEDBACK_HALF_LIFE_DAYS` | `7` | 点踩半衰期（天） |
| `RAG_FEEDBACK_THRESHOLD` | `2.0` | 生效阈值（有效点踩 ≥ 此值才惩罚） |
| `RAG_FEEDBACK_HARD_DOWN` | `3` | 硬阈值（≥ 此值穿透精确型号/authority 置顶） |

**默认 `RAG_FEEDBACK_ENABLE="0"`**：阶段二落地后先不启用，等你确认行为符合预期后再改 `1` 灰度。这也是「可回退」的保障——关掉开关即完全退化为现状。

## 5. 回归风险与测试计划

### 5.1 风险点

- **触碰 `search()` 核心**：融合后加一步，需确保 `collect_detail=False` 时行为不变（`RAG_FEEDBACK_ENABLE=0` 时 `_apply_feedback_penalty` 直接 return 原列表）。
- **`weighted_rrf_fusion` 的 score 已四舍五入到 6 位**（`round(score, 6)`），惩罚乘在这个值上，量纲无问题。
- **性能**：每请求读 feedback 表 → 用 TTL 缓存 + 只查候选集合，避免全表扫描。

### 5.2 测试计划

1. **单测**：`chunk_penalty_stats` 已存在，补 `get_chunk_penalties`（含时间衰减）的单测：给定点踩记录+时间戳，验证半衰期衰减和阈值门槛。
2. **回归**：`RAG_FEEDBACK_ENABLE=0` 时，全量检索测试必须与现状完全一致（0 变化）。
3. **行为验证**（需先灌回测试文档）：点踩某 chunk → 检索同 query → 该 chunk 排名下降；撤销点踩 → 恢复。
