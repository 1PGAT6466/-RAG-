## §1 登录与认证



| 项    | 内容                                                                                                                                 |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 现状   | `src/api/auth.py` + `src/auth/`（JWT 24h、登录 IP 限流 `rate_limit.py`）；前端 `LoginView.vue`                                               |
| 常见问题 | 登录偶尔慢（LLM 无关，通常是限流误判 / DB 锁）；token 过期前端无自动刷新，跳回登录但会话丢失                                                                             |
| 根因   | `rate_limit.py` 若用 SQLite 存储计数则高并发下有锁竞争；前端无 401 全局拦截                                                                               |
| 优化步骤 | ① 限流计数改内存 + 定期落库（单机内网足够），消除 DB 写锁；② 前端 axios 拦截 401 → 弹提示并清理本地 token（`stores/auth.js`），而不是白屏；③ `JWT_EXPIRY_HOURS` 与登录保持策略明确（如 7 天） |
| 调试方法 | 压测登录接口看 429/503；`logs/*.json` 按 `path=/api/auth/login` + `status_code` 过滤查限流命中；前端 Network 面板看 401 时序                               |
| 验收指标 | 登录 p95 < 300ms；并发 20 登录无 429 误伤；token 过期跳登录不丢会话数据                                                                                  |

## §2 文档管理

### 2.1 文档列表（重点：无分页全量加载）



| 项    | 内容                                                                                                                                                                                                                                                                                                                         |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现状   | `src/storage/files.py::list_files` → `SELECT * FROM files ORDER BY updated_at DESC` **无 LIMIT**；`list_files_with_entities` 在此基础上**逐文件查询实体（N+1）**；前端 `DocumentsView.vue` 一次性 `el-table` 渲染全部，过滤在客户端                                                                                                                         |
| 问题   | 文件数 >300 后列表明显变慢；>1000 后接口 + 渲染双重卡顿                                                                                                                                                                                                                                                                                        |
| 根因   | ① 后端全量 SELECT \*（含 summary/tags 大字段）；② N+1 实体查询；③ 前端无虚拟滚动 / 分页                                                                                                                                                                                                                                                             |
| 优化步骤 | ① 后端：`list_files` 改**服务端分页**（`page/page_size` + `LIMIT/OFFSET`，列表接口只查 `id,name,ext,category,folder,chunk_count,size,updated_at` 轻量列，summary/tags 按需进详情接口）；② `list_files_with_entities` 用一条 `JOIN` 或 `IN` 批量查询替换 N+1；③ 前端：`el-table` 开 `v-loading` + 分页器（或 500 条内继续全量 + 前端过滤，>500 强制分页）；④ 列表接口加 Redis / 进程内 30s 缓存（文件变更时失效） |
| 调试方法 | 后端：`sqlite3 data/rag.db "EXPLAIN QUERY PLAN SELECT * FROM files ORDER BY updated_at DESC"` 看全表扫描；计时接口：`curl -w "%{time_total}"`；前端：Performance 面板看 "接口等待 vs 渲染" 占比                                                                                                                                                         |
| 验收指标 | 1000 文件时列表接口 p95 < 300ms；页面首屏可交互 < 1s；内存无整表驻留                                                                                                                                                                                                                                                                              |

### 2.2 上传（重点：整文件进内存 + 后台线程）



| 项    | 内容                                                                                                                                                                                                                                                                                                                                 |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现状   | `api/documents.py::api_upload` 先把**整个文件读进&#x20;**`bytearray`（上限 200MB），同步写 SeedDMS，再 `_spawn_vectorize` 开**裸线程**调 `import_service.import_documents`；`_vectorize_jobs` 是**内存 dict**（重启丢映射，前端查不到进度）                                                                                                                                  |
| 问题   | 大文件上传时服务内存瞬时暴涨；多文件并发上传内存叠加；上传接口虽快返回但后台任务无重试、重启后进度丢失                                                                                                                                                                                                                                                                                |
| 根因   | ① 整文件驻留内存；② 后台线程无任务队列 / 重试（同 P20）；③ 进度映射在内存                                                                                                                                                                                                                                                                                        |
| 优化步骤 | ① 上传改**流式落盘**：`UploadFile` 分块写临时文件（`8MB` 块），校验大小后传 SeedDMS，避免整文件驻留（`MAX_UPLOAD_SIZE_MB` 保留做硬限）；② `_spawn_vectorize` 改走 01 文档 L2 的**持久化任务队列**（重试 + 重启恢复），`_vectorize_jobs` 落 SQLite 表 `upload_jobs(dms_doc_id, task_id, status, error)`；③ 上传进度：前端轮询 `upload/{task_id}/progress` 已有，后端确保 task 状态实时持久化；④ 大文件提示 "预计耗时"（按大小估算，避免用户以为卡死） |
| 调试方法 | 上传 50MB 文件观察任务管理器内存曲线；`logs/*.json` 按 task\_id 过滤查 Stage 耗时；断网重传验证重试                                                                                                                                                                                                                                                               |
| 验收指标 | 100MB 上传峰值内存 < 300MB；并发 5 个 20MB 上传不 OOM；任务失败自动重试 ≤3 次；重启后任务续跑、前端进度不丢                                                                                                                                                                                                                                                              |

### 2.3 文档详情 / Markdown 预览



| 项    | 内容                                                                                                                                          |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 现状   | `GET /api/documents/{id}` + `/markdown`（`markdown_render.py`）；`DocumentDetail.vue`                                                          |
| 问题   | 详情页打开慢通常不是接口慢，而是**图片懒加载缺失**（可读模式 `![[图]]` 全量加载）；chunk 列表无分页时大文档 DOM 爆炸                                                                      |
| 优化步骤 | ① 前端 `DocumentDetail.vue`：chunk 列表**按需渲染**（IntersectionObserver 或分页）；② markdown 图片加 `loading="lazy"`；③ `/markdown` 接口返回前截断超大文档（>2MB 提示分段查看） |
| 验收指标 | 2000 chunk 文档详情页滚动流畅（FPS ≥ 50）；图片首屏外不加载                                                                                                     |

## §3 检索与调试面板



| 项    | 内容                                                                                                                                                                                                                                                                                                                                                                  |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现状   | `api/search.py` → `search()`：四路召回**串行**（BM25→向量→图谱→文件名）；rerank 远程无缓存；`/api/search/debug` 已有四路明细面板（`DebugView.vue`）                                                                                                                                                                                                                                                  |
| 问题   | 单次检索延迟 = 串行四路 + rerank 远程，典型 1\~3s；SiliconFlow 抖动时 rerank 超时拖垮整体                                                                                                                                                                                                                                                                                                    |
| 优化步骤 | ① **四路召回并行**：`search.py` 用 `asyncio.gather`（BM25 / 向量 / 图谱 / 文件名互不依赖），预计省 30\~50% 召回时间；② **rerank 缓存**：新增表 `rerank_cache(query_hash, chunk_id, score, created_at)`，命中直接跳过远程（热门查询命中率 >50%）；③ rerank 加**独立短超时**（如 1.5s）+ 超时静默用融合结果（已有降级链，补超时上限即可）；④ 向量检索常驻 Chroma（`RAG_CHROMA=1` 已默认），确认不走 SQLite 暴力回退（数据量大时 P13）；⑤ `/api/search` 响应里附 `stage_ms`（已有 profile，返回给前端展示） |
| 调试方法 | 用 `/api/search/debug` 看四路明细：某路召回 0 条 → 查该路实现；看 `rerank_source` 判定走的哪级降级；`logs/*.json` 搜 `检索 profile:` 看阶段耗时分布                                                                                                                                                                                                                                                       |
| 验收指标 | 检索 p50 <500ms、p95 < 1.5s（含 rerank 缓存后）；rerank 缓存命中率>50%；四路并行后召回阶段耗时下降 ≥30%                                                                                                                                                                                                                                                                                          |

## §4 智能找文件



| 项    | 内容                                                                                                                                               |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 现状   | `api/search.py::api_find_files`：`search(top_k=30)` → 聚合到文件级 → `call_llm` 生成推荐理由                                                                  |
| 问题   | 全程串行：检索 + **LLM 生成理由阻塞返回**（`await call_llm`），文件多时理由 JSON 可能解析失败                                                                                  |
| 优化步骤 | ① 理由生成**并行**（`asyncio.gather` 或裁成 2 批）；② 理由生成失败降级为 "命中片段" 兜底文案（现在失败返回空 reason，前端显示空白）；③ 前端 `doFindFile` 加 "正在分析理由..." 独立 loading（与检索 loading 分离） |
| 验收指标 | 找文件全流程 p95 < 3s（含 LLM）；LLM 失败时仍返回文件列表 + 片段                                                                                                       |

## §5 对话（流式 / 引用 / 多轮）



| 项    | 内容                                                                                                                                                                                                                                     |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现状   | `ChatView.vue` 用 `fetch('/api/chat/stream')` + `TextDecoder` 逐块渲染；`orchestrator.py` 已有意图路由 / 改写 / 多轮 / 语义缓存；`engine.py` 引用清洗                                                                                                           |
| 问题   | ① **页面离开时流式请求未中止**（`onUnmounted` 只移除事件监听，无 `AbortController`）→ 切页后后台还在生成，浪费 token 且下次进入状态错乱；② "思考中..." 期间无超时兜底（LLM 三连降级最坏 60s×3）；③ 语义缓存 `lookup` 用 `numpy` 暴力扫描全表（`cache.py`），条目多后命中查询变慢                                               |
| 优化步骤 | ① 前端：`AbortController` + `onUnmounted` 中止流式；② 后端：对话链路加**总超时**（如 45s）与阶段超时（改写 8s / 检索 10s / 生成 30s），超时返回已生成部分 + 提示；③ 语义缓存：条目 >5000 时索引化（或按 query 哈希预筛再算相似度，避免全表扫描）；④ 多轮融合与缓存跳过逻辑已有（`multiturn_fused`），保持；⑤ 流式事件 `__SOURCES__` 已做单行安全，保持 |
| 调试方法 | `logs/*.json` 按 `trace_id` 搜一轮对话全链路耗时；`/api/health` 的 `last_chat_profile_ms` 看 rewrite/search/generate 分布；浏览器 Network 看 SSE 帧间隔定位卡顿段                                                                                                   |
| 验收指标 | 首 token 延迟 p50 < 2s；流式中止后 LLM 侧不再计费生成；对话 p95 < 10s（含检索）；缓存命中对话 < 1s                                                                                                                                                                    |

## §8 插件 / MCP / 配置面板



| 项    | 内容                                                                                                                                                                                                                          |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现状   | `plugins/`（manifest + 子进程 host 池）、`src/mcp/`（Smithery 市场）、`ConfigView.vue`（`/api/config` get/put）                                                                                                                           |

| 验收指标 | 挂机 24h 无残留子进程；配置面板每项有明确 "生效方式" 提示；MCP 超时不拖垮对话                                                                                                                                                                               |

## §10 后端基础性能（SQLite / 并发 / LLM）



| 项      | 内容                                                                                                                                                                                                                                             |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SQLite | WAL + `busy_timeout=5000` 已有；**写热点**在上传 / 入库 / 反馈；建议：① 长事务收敛（入库批量 `commit` 已做，检查分类 / 实体等小 stage 是否各自 commit）；② 高频只读（列表 / 详情）走 `get_conn()` 单连接已够，不要为每查询开连接；③ 索引检查：`chunks(file_id)`、`entity_files(file_id)` 已有，确认 `files(updated_at)`（列表排序）加索引 |
| 并发     | uvicorn 单进程；入库信号量 3；**对话 / 检索是 IO 密集**（LLM/rerank/embedding 等待网络），单进程 async 够用；若 CPU 密集（本地 embedding）与对话混跑会互相拖慢 → 可拆：embedding 入库进程与对话进程分离（两个实例共享 data/，SQLite WAL 支持），或 `EMBEDDING_ONNX=1` 加速本地推理                                             |
| LLM    | 统一降级链已有；补：① **provider 级熔断**（连续 5 次失败 → 停用 60s）；② **429/5xx 退避**（`call_llm` 只对截空重试，对 429/5xx 无退避，三连降级全撞限流窗口）；③ 并发请求数限制（对话 + 后台 stage 共用令牌桶，防把 API 打满）                                                                                          |
| 调试方法   | `llm_audit` 的失败率 / 降级率（`/api/health` 有）；慢 SQL：`sqlite3` 打开 `PRAGMA` 或日志搜 "慢请求"；并发压测用 §12 脚本                                                                                                                                                    |
| 验收指标   | 检索 / 对话期间批量入库不互相拖垮（p95 劣化 <30%）；LLM 429 后自动退避不三连失败；本地 embedding ONNX 后大文档入库时间下降 ≥50%                                                                                                                                                           |

## §11 调试方法工具箱（每个功能怎么定位问题）



```
用户反馈"XX 功能不行" → 按此流程定位：

1\. 先复现 + 抓后端日志

&#x20;  logs/\*.json 按关键词过滤：

&#x20;    路径   Select-String -Path logs\\\*.json -Pattern 'path":"/api/xxx'

&#x20;    慢请求 Select-String -Path logs\\\*.json -Pattern '慢请求|elapsed\_ms":\d{4,}'

&#x20;    trace  Select-String -Path logs\\\*.json -Pattern '你的trace\_id'   # 一轮请求全链路

2\. 看健康与指标

&#x20;  curl http://127.0.0.1:8099/api/health

&#x20;    → last\_search\_profile\_ms / last\_chat\_profile\_ms / llm\_degradation\_rate

3\. 检索质量问题 → 调试面板

&#x20;  前端 DebugView 或 POST /api/search/debug {"query":"...","top\_k":10}

&#x20;    → 看四路召回明细：哪路 0 条？rerank 前后排序变化？route 判成什么？
```
