## 1. 系统自述（请 AI 先读这段，建立完整上下文）

我维护一个**企业内网工业知识库 RAG 系统**（项目名"伏羲"，目录 `E:\更新RAG框架`），用于把连接器/材料/标准件/工艺类技术文档变成可检索、可问答的知识服务。它已经投入业务试用，但**使用体验不稳定、文档清洗效果差、性能不足、无法真正部署到生产环境**，我需要你以资深 RAG 系统工程师 / 知识库架构师的身份，帮我诊断并给出可落地的改造方案。

**技术栈**：
- 后端：Python 3.11 + FastAPI + SQLite（WAL 模式，FTS5 双表：unicode61+trigram）+ ChromaDB 向量库 + uvicorn 单进程
- 前端：Vue 3 + Element Plus + Vite + D3 图谱（SPA，由后端 `server.py` 托管构建产物）
- LLM：DeepSeek Flash/Pro + MiMo 三级降级链（`src/llm.py` 统一调用），embedding 本地 BAAI/bge-large-zh-v1.5（CPU，可切 SiliconFlow 远程），rerank SiliconFlow BGE → DeepSeek → 本地 TF-IDF 降级链
- 文档源：本地上传 + SeedDMS 文档管理系统直连导入（`src/dms/`）+ 文件夹监控（`scripts/watch_folder.py`）

**当前能力（都已实现且可运行）**：
- 入库引擎：Stage 编排（同步关键链 + 异步后处理），PDF 流式入库（大 PDF 边解析边向量化），OCR 乱码自动检测（jieba 分词命中率判定），MinerU 可选深度解析，多格式解析（pdf/ppt/pptx/docx/xls/xlsx/csv/txt）
- 检索：BM25（FTS5+jieba） + 向量（ChromaDB） + 图谱实体导航 + 文件名召回 四路混合 → 动态权重 RRF 融合 → 三级 rerank 降级 → 精确型号/标准号置顶（带权威等级加权） → 反馈点踩惩罚（默认关）
- 对话：意图路由（规则+LLM 兜底）→ 查询改写（规则同义词+LLM+跑偏检测）→ 多轮指代融合 → 语义缓存（版本化）→ Adaptive-RAG 复杂度路由 → 生成（引用编号由代码生成）→ 引用忠实度校验（杜撰编号清洗）
- 图谱：规则实体抽取（连接器型号/材料/标准号/工艺/参数）+ 共现边 + 语义边（material→compatible_process、standard→category）+ 文档相似边
- 工程：JWT+RBAC、结构化 JSON 日志（trace_id 贯穿）、请求慢查询告警、`/api/health` 健康检查、LLM 审计（`src/llm_audit.py`）、启动任务恢复 + Chroma 孤儿向量对账、pytest 20+ 测试文件、离线检索基准（`scripts/retrieval_benchmark.py`，20 条用例）

## 3. 我观察到的核心问题（详细根因见《01-深度诊断报告》）

1. **任务可靠性**：任务队列在内存（`engine.py` 的 `_tasks` dict），瞬时错误（LLM 超时/网络抖动）直接 failed 不重试；**服务重启后所有运行中任务被标记失败，用户必须重新上传**。
2. **文档清洗**：PDF 解析只输出纯文本，**标题/表格/页眉页脚结构全部丢失**（chunker 拿不到结构）；OCR 结果无后处理；**没有清洗质量评估**，用户不知道哪些文档可信。
3. **性能**：rerank 每次查询都远程调用无缓存；SQLite 暴力向量回退 O(N)；四路召回串行；前端 Element Plus 全量打包 938KB。
4. **数据安全**：**没有任何备份脚本**（`data/rag.db + Chroma + uploads` 是全部家当，损坏即归零）；无版本化；删除是硬删无回收站。
5. **可观测**：有日志/健康检查/单次 profile，但没有连续指标、没有阈值告警、没有历史趋势。
6. **模式落后**：还是"原始文档→chunk→检索"单向链路，**没有 LLM Wiki 编译层**（知识不沉淀、不可人工编辑、不越用越聪明）；没有评测闭环（改参数无依据）。

## 4. 我的优化目标（按优先级）

1. **引入 LLM Wiki 编译层**：把高价值文档（技术手册/规格书/标准）由 LLM 编译成结构化 Markdown 知识页（双链、版本、可人工编辑、可溯源回原文），查询时 Wiki 优先、RAG 兜底。**设计参考《02-LLM-Wiki混合架构设计》**，要点：新增 `wiki_pages/wiki_links/wiki_versions` 三张表；编译做成入库引擎的 async Stage；路由接入 `orchestrator`；复用现有 `entities`（实体关联）、`classification.py`（分类）、`GraphView`（双链图）、`extract_json`（结构化输出）、`call_llm_sync`（后台调用）。
2. **任务可靠化**：任务队列持久化到 SQLite、瞬时错误指数退避重试、重启断点续跑、死信可查。
3. **清洗升级**：PDF 结构化解析（Markdown 化：标题/表格/段落）、OCR 后处理（页眉页脚/页号过滤）、清洗质量分、清洗样本回归库。
4. **生产化**：备份/恢复脚本、服务守护（NSSM 或 Docker）、连续指标 + 阈值告警、版本化迁移、同名上传去重与版本策略、回收站、审计日志。
5. **检索演进**：rerank 结果缓存、parent-child（子块检索/父段喂上下文）、元数据过滤、multi-query（默认关）、空结果引导。
6. **评测闭环**：golden set 结构化 + Recall@K/MRR/nDCG + 答案忠实度 LLM judge + 回归门禁（详见《01》§3 健康度指标表）。

## 6. 硬性约束（AI 必须遵守）

1. **不推翻已验证的检索逻辑**：`search.py` 的四路召回 + RRF + 置顶是多次评测调优的结果，改造只做增量（加缓存/加路由/加并行），不重构融合逻辑；历史上有过"为重构而重构"的教训（`MEMORY.md` 有记录）。
2. **新功能必须可回滚**：新增能力用 config 开关控制（沿用 `config.py` 的 `"1"/"0"` 风格），默认关，评测通过再开。
3. **SQLite 单机架构不变**：内网单团队、文档量 < 50 万 chunk，不上 Postgres/Redis/ES，除非数据量触发阈值。
4. **复用现有能力**：图谱实体（`src/extraction/`）、分类字典（`src/classification.py`）、LLM 降级链（`src/llm.py`）、JSON 结构化输出（`extract_json`）、前端 D3（`views/graph/`）——不要重复造轮子。
5. **代码风格**：与现有文件一致（中文注释、文档字符串说明设计决策与历史坑、`logging.getLogger("rag.xxx")`、容错降级优先）。
6. **每个改动要能独立验证**：给出验证方式（pytest / `scripts/smoke_test.py` / 手工 curl），不能"改了不测"。
7. **注意已知坑**（`AGENTS.md` 有完整清单）：MCP 依赖必须 `mcp>=1.0.0,<2.0.0`（否则 httpx 被替换全项目崩）；MiMo 是推理模型 `max_tokens` 要宽裕；SPA fallback 会吞掉非 `/api/` 路由；FTS5 中文必须 Python 侧先分词；Chroma 遥测必须静默（posthog 版本冲突）。
