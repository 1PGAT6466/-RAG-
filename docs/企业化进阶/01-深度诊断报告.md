# 01 · 深度诊断报告(伏羲 RAG 知识库)

> 诊断基线:2026-09,基于全量代码走读(backend 65+ py 文件、前端 11 个视图、schema、LLM 层、图谱、DMS 集成、运维脚本)。
> 本文只讲"真实存在的问题 + 根因 + 修法",不重复已有优点(优点见各文件头注释)。

---

## 1. 系统现状速览(一句话版本)

**功能面**:登录 / 文档管理(上传、分类、标签、文件夹)/ 对话(流式、引用、多轮、联网)/ 检索调试面板 / 图谱 / DMS 导入 / 插件 / MCP 市场 / 配置面板 / 反馈--11 个前端视图,后端路由 50+。

**技术面**:FastAPI + SQLite(WAL, FTS5 双表) + ChromaDB + 本地/远程双路 embedding + 规则实体图谱 + 三级 LLM 降级链(DeepSeek Flash→Pro→MiMo)+ 插件子进程 + SeedDMS 直连。

**结论先行**:这不是玩具,**是一个"单人/小团队能做到的上限"的系统**。它的问题不在"有没有"(该有的都有),而在四个系统性缺陷:
1. **所有高级能力都做成了"默认关/依赖外部 key"的可选件**,导致用户看到的真实体验只有"上传→检索→问答"这条裸链路;
2. **结构化信息在解析阶段被丢弃**(PDF→纯文本),后续所有环节(切块、图谱、Wiki)都在残缺数据上工作;
3. **没有"质量可见性"**:清洗好不好、检索准不准、任务为什么失败,用户和开发者都看不见;
4. **没有生命周期与部署保障**:无备份、无版本、无重试、无容器化--"只能在电脑里跑"的根本原因。

下面按模块给真实问题清单(现象 → 根因 → 影响 → 修法),每条都标了严重度。

## 2. 真实问题清单

### 2.1 解析清洗层("文档清洗能力不行"的根因区)

| # | 问题 | 根因 | 影响 | 修法 | 严重度 |
|---|---|---|---|---|---|
| P1 | **PDF 解析输出纯文本,结构全丢** ✅ 已修复 | `parser.py::_parse_pdf` 用 `page.get_text("blocks")` 重排后 `"\n".join` 纯文本;`parse_pdf_streaming` 同理 | 标题层级、表格、页眉页脚、列表结构全部丢失;chunker 的 `HEADING_PAT` 在纯文本上命中率低 → 切块语义散;图谱实体抽取在扁平文本上漏实体 | 引入**结构化中间格式**:解析产出 Markdown 化文本(`# 标题` / `| 表格 |` / 段落),用 fitz dict API 提取字体信息自动识别标题层级 | ✅ 已修复 |
| P2 | **OCR 结果无后处理** ✅ 已修复 | `_parse_pdf_ocr` 逐页拼接,页眉页脚、页号、重复行原样保留 | 向量库被页眉/页码污染,检索噪声高;可读模式展示脏 | OCR 后处理管线:页眉页脚检测(连续页相同行)、页号过滤、段落合并、重复行去重 | ✅ 已修复 |
| P3 | **无清洗质量评估** ✅ 已修复 | 没有"这篇文档洗得怎么样"的量化 | 用户不知道哪些文档可信;优化无从下手 | 解析后计算**质量分**(乱码比例 / 结构完整度 / 有效 token 率 / OCR 置信度),写入 `files.quality_score`,前端列表展示 + 低质量标记 | ✅ 已修复 |
| P4 | **清洗规则无样本回归** | 无样本库、无清洗测试 | 改一条清洗规则,不知道哪些文档变好/变坏 | `data/eval/cleaning_samples/` 存 20~50 篇典型脏文档(乱码 PDF/扫描件/表格/页眉),清洗改动必须跑样本回归 | 🟡 P1 |
| P5 | **docx 表格转 markdown 但不还原单元格语义** | `_parse_docx` 表格 `' | '.join(cells)` | 长表格超 chunk 被硬切,检索时表格语义断裂 | 表格行按"单元格=值"或保持 markdown 表格语法 + 表格专有切块策略(见 4.2) | 🟡 P1 |
| P6 | **xlsx 大表全量进文本** | `_parse_xlsx` 逐行 join | 上万行 BOM 表 → 单 chunk 无意义、embedding 浪费 | 大表(>N 行)走"列头+抽样行+统计摘要",或按行组分块保留结构 | 🟡 P1 |

### 2.2 切块索引层

| # | 问题 | 根因 | 影响 | 修法 | 严重度 |
|---|---|---|---|---|---|
| P7 | **无 parent-child,表格/长文档上下文断裂** ✅ 已修复 | chunker 只产扁平 400 字块,`_build_reference_context` 直接拼 top_k 子块(各截 800 字) | 问“标准件新表里导轨的规格”时,命中碎片块缺少表格上下文 | 切块时记录 `section_id`(父段落),检索命中子块时优先喂父段;`chunks.metadata` 已可承载 | ✅ 已修复 |
| P8 | **embedding 无去重缓存** | `encode()` 每次全量计算 | 重入库/近似文档重复烧钱烧时间 | LRU `text→vec` 缓存(复用 `semantic_cache` 模式) | 🟡 P1 |
| P9 | **标题感知只靠正则** | `HEADING_PAT` 对"1.1.1 "、"(一)"、PDF 无标题文本无效 | 章节结构感知有限 | 从 P1 的 Markdown 化解析直接取标题层级;chunker 改为消费结构化文档 | 🔴 P0(随 P1) |

### 2.3 检索层(已很强,剩硬伤)

| # | 问题 | 根因 | 影响 | 修法 | 严重度 |
|---|---|---|---|---|---|
| P10 | **rerank 每次远程调用、无缓存** | `rerank.py` 直接打 SiliconFlow | 每问 +0.5~2s 延迟 + 费用;SiliconFlow 抖动时整链降级 | rerank 结果按 `(query_hash, chunk_id)` 缓存;加本地 `bge-reranker-v2-m3` 选项 | 🟡 P1 |
| P11 | **无 multi-query** | 单查询检索 | 语义模糊问题召回单一视角 | 对 `route==semantic` 用 LLM 生成 2~3 变体 → 合并去重 → RRF(flag 默认关,评测通过再开) | 🟡 P1 |
| P12 | **无元数据过滤参数** | search API 只有 `query, top_k` | 无法按分类/权威/日期收敛 | API 加 `category/authority_min/date_range` 过滤,召回层 SQL 预过滤 | 🟡 P1 |
| P13 | **SQLite 暴力回退 O(N) 解包 1024 维** | `_vector_search_sqlite` 全表逐行 `_unpack`+cosine | 数据量上万后慢(性能问题根因之一) | 数据量 >5 万 chunk 时评估:常开 Chroma(已默认开)/ 换 HNSW 索引(`sqlite-vec`) | 🟡 P1 |
| P14 | **四路召回串行** | `search()` 顺序 await | 每路多几 ms~几十 ms | `asyncio.gather` 并行召回(BM25/向量/图谱/文件名互不依赖) | 🟢 P2 |
| P15 | **benchmark 只有 20 条 top1 判定** ✅ 已修复 | `retrieval_benchmark.py` 判 `expect in top_file` | 无法度量召回率/排序质量,改参无依据 | 升级:golden set 32 条 + Recall@K/MRR/nDCG + 离线模式 + 工业/语义分类统计 | ✅ 已修复 |

### 2.4 对话生成层

| # | 问题 | 根因 | 影响 | 修法 | 严重度 |
|---|---|---|---|---|---|
| P16 | **上下文组装 token 预算硬编码** | `_build_reference_context` `max_chunk_chars=800 / max_total_chars=6000` | 模型上下文未利用(DeepSeek 64k 只用 6k 字符);长文档能力浪费 | 按模型窗口动态计算预算;命中父段模式时单文档可整段读入 | 🟡 P1 |
| P17 | **无 grounding 校验** | 只有引用编号清洗,无"断言是否有文档支撑" | 幻觉句(有引用编号但内容无关)无法拦截 | 生成后 entailment 检查:关键断言(数值/结论句)在引用 chunk 中找不到支撑 → 标记"缺乏支撑" | 🟡 P1 |
| P18 | **LLM 调用无限流/熔断** | `call_llm*` 有降级链但无 429/5xx 退避、无熔断状态 | 限流时三连降级全失败 → 对话失败 | provider 级令牌桶 + 熔断器(连续失败 N 次 open,冷却后 half-open) | 🟡 P1 |
| P19 | **无上下文命中质量检查** | 检索空时只返回"未检索到相关内容" | 用户无引导、无法自纠 | 空结果时给出:相近问题推荐 / 上传建议 / "试试去掉口语词"等引导 | 🟢 P2 |

### 2.5 任务与数据生命周期("功能点莫名不可用"的根因区)

| # | 问题 | 根因 | 影响 | 修法 | 严重度 |
|---|---|---|---|---|---|

| P24 | **links 表语义混乱** | MEMORY 已承认:`add_link` 有时存 chunk_id 有时存 file_id | 图谱/backlink 数据不可信 | 不修旧表(风险),新增干净语义的 `wiki_links`/`doc_links` 专用表,旧表只读 | 🟡 P1 |

## 4. 关键根因总结(一句话版)

1. **体验差** = 高级能力全部"默认关/靠外部 key" + 任务失败无重试无解释 + 空结果无引导。
2. **清洗差** = PDF 解析丢结构 + OCR 无后处理 + 无质量评估 + 无样本回归。
3. **性能差** = rerank 远程无缓存 + 暴力向量回退 + 串行召回 + 前端全量打包。
4. **不能部署** = 无备份 + 无容器 + 无 CI + 无迁移体系。
5. **落后于模式** = 无 Wiki 编译层(知识不沉淀)+ 无评测闭环(改不动参数)+ 无反馈闭环(系统不越用越聪明)。

## 5. 结论

这份诊断里 P0 共 7 项(P1/P3/P7/P15/P20/P21/P25),其中 **P3(清洗质量分)✅ P15(检索评测基线)✅ P20(任务队列持久化+重试)✅ P21(备份+恢复)✅ P25(健康指标端点)✅ 已修复**(2026-09-10);剩余 P0:P1/P7(均为 Phase 1 内容)。
LLM Wiki 引入是架构级新增(P30),独立成文档设计;
生产部署是收尾项(P28 等),排到最后。

顺序:**先止血(P0)→ 再引进(Wiki)→ 后收尾(部署)**,详见 04 路线图。
