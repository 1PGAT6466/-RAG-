# 04 · 分阶段迭代路线图（从"能跑"到"敢用"）

> 总原则：**每阶段都有可验收的数字，每阶段都可独立上线，不搞一次性大重构。**
> 编号对应：01 诊断报告的 P0~P33、02 文档的 M1~M3、03 文档的章节。

---

## Phase 0 · 止血（第 1~2 周）—— 解决"用起来老出问题"

**目标**：任务不再莫名失败、数据不再裸奔、质量问题开始"看得见"。

| 任务 | 对应项 | 产出 | 验收标准 |
|---|---|---|---|
| 任务瞬时错误重试 + 重启续跑 | P20 | `task_queue` 表 + `engine.py` 改造（checkpoint/退避重试/死信） | kill 服务 → 重启 → 任务续跑成功；模拟 LLM 超时 → 自动重试 2 次成功；失败任务带可读 error |
| 首次全量备份 + 恢复演练 | P21 / 03§2 | `backup.py` + `restore.py` + 计划任务 | 备份 zip 可校验；**恢复演练成功一次**（这是唯一硬性验收） |
| 检索评测基线（golden set + 指标） | P15 | `data/eval/golden_retrieval.json`（≥30 条）+ `scripts/eval_retrieval.py`（Recall@K/MRR/nDCG，离线模式） | 跑分可复现、可存档；改动任何检索参数能在 30 分钟内看到分数变化 |
| 清洗质量分 + 低质量标记 | P3 | `files.quality_score` + 解析后计算 + 列表展示 | 每篇文档有质量分，低质量文档前端可见可筛选 |
| 健康指标端点 + 巡检告警 | P25 / 03§4 | `/api/metrics` + 巡检器（阈值→webhook） | 测试告警能发出；指标可回溯 |

**退出条件**：以上 5 项全部验收通过。Phase 0 结束时的系统 = "任务可靠 + 数据安全 + 质量可见"。

---

## Phase 1 · 引进（第 3~5 周）—— 引入 LLM Wiki 编译层 + 修清洗根因

**目标**：知识开始沉淀（Wiki），核心文档解析质量上台阶。

| 任务 | 对应项 | 产出 | 验收标准 |
|---|---|---|---|
| Wiki 地基 + 编译链路 | 02 M1~M3 | 3 张表、`wiki_compiler.py` Stage、`wiki.py` API、`WikiView.vue`、双链图 | 见 02 §7 的 5 条验收（命中率 ≥60%、忠实度 ≥4/5、可溯源、人工编辑不被覆盖、RAG 不回归） |
| PDF 结构化解析（Markdown 化） | P1/P9 | `parser.py` 产出结构化文本（标题/表格/段落标记），chunker 消费结构 | 抽样 10 篇：标题层级识别率、表格保留率明显提升；清洗样本回归通过 |
| OCR 后处理管线 | P2 | 页眉页脚/页号过滤 + 段落合并 | 扫描件入库后：页眉/页号词不再出现在 top 检索结果 |
| 清洗样本库回归 | P4 ✅ | `data/eval/cleaning_samples/` + 清洗测试 | 清洗规则改动必须跑样本，回归报告留档 |
| 检索演进（rerank 缓存 + parent-child） | P10/P7 | rerank 缓存表、`section_id` 切块 + 上下文父段模式 | rerank 缓存命中率 >50%；表格类问题评测通过率提升 |
| CI 门禁 | P26 ✅ | 内网 runner（或 GitHub Actions）：pytest + 检索评测门禁 | 每次 push 自动跑；评测分数低于基线即失败 |

**退出条件**：Wiki 已能在真实问题上被问答命中并溯源；核心文档解析质量有可量化提升；CI 门禁生效。

---

## Phase 2 · 收尾（第 6~8 周）—— 生产化 + 体验

**目标**：可部署、可运维、体验补全。

| 任务 | 对应项 | 产出 | 验收标准 |
|---|---|---|---|
| 服务化 + 运维入口 | P28 / 03§3 | `ragctl.cmd`（start/stop/status/backup/logs）+ NSSM 或 Docker 二选一 | 崩溃自拉起；开机自启；一键备份 |
| 版本化迁移 | P27 | `schema_version` 表 + 有序迁移脚本 | 从旧版本升级到新版本脚本化可跑 |
| 同名上传版本化 + 内容去重 | P22 ✅ | 上传 sha256 检测 + 替换策略 | 重复上传不重复入库；替换走级联安全 |
| 回收站（软删） | P23 ✅ | `files.deleted_at` + 回收站视图 | 误删可恢复，30 天自动清 |
| 元数据过滤检索 | P12 ✅ | search API 加 category/authority/日期过滤 + 前端筛选器 | 按分类收敛检索结果正确 |
| 空结果引导 | P19 ✅ | 相近问题推荐/上传建议 | 空结果不再只有一句话 |
| 前端按需引入 | P29 | Element Plus 按需 | 打包体积下降 ≥50% |
| 审计表 + 埋点 | 03§6 ✅ | `audit_log` + 管理查询页 | 可回答"上周谁删了什么" |

**退出条件**：全部验收通过——系统可部署、可备份、可监控、可审计。

---

## Phase 3 · 演进（持续，按需）

| 方向 | 触发条件 | 内容 |
|---|---|---|
| Agentic 检索 | 多步/跨分类问题占比高 | `complex` 路由两步检索（先窄分类再细检索）✅ |
| 多轮检索 | 语义模糊查询 Recall 不足 | multi-query（flag 默认关，评测通过再开）✅ |
| LLM 熔断/限流 | 外部 API 抖动影响体验 | provider 级令牌桶 + 熔断器 ✅ |
| 文件级权限 | 多部门使用 | SeedDMS 权限映射 + 检索过滤 ✅ |
| 向量扩展 | chunks > 50 万 | 评估独立向量服务（03§8）（按需） |
| 答案 grounding 校验 | 用户反馈"回答不对"比例高 | entailment 检查 + 坏例回流 ✅ |

---

## 投入与收益对照

| 阶段 | 大约投入 | 用户能感知的收益 |
|---|---|---|
| Phase 0 | 2 周 | 任务不莫名失败、数据不怕丢、质量问题可见 |
| Phase 1 | 3 周 | 概念/选型问题回答明显连贯、文档清洗变干净、Wiki 可人工维护 |
| Phase 2 | 3 周 | 能部署到服务器/内网、可备份可监控、体验补全 |
| Phase 3 | 按需 | 系统越用越准、容量可扩展 |

## 最后提醒

**每个 Phase 结束时跑一次 01 §3 的健康度指标表**，用数字确认"真的在变好"，而不是"感觉在变好"。这是这套路线图和普通清单的本质区别。
