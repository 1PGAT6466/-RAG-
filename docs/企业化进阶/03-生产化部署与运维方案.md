# 03・生产化部署与运维方案

> 目标：把 " 只能在自己电脑上 
>
> `python server.py`
>
>  跑 " 的系统，变成
>
> **可部署、可备份、可监控、可恢复**
>
> 的内网生产服务。
> 原则：
>
> **先保数据安全（备份），再保可用性（服务化 / 监控），最后保效率（CI / 迁移）**
>
> 。你的环境是 Windows 内网单机起步，方案按 "Windows 单机 → 可选 Docker" 两档给。



***

## 1. 部署目标架构



```
&#x20;                   ┌───────────────────────────────┐

&#x20;内网用户浏览器 ────▶│  Nginx（可选，反向代理+HTTPS） │

&#x20;                   └───────────────┬───────────────┘

&#x20;                                   │ 8099

&#x20;                   ┌───────────────▼───────────────┐

&#x20;                   │  服务进程（uvicorn，单机）      │

&#x20;                   │  server.py → FastAPI + SPA     │

&#x20;                   └───────────────┬───────────────┘

&#x20;           ┌───────────┬───────────┼───────────┬───────────────┐

&#x20;           ▼           ▼           ▼           ▼               ▼

&#x20;       data/rag.db  data/chroma  data/uploads  data/images  logs/（JSON 轮转）

&#x20;  （SQLite WAL）   （向量）       （原文）      （图片）      （审计/日志）

&#x20;           └──────────────────────┬──────────────────────────────┘

&#x20;                                  ▼

&#x20;                       scripts/backup.py → backups/（每日快照，保留 N 份）
```

**关键决定：**



* 单机 + SQLite + Chroma 在**内网、单团队、文档数 < 50 万 chunk** 的场景完全够用，**不要为了 "企业级" 硬上 Postgres/ES/K8s**—— 那是给多实例、多团队、海量数据准备的。你的路径是 "先把单机做扎实"。

* `server.py` 单进程即可；如需更高并发，uvicorn `--workers 2`（注意 SQLite 连接与内存任务需随改造同步评估，见 4.2）。

## 2. 数据安全：备份与恢复（P0，先做）

### 2.1 `scripts/backup.py`（新增）



```
"""

每日备份：data/rag.db（VACUUM INTO 一致性快照）+ data/chroma + data/uploads + data/images

&#x20; → backups/rag-YYYYMMDD-HHMMSS.zip，保留最近 N 份（默认 7）

用法：python scripts/backup.py \[--keep 7] \[--dest backups]

"""

\# 关键实现点：

\# 1. SQLite 一致性快照：sqlite3.connect(DB\_PATH).execute(

\#      "VACUUM INTO ?", (tmp\_rag\_db,))   # 替代文件复制，避免 WAL 未合并丢数据

\# 2. Chroma：整个 data/chroma 目录压缩（先 flush/compact）

\# 3. .env 单独脱敏备份（JWT\_SECRET 必须保留否则 token 全失效；API key 保留）

\# 4. 备份完成后校验 zip 可打开、rag.db 可 SELECT 1
```

### 2.2 `scripts/restore.py`（新增）



```
"""

恢复：停服 → 解压备份 → 覆盖 data/ → 启动 → 跑启动对账（孤儿清理/任务恢复）

用法：python scripts/restore.py backups/rag-YYYYMMDD-HHMMSS.zip

"""
```

### 2.3 备份策略



| 项  | 策略                                         |
| -- | ------------------------------------------ |
| 频率 | 每日 1 次（业务低峰，如 02:30）+ 重大变更（批量入库 / 升级）前手动   |
| 保留 | 7 份滚动；关键节点（上线前）单独留一份                       |
| 存放 | 本机 `backups/` + **定期拷到第二块盘 / 共享目录**（防磁盘损坏） |
| 演练 | **每月至少恢复演练 1 次**—— 没有演练过的备份等于没有            |
| 验证 | 备份后脚本自动 `SELECT 1` + zip 完整性校验，失败告警        |

### 2.4 挂 Windows 计划任务



```
schtasks /create /tn "RAG备份" /tr "python E:\更新RAG框架\scripts\backup.py" /sc daily /st 02:30
```

## 3. 服务化与守护（P0/P1）

### 3.1 Windows 档（你的现状最简路径）



* `scripts/ragctl.cmd` 统一运维入口：



```
ragctl start     # 后台启动（nssm 或 pythonw + 日志重定向）

ragctl stop      # 优雅停止（发 SIGTERM，等待任务收尾）

ragctl status    # 查 /api/health + 进程存在性

ragctl restart

ragctl backup    # 调 backup.py

ragctl logs      # tail logs/latest.json
```



* 推荐用 **NSSM**（`nssm install RAG`，配置 `server.py` 启动命令、日志输出、自动重启），比裸 `start_service.cmd` 稳（崩溃自拉起、开机自启）。

### 3.2 Docker 档（可选，迁移 / 交付更干净）



* `Dockerfile`：`python:3.11-slim` + `requirements.txt` + 前端 `dist/` + 模型权重目录挂载；

* `docker-compose.yml`：服务 + 三个 volume（`data/`、`logs/`、`backups/`）+ `restart: unless-stopped` + healthcheck（`curl /api/health`）；

* 注意：Chroma / 本地 embedding 模型权重（`data/models/`）要打进镜像或挂载，避免每次构建重下。

### 3.3 反向代理（可选但推荐）



* 内网 Nginx：80 → 8099，加 HTTPS（自签 / 内网 CA）—— 解决：浏览器安全提示、访问统一入口、后续可加限流。

* 你的 `CORS_ORIGINS` 需追加代理域名。

## 4. 监控与告警（P1）

### 4.1 轻量巡检器（不引 Prometheus 的第一档）



* `scripts/health_check.py` 升级为**巡检器模式**：


  * 每 5 分钟调 `/api/health` + 新增 `/api/metrics`（见下）；

  * 命中阈值 → webhook 通知（钉钉机器人 / 企业微信 / 邮件，任一即可）；

  * 历史写入 `logs/metrics_history.jsonl`，可回溯 30 天。

* 挂计划任务每 5 分钟跑（或用线程常驻）。

### 4.2 `/api/metrics` 指标清单（新增端点，Prometheus 文本格式，零依赖手写即可）



| 类别  | 指标                                  | 告警阈值（示例）                       |
| --- | ----------------------------------- | ------------------------------ |
| 服务  | 请求 QPS、p50/p95 延迟                   | p95 > 3s（对话）/ 1.5s（检索）持续 10 分钟 |
| LLM | 调用量、失败率、降级率（`llm_audit` 已有数据）       | 降级率 > 20%/ 小时                  |
| 任务  | 成功率、重试次数、dead 数                     | 失败率 > 10%/ 小时                  |
| 缓存  | 语义缓存命中率、rewrite 命中率                 | 命中率骤降 > 30%                    |
| 数据  | files/chunks/entities 计数、孤儿向量数、磁盘剩余 | 磁盘 <10GB、孤儿> 0                 |
| 备份  | 最近备份时间、校验结果                         | 超过 36h 未成功备份                   |

### 4.3 日志



* 现有 JSON 轮转（`logging_setup.py`）已够用；补：保留 30 天、日志目录纳入备份外的独立清理任务；

* 需要 "查上周某问题" 时：`logs/*.json` 按 `trace_id`/`path`/`level` 过滤，先满足单机可查，不上 ELK。

## 5. 安全加固（P1，内网也要做）



| 项     | 现状                           | 动作                                 |
| ----- | ---------------------------- | ---------------------------------- |
| 登录爆破  | `rate_limit.py` 有 IP 限流      | 保留；必要时加账号锁定（连续 N 次失败锁 15 分钟）       |

## 8. 容量与扩展路径（现在不用做，但要写进运维手册）



| 信号            | 动作                                          |
| ------------- | ------------------------------------------- |
| chunks > 10 万 | 评估 `sqlite-vec` HNSW 索引替代暴力回退（P13）          |
| chunks > 50 万 | 评估向量独立服务（Chroma Server）或 Postgres+pgvector  |
| 并发 > 50 用户    | uvicorn `--workers 2-4` + 任务队列与 SQLite 连接复查 |
| 多团队 / 多部门     | 文件级 ACL（对接 SeedDMS 权限）+ 审计先行（P2）            |
| 多实例 / 异地      | 才考虑 Redis/Celery 级任务队列与独立检索服务               |

**一句话**：单机单团队，把 SQLite+Chroma 用好、备份做扎实、监控看得见，就是合格的生产系统；不要提前为不存在的数据规模买单。
